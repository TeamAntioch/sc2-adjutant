# Screenplay format

A Mission's Screenplay is one Markdown file, named by the Blueprint's `screenplay.script.source` (relative to the Blueprint). Core reads this format and nothing else. A Campaign Pack's Screenplay Source must return it, whatever the Campaign keeps its Screenplays in. The parser is `packages/core/src/script/parse-script.ts`. A Campaign Mod's interludes and hub chats are Screenplays in the same format, each named by its Mod Blueprint's `screenplays` ([mod-screenplays.md](./reference/mod-screenplays.md)).

```markdown
# 01-3: THE OUTPOST

- Chapter: 3
- Revision: 7c6b8db00f8d

## Scene 1: THE YARD

> Two officers stand by the gate.

**RAYNOR** `outpost-01`: [Serious 40]Hold here[/Serious] until the convoy comes.

**MATT HORNER**: Understood, sir.

## Scene 2: THE CONVOY

**RAYNOR**: [Happy 30]Right on time.[/Happy]
```

## Title

The first `# ` heading is the title. If its first word ends in a colon, that word is a prefix and is dropped: `# 01-3: THE OUTPOST` is titled `THE OUTPOST`. Any other heading is the title whole, so `# Lava Field: The Return` keeps its colon.

## Header fields

`- Key: value` lines before the first `##` heading are header fields, such as `- Chapter: 3`. The first line for a key wins. Core doesn't read them itself. A Campaign Pack's naming template can, for example to build a conversation id from the chapter. Bullets after the first `##` heading aren't fields.

## Scenes

Each `## Scene N: TITLE` heading starts a scene. `N` is the scene's number, and the Blueprint's `screenplay.script.cues` name scenes by it, so a renumbered scene needs its cue moved. A cue may be a Beat's start (`{ "type": "beatStarts", "beatId": "harried" }`, once, whichever of the Beat's `startsWhen` started it). A Beat may start, too, at one of a Mechanic's moments, named as a cue names it (`"startsWhen": [{ "type": "mechanic", "mechanicId": "meditation_ruin1", "cue": "ends" }]`): the Mechanic's triggers start it there, after what the Blueprint cues at the same moment. The Beat's trigger plays its Cinematics and trigger scenes, then pings its reveals, then runs "Beat - <title> Lines" without waiting, which plays the Transmissions cued after the last of them, in cue order, each queued behind the lines already playing: so the pings and the Beat's Mechanic actions don't wait on those lines, and a later Beat starting during them doesn't drop the pings. Transmissions cued before a Cinematic or trigger scene on the same cue play in the Beat's trigger, before it. An entry's `afterSeconds` plays its scene that long after the cue, once however often the cue fires, counted in AI time (which a playing Cinematic or trigger scene pauses), without holding up the rest of what the cue plays. A cue may be a bookmark of a Cinematic (`{ "type": "cinematicBookmark", "cinematicId": "radio", "bookmark": "flash" }`, once, as its cutscene plays past a bookmark its shot list declares). Prefer a `scenePlayed` cue: the engine doesn't hear a bookmark when the player skips, so by default (`"onSkip": "skip"`) a skip never runs the cue, and `"onSkip": "fire"` has the Cinematic's cleanup run it late instead; `check` warns about every one. A cue may also be a unit nearing another (`{ "type": "anchorNears", "anchorId": "raider", "targetId": "assimilator_e2", "distance": 10 }`, once, when either unit's move brings them within `distance` cells), or nearing the first of a player's units of a type in place of `targetId` (`"unitType": "Assimilator", "player": 1`), the unit neared then kept for the scene to film. Either unit may be a Wave's unit bound to an Anchor (a Wave unit entry's `anchorId`, ADR 0008), which is there only once its send creates it: the range event reads the unit it measures from as the map starts, so such a cue looks instead, every 0.25 game seconds, for the target within `distance` of the Anchor's unit's position (point to point for a `targetId`, a circle for a unit type). That check is off until the send creates the Wave's unit, so it never runs on a difficulty where its count is 0, and it turns itself off for good once either unit is dead. A cue may also be an Anchor's unit starting a data effect (`{ "type": "effectStarts", "anchorId": "raider", "effectId": "RaiderStrikeDamage" }`, once, compiled to "Cue - <Anchor> Starts <effect>" on Player Uses Effect for any player, its caster the Anchor's unit, which may be a Wave's unit, never matched before its send creates it, as an effect with no caster unit never matches), the effect's target unit then kept for the scene to film, or its caster for an effect on a point, which has none. The caster stays the Anchor's unit down a chain of effects, so name the effect a search runs on the unit it found, not the search, whose target is no unit: the first of them (the effect that starts the strike, such as one that launches its marker or missile) to cue the scene as the strike starts, or its damage to cue it as the strike hits. `check` refuses an `effectStarts` on an Anchor that isn't a unit, and warns of an effect id that neither the game's data (`data/tech-catalog.json`), the Campaign Mod's, a Plugin Mechanic's nor the Mission package's own defines, which would never fire; data it can't read, such as a packed dependency's, may define it. Prefer it to `anchorNears` by unit type when a scene aimed at the cue's unit frames what the data does: `anchorNears` keeps the first of the type in a circle round the Anchor's unit, measured from the units' centres and counting units under construction, so it can frame another unit than the one a data search picked, nearest to the unit's edge and complete, while the effect gives exactly the unit struck, as that effect runs. A cue may also be Objectives completing (`{ "type": "objectivesComplete", "objectiveIds": ["collect_junctions", "recover_warp_drive", "deliver_scv", "arm_silo"], "count": 2 }`, once, as the Objective that brings the count of them Completed to `count`, or to all of them without it, completes: so entries at `count` 1, 2 and 3 play a line after the first, second and third of four any-order Objectives, README "Objectives complete"; `"exactly": true` in place of `count` is the Objectives named and no others, to play a part by which are done). A cue may also be a player's structures of a type dying (`{ "type": "structureDies", "player": 1, "unitType": "Assimilator", "count": 2 }`, once, at the `count`th loss, 1 when left out, so a first and a second loss can each cue a line); or an encounter's end (`{ "type": "encounterEnds", "encounterId": "fortress" }`, once), which the encounter declares as `endsWhen: { "afterSeconds": 15, "damageTaken": 300 }`, the first of a time from its start (AI time) and the damage its attackers have taken together, either or both, or as `behavior: { "anchorId": "raider", "behavior": "RaiderFortressEncounter" }`, a data Behavior its start adds to the Anchor's unit (whether or not a cue plays on its end), the end coming when the unit has none of it left (every stack and instance gone) or dies, so the Behavior's duration and removal validators set the clock and what cuts it short. The Behavior's clock runs in game time, which a playing Cinematic or trigger scene doesn't pause (unlike `afterSeconds`' AI time), so a scene the encounter's start plays eats into its duration: give the Behavior the scene's length on top. A unit already dead, or one the Behavior didn't take on, ends the encounter at once, after the scenes its start plays. An encounter with both ends on the first of them, and `check` refuses an `encounterEnds` cue on an encounter with neither. An encounter starts when a unit of its `player` (player 1 when left out) enters its zone, or on its `startsWhen` instead: an Anchor's unit dying, entering a Zone or being captured, that is, becoming player 1's (`{ "type": "anchorEntersZone", "anchorId": "hero", "zoneId": "fortress" }`, as an objective's `completeWhen` gives them), so a hero's arrival starts it and not the army that came first. `check` refuses a `player` beside `startsWhen`, which nothing reads. An encounter's `fromBeat` (`"fromBeat": "last_call"`) arms it only once that Beat has started, as a victory or defeat condition's or an objective's `completeWhen` does (README, "Armed from a Beat"): until then its trigger is off, and as the Beat arms it, it starts at once if its start already holds, the Anchor's unit dead, captured or in the Zone for a `startsWhen`, or one of its `player`'s units in its zone without one. An encounter armed so may start with no unit that set it off, so its attackers go for the `startsWhen` Anchor's unit, or the first of the player's units in its zone, rather than the triggering unit's position. The layout checks schedule it from the later of its `fromBeat` and the Beat that starts on its `startsWhen`. The layout checks and preview place an encounter with `startsWhen` where it starts: the Zone its Anchor enters, or where the Anchor stands for its dying or capture, from the Beat that starts on the same condition (the first Beat when none does). An entry's `from` plays only part of its scene: the lines from that stage direction to the next one (or the scene's end), addressed as `S<scene>><n>`, `S07>2` for scene 7's second, so a scene of several messages, each introduced by a stage direction, plays each on its own cue. The stage direction must be its own scene's, the scene must play as Transmissions (a Cinematic or trigger scene plays whole), and the pull refuses a Screenplay that has lost it or left it no lines. Its address is its place in the scene, so a stage direction added or cut before it at the Source renumbers it, and the cue must follow. An entry's `line` (a sound ID of its scene, `{ "scene": 5, "line": "D-01-01-05-002-NOVA", "cue": { "type": "structureDies", "player": 1, "unitType": "Assimilator", "count": 2 } }`) plays only that line, queued as a part is, so a scene of one-off lines with no stage directions between them plays each on its own cue. An entry names a part or a line, not both; the scene must play as Transmissions; and `check_workspace` reports a sound ID that is another scene's line, or no line of the scene, which the compile refuses too. A `line` is a sound ID as the naming makes one: letters, digits, `_`, `-` and `.`. A sound ID the Campaign Pack names by the line's place in its scene (as core's default naming does) changes when a line is added or cut before it at the Source, moving another line onto the cued ID. So the pull follows the cued line from the copy it replaces and refuses a Screenplay that has lost it, or moved it to another sound ID, and `refresh-screenplay` moves the cue with it. A Screenplay with no Source, edited in place, has no earlier copy to follow from: change the cue with the line. A cue may also be another scene, or part or line of one, having played (`{ "type": "scenePlayed", "scene": 7, "from": "S07>4" }`, or `"line"` for a line, both left out for the whole scene): once, the first time a cue entry of that scene and part or line (the same `scene`, `from` and `line`, so a line's entry doesn't count as its whole scene's; `S7>4` and `S07>4` are one stage direction, so either spelling names its part) has played its last Transmission, or its Cinematic or trigger scene has handed back (after a run that hands on, once the run's last scene has handed back), so an entry's `afterSeconds` counts from the scene's real end however long it queued behind other lines. It compiles to "Script Scene <n> [<part or line>] Played", run without waiting from the trigger that played the scene. Only a cue entry's play counts: a Wave warning that plays the scene doesn't fire it. `check_workspace` reports a `scenePlayed` cue on a scene, part or line no cue entry plays, one naming a part and a line, on a stage direction of another scene, and a cycle of entries that wait only on each other having played (a loop in which some scene also has a cue of another kind still plays, each entry once). The compile refuses one, on a script scene, a transition or an inline scene, waiting on a victory outro, which ends the game, or on a scene only a victory or defeat condition's cues play, after which the game is over. An entry's `after` keeps a scene's parts in order (`{ "scene": 7, "from": "S07>4", "cue": { "type": "beatStarts", "beatId": "fallback" }, "after": { "scene": 7, "from": "S07>3" } }`, naming another entry's `scene`, `from` or `line` as a `scenePlayed` cue does): the entry plays on its own cue, after its `afterSeconds`, but never before the named entry has played, as `scenePlayed` counts it (its last Transmission ended, or its Cinematic or trigger scene handed back). It plays from a trigger of its own, "Script Scene <n> [<part or line>] On <cue> Behind Scene <m> [<part or line>]", which waits for the named entry. Its cue runs that trigger in the entry's place: waiting for it if the named entry has already played (or plays earlier on the same cue), so it plays there as any entry would, in a Beat's Lines trigger too; else without waiting, so nothing else on its cue (a Beat's pings, the entries and lines after it) waits with it, and it plays behind the named entry once that has played, queued as any Transmissions are. It plays once, however often its cue fires. With `afterSeconds`, its delayed trigger ("Script ... After <cue> <n>s Behind Scene <m> ...") waits the delay, then for the named entry. A Cinematic or trigger scene may be either side. An entry with an `after` plays apart from the run of scenes back to back on its cue, and ends that run: the scene before it hands back rather than on, none hands on to it, and it hands on to none. A Beat's trigger doesn't play it as part of the run its pings wait for. `check_workspace` reports an `after` on a scene, part or line no cue entry plays, one naming a part and a line, or a stage direction of another scene, and a cycle through `after`s and the waits above together (an entry after one that waits on it having played, or after itself; an entry plays once its cue can fire and the entry it plays after can play). The compile refuses an `after` on a victory outro's entry, which plays at once on its cue, or naming a victory outro or a scene only a victory or defeat condition's cues play. An `after` alone doesn't drop an entry that has been overtaken: it plays late rather than never. For a message that no longer makes sense once overtaken, the earlier entry takes `skipIfLate: true` (`{ "scene": 7, "from": "S07>3", "cue": { "type": "scenePlayed", "scene": 7, "from": "S07>2" }, "afterSeconds": 97, "skipIfLate": true }`, with Message 4 `after` it): it is dropped the moment an entry after it, directly or down a chain of `after`s, reaches its cue (after that entry's `afterSeconds`) before it has begun, whether it is still counting down its own `afterSeconds`, waiting on its own `after` or queued behind another transmission, and it never plays then. One that has begun plays to its end, and the later entry plays behind it. Dropped, it counts as played, once the entry it is itself `after` (if any) has played, so the chain keeps its order: the entries after it go on, its `scenePlayed` cues fire (their `afterSeconds` counted from then) and the Beats that start on it (`scenePlays`) start. It compiles to "Script Scene <n> [<part or line>] Dropped", which the later entry runs without waiting once it has settled the entry unplayed, on its own thread, as it reaches its cue; the entry settles itself as it begins, at its turn, and plays nothing if it has been dropped, nor queues once dropped. Whichever comes first settles it, once. A cue that fires again doesn't play it again. Whether a message takes it is the author's call. `check_workspace` refuses a `skipIfLate` that never applies (no entry is `after` it, directly or down a chain, or every such entry is cued only once it has played, on a `scenePlayed` of it or a Beat only it starts, or is listed after it, undelayed, on its own cue, which plays it first), one that always applies, so the entry never plays (an entry after it, undelayed, on its own cue and listed before it, or the entry itself delayed there), one on a scene that plays as a Cinematic or trigger scene (it drops Transmissions), and one on a scene, part or line more than one cue entry plays. A Beat may start on a scene, or part or line of one, playing (`"startsWhen": [{ "type": "scenePlays", "scene": 8 }]`, with `from` or `line` as `scenePlayed` names them): for a Beat that is a scene, such as a call the Beat's objective hangs off. It starts the first time a cue entry of that scene and part or line plays it, after the entry's `afterSeconds`, as its Cinematic or trigger scene starts or, for Transmissions, once they have their turn and before the first line, so the Beat's reveals, Mechanic actions and `beatStarts` scenes come with the call, and its scenes of Transmissions queue behind the call's lines. Started by a Cinematic or trigger scene, the Beat starts as the scene does (its trigger, and every earlier Beat's, turned off), and what it starts waits for the scene to hand back: its explores and pings, its Mechanic actions (so a clock one starts isn't running under the scene) and the scenes cued on its start, which then don't play over the scene. The run of scenes holds "staged playing" (`script_staged_playing`) from its start until its last scene hands back, and the Beat's trigger waits on it. A Beat whose own `beatStarts` scenes start a later Beat this way still pings its reveals after them. The trigger that plays the scene runs "Beat - <title>" without waiting, only while it is still on, as Beats only move forward; a Beat with other starts too starts on whichever comes first. `check_workspace` reports a `scenePlays` on a scene, part or line no cue entry plays, one naming a part and a line, or a stage direction of another scene, and a cycle through it: a Beat starting on a scene that only its own start (`beatStarts`), or a scene waiting on that, plays. A script scene's Transmissions, whole, in part or one line, wait for another cue's script scene to finish all its lines, then for any transmission still playing, so one cue's lines don't cut into another's. A trigger scene doesn't wait for them: it starts the moment its cue fires, since it may frame a moment in play, and cuts off the in-play line playing. No in-play line starts while it plays, or while its lines after the handback (`handback.linesFrom`) play. Then the cut line plays again from its start, followed by the rest of its cue's lines (ADR 0013). Any other `##` heading before the first scene, such as a `## Format` note, ends the header fields, and what follows it is ignored until the first scene. Don't put other `##` headings after the first scene: the lines under them are read as part of the scene above.

Inside a scene:

- **Stage directions** start with `>`. They aren't spoken.
- **Dialogue lines** are `**SPEAKER**: text`, or `` **SPEAKER** `id`: text `` with the line's own id in backticks. The line starts with the `**`, and the colon follows the closing `**` or the id directly: `**RAYNOR** : text` isn't dialogue. Every such line in a scene is dialogue, numbered from 1 in the order it appears in the scene; stage directions aren't counted.
- **Delivery directions** say how a line is spoken. They sit in italics and brackets just before the colon: `` **SPEAKER** `id` *(slowly)*: text ``, or `**SPEAKER** *(slowly)*: text`. They aren't spoken or shown. A line with a speaker and an id that can't be read as dialogue is an error, not ignored, so a line in a shape the parser doesn't know can't drop out of the map unseen.
- Anything else, such as blank lines, is ignored.

The speaker is matched to the characters the Campaign Mod's Blueprint declares ([characters.md](./reference/characters.md)) ignoring case and extra spaces, so `**Matt  Horner**` is the character `MATT HORNER` (but `MATTHORNER` isn't). A speaker with no character shows its name title-cased without spaces (`VAN DER BERG` shows as `VanDerBerg`). A speaker the Blueprint's `speakerAnchors` places on the map speaks from that unit, and in a trigger scene, a speaker its `speakers` gives a staged unit speaks from that unit instead; any other speaker's Transmission shows its character's unit type or portrait model, or nothing when it has no character. Once the Campaign Pack names a Campaign Mod, every speaker needs a character, and one without fails the compile and `check_workspace`.

## Emotion tags

`[Mood N]text[/Mood]` gives the wrapped words a mood at intensity `N`, from 0 to 100. Mood is one of `Angry`, `Sad`, `Happy`, `Serious`, `Surprise` or `Fear`. Text outside a tag has no mood. A tag with any other mood is kept as plain text. The tags are removed from the subtitle.

## Emphasis

`*word*`, Markdown italics, emphasizes the words between the asterisks: the subtitle and the Transmission's text show them in the game's italics (`<i>word</i>`), and the placeholder voice speaks them plainly. Lines are matched (for `refresh-screenplay`) by their text without the asterisks, so adding or removing emphasis doesn't count as a change of text there. A lone asterisk, or one with a space inside it, is kept as it is.

## Names in the map

The Screenplay gives no names to the compiled map itself. The Campaign Pack's naming template names the conversation, each line, its sound (and voice file) and each speaker's CCharacter (a speaker's character gives its own id instead), and may read the title, the header fields and each line's backticked id to do it. Any hook the template leaves out, or every hook when there is no template, falls back to core's default: the Mission id, scene and line. A Blueprint's `screenplay.script.conversationId` names the conversation in place of the template: an imported map's own id, which Import writes, so the Screenplay is the conversation its Kept cutscenes and triggers already play.

| Name | Core default | For Mission `outpost`, scene 1, line 2 |
|---|---|---|
| Conversation | the Mission id | `outpost` |
| Line | `Line<scene>-<line>` | `Line1-2` |
| Sound and voice file | `<mission>-<scene>-<line>` | `outpost-1-2` (`outpost-1-2.ogg`) |
| CSound `Line` | the line id without `Line` | `1-2` |
| Character | the speaker's name | `MattHorner` |

Under core's default, a line's backticked id is ignored. A cut renumbers the later lines in its scene, and their voice files with them. See `packages/core/src/script/name-script.ts` and the `NamingTemplate` type in `packages/core/src/plugins/plugin-api.ts`.

## Voice files

Each line's voice file is in the Blueprint's `screenplay.script.audioDir` (`audio` beside the Blueprint by default), named by its sound: `<sound>.ogg` or `<sound>.wav`. A compile writes a placeholder for each line that has neither, and `npm run tts` (or the `speak_placeholder_voices` tool) speaks them through the machine's Host Adapter. Placeholders are in the Mission's voice format, `screenplay.script.voiceFormat`: `"ogg"` by default, or `"wav"`. An .ogg placeholder is spoken as a WAV, trimmed to its speech, then encoded to Ogg Vorbis with ffmpeg (`brew install ffmpeg` on a Mac, `winget install BtbN.FFmpeg.GPL.9.0` on Windows). `manifest.json` in the folder records each placeholder's hash, so a file it didn't write is a recording, which no tool replaces. A recording goes in as either format, beside or over its placeholder.

In the Map Package every voice file is in the voice format, at `Assets/Sounds/Conversations/<sound>.<format>`, and each line's CSound plays it. For `"ogg"`, a .wav (a recording, or a placeholder from before the default changed) is encoded with ffmpeg as it goes in, and an .ogg is copied as it is. Encoding is deterministic and cached by the WAV's hash (`<cacheDir>/derived/` in the machine config, else the system's temporary folder), so a repeat compile writes the same bytes and leaves the compile record as it was. For `"wav"`, each file must be a .wav, and is copied.

When a line has both an .ogg and a .wav, its recording voices it over its placeholder: the compile, the Cinematic and trigger-scene timing, `npm run check` and refresh-screenplay all use that one, and `npm run tts` deletes the placeholder the recording replaces. Two recordings, or a file an old manifest records without its hash beside another, are settled by the voice format, and the compile warns about two recordings. On an `"ogg"` Mission, `npm run tts` also encodes each up-to-date .wav placeholder to .ogg in place, without speaking it again. See `packages/core/src/host/voice-files.ts`.

## An imported map's own conversation

An imported map (a Mission with Kept terrain) keeps its own conversation, the one `screenplay.script.conversationId` names: the compile writes none of the Screenplay's lines over it, and says so. To compile the Screenplay over it, convert it once:

```sh
npm run convert-screenplay -- missions/<id>/blueprint.json                    # lists what differs
npm run convert-screenplay -- missions/<id>/blueprint.json --accept "<reason>" # and accepts it
npm run compile-map -- missions/<id>/blueprint.json
```

The MCP `convert_screenplay` tool does the same given the Mission (`mission`, and `accept` for the reason), returning what it lists under `mission` in its structured output.

The conversion pulls the Screenplay and pairs its lines with the conversation's by line id, which the naming template gives. It records what the lines keep in `screenplay.script.conversion`: each imported Sound (`importedSounds`, by line id), and the group names, facial animations and overlap the Kept lines had. A line keeps its imported Sound only while its words are the recording's. Words are compared without mood tags, emphasis, punctuation, spacing or case, so `Lefty?Looks` and `Lefty? Looks` are the same words. A line whose words changed plays the naming template's Sound instead, and so does an added line, each with a placeholder voice until it's recorded. The old recording of other words never plays.

It lists every difference: the lines whose words changed, those added and dropped, the speakers changed, the Kept cutscenes that still play a dropped line, and those that link a changed line's old recording. It also lists each part the first compile writes other than as the Editor has it: the CConversation, a CSound whose speaker changed, a string whose text changed. That compile runs under the Equivalence Check, as a mod's conversion does, so each of those parts must be named in the Blueprint's `acceptedDifferences` as `{ "item", "reason" }`, or it refuses and writes nothing. `--accept <reason>` names them all with the author's reason. The conversion may run again (after an edit at the Source, say) until the first compile. After that the conversation is Compiled Content, and each compile rewrites it with no check. `importedSounds` is then fixed: rewriting a line's words at the Source no longer changes which recording it plays. Once a line's words no longer fit its recording, take the line out of `importedSounds` (by hand, or ask the assistant to). It then plays the naming template's Sound with a placeholder, and the next compile removes the old recording, unless a Kept trigger still names it.

The compile writes the CConversation into the package's ConversationData.xml and a CSound per line into SoundData.xml, each by entry, and the strings into ConversationStrings.txt by key, so the package's other entries, such as its music, stay as they are. An imported Sound's CSound plays its Kept recording from `Assets/Sounds/Conversations/`, and the Mission's Cinematics and trigger scenes are timed by it. A Kept cutscene element that links a changed line's old recording (`soundLink`) is relinked to the line's new Sound. Only that attribute changes, the file stays Kept Content, and the compile lists each relink. Nothing is left behind: each Sound the conversation no longer plays (a dropped line's, or a changed line's old one) is removed with its CSound and its recording, and so is each dropped line's or scene's string. The conversion lists them first, and the compile reports them. A Sound a Kept trigger names is kept, compile after compile, and the compile says so. The compile's own triggers don't count, since they're rebuilt from the Screenplay. A Kept cutscene that still plays a dropped line fails `check`, which names the cutscene and the line: take the line out in the Cutscene Editor, or put it back at the Source.

## Where the file comes from

A Workspace whose Campaign Pack has no Screenplay Source keeps its Screenplays as files: the author writes the Markdown in the Workspace and edits it in place, and the compiler reads it as it is.

A Campaign Pack can contribute a Screenplay Source (`contributions.screenplaySource` in its manifest, `screenplaySource` in its code, typed `ScreenplaySource` in `packages/core/src/plugins/plugin-api.ts`). Then the file is a pulled copy, and the Blueprint's `screenplay.script.ref` names what the Source knows the Screenplay by:

- `npm run pull-screenplay -- <blueprint>` asks the Source's `fetch` for the Screenplay and writes it over the file. What it returns must be in this format, with a title and at least one scene, and must be one the naming template can name. It also follows each line a cue plays (a cue entry's `line`) from the copy it replaces, as `refresh-screenplay` does, and refuses a cued line that is gone, or that has another sound ID now (pull with `refresh-screenplay` instead, which moves the cue with it). Otherwise the file is left as it was.
- `npm run edit-screenplay -- <blueprint> <edits.json> [--dry-run]` hands an edits file, in the Source's own format, to the Source's optional `edit` and prints its report. Pull again afterwards. Given a Mod Blueprint, it edits one of the mod's Screenplays, named with `--screenplay <name>` (its `ref`, conversation or source file; optional when the mod declares only one): see [a Campaign Mod's Screenplays](./reference/mod-screenplays.md).
- `npm run refresh-screenplay -- <blueprint> [--map <output-dir>]` is the pull after an edit, and what follows it. It follows each line from the old copy to the new one by speaker and text (mood tags aside), since an edit may renumber them. It moves each of the Blueprint's Cinematics' shots, and each cue's `line` (a script cue entry's and a `scenePlayed` cue's), onto its line's new sound ID and lists every moved, changed and gone line, for prose that names them, such as cutscene plans. It then writes placeholder voices as `npm run tts` does, compiles the map when given `--map`, and checks the Mission. It exits 1 when a shot's line is gone or the check finds an error. (Given a Mod Blueprint it pulls each of the mod's Screenplays, lists the lines that moved, changed or went, and checks the mod; see [a Campaign Mod's Screenplays](./reference/mod-screenplays.md).) A line alone between the same two unchanged neighbours before and after counts as changed in text or speaker. Any other line that can't be followed is gone.

Never edit a pulled copy by hand: the next pull overwrites it. Change the Screenplay at its Source and pull again, with `edit-screenplay` where the Source supports edits.
