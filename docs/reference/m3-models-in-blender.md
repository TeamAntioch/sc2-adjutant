# M3 Models in Blender

How an assistant runs Blender and the m3studio add-on headless from the shell to read a `.m3` model, gets a model into an Asset Mod or onto a map as a doodad, watches a model's animations to draft a Model Guide, and draws the cinematic sets.

## Tools

- **Blender 4.5 LTS, not 5.** m3studio (GPL-2.0; upstream Solstice245/m3studio at `bef1b08`, and the fork below, which is built on it) calls `Action.fcurves`, which Blender 5.0 removed. On 5.x the import fails in `m3_animations.set_default_value` with `'Action' object has no attribute 'fcurves'`. Homebrew's `blender` cask is 5.x, so install 4.5 beside it from `download.blender.org/release/Blender4.5/` (check it against the `.sha256` file there), for example as `~/Applications/Blender4.5.app`, and run `~/Applications/Blender4.5.app/Contents/MacOS/Blender`.
- **m3studio from TeamAntioch's fork.** Use [TeamAntioch/m3studio](https://github.com/TeamAntioch/m3studio), branch `adrianbw-m3studio-fixes`. It is upstream `bef1b08` plus five export fixes, one branch each. Upstream `bef1b08` has these defects (2026-11-20), and each upstream workaround follows its repro:
  1. **Influence sort** (`adrianbw-influence-sort`). The exporter sorts a vertex's bone influences in ascending order and keeps the first four, so a vertex with more than 4 loses its strongest bone. Repro: weight one vertex 0.6 / 0.1 / 0.1 / 0.1 / 0.1 to five bones, export and re-import; the 0.6 bone is gone. On upstream, run Limit Total 4 and Normalize All on the vertex groups before export.
  2. **Cloth tie sort** (`adrianbw-cloth-tie-sort`). `create_physics_cloths` sorts simulation vertices by (distance, vertex), and two at the same distance raise `TypeError: '<' not supported between instances of 'BMVert' and 'BMVert'`. Repro: round-trip a model whose cloth has two simulation vertices at the same distance. On upstream, clear `arm.m3_cloths` first, which drops the cloth.
  3. **Turret parts** (`adrianbw-turret-parts`). LookAt turret parts are written with zero up quaternions, every group id reset to 1, and a bone shared by two groups kept in only one. Repro: round-trip a hero model with LookAt turrets (a Campaign Asset Mod's) and compare its `PATU`/`TRGD` records; 4 of 15 parts are lost.
  4. **Empty material layer** (`adrianbw-empty-material-layers`). With `cull_material_layers=False`, an empty layer slot raises `UnboundLocalError` for `m3_layer`. Repro: export any standard material with an unused layer slot, with that option off.
  5. **Turret main flag** (`adrianbw-turret-main-flag`). A turret group with no main part is exported with every part marked main. Repro: round-trip a model with a turret group that has no main part.

  The fork's commits carry the details.
- **m3studio, from a clone of the fork.** It doesn't need installing as an add-on: put the clone's parent folder on `sys.path` and call `m3studio.register()`. The older m3addon is obsolete and stops at Blender 3.6.

## Running headless

`blender --background --factory-startup [file.blend] --python boot.py --python <task>.py -- <args>` runs a script with no window. Two things m3studio expects from its interface have to be supplied.

**No GPU.** `bl_graphics_draw` builds drawing shaders when the add-on is imported, and `gpu.shader.from_builtin` raises `SystemError` in background mode. Nothing is drawn headless, so let that call return nothing:

```python
# boot.py: load m3studio in background mode
import sys, gpu
sys.path.insert(0, "<folder holding the m3studio clone>")
_from_builtin = gpu.shader.from_builtin
def _safe(*args, **kwargs):
    try: return _from_builtin(*args, **kwargs)
    except SystemError: return None
gpu.shader.from_builtin = _safe
import m3studio; m3studio.register()
```

**No operator.** `io_m3_import.m3_import(path, bl_op=…)` and `io_m3_export.m3_export(armature, path, bl_op=…)` read their options from the File menu operator. Pass a stand-in:

```python
from types import SimpleNamespace
from m3studio import io_m3_import, io_m3_export
report = lambda kind, message: print("REPORT", kind, message)
io_m3_import.m3_import(src, bl_op=SimpleNamespace(report=report))
armature = next(o for o in bpy.data.objects if o.type == "ARMATURE")
io_m3_export.m3_export(armature, dst, bl_op=SimpleNamespace(
    output_anims=True, section_reuse_mode="EXPLICIT", face_storage_mode="STANDARD", vert_format_lookup="STANDARD",
    cull_unused_bones=False, cull_material_layers=False, use_only_max_bounds=False, report=report))
```

`cull_unused_bones=False` keeps every bone, and `cull_material_layers=False` writes material layers as Blizzard does. Import logs `invalid operator call 'M3_OT_material_remove'` once per material: its clean-up of unused materials needs the interface. It's harmless, since the exporter leaves out materials nothing references anyway. Save a `.blend` after importing and work from that.

## How m3studio holds a model

Everything is on the armature object:

- **Animation groups** (`armature.m3_animation_groups`) are the model's sequences, each with `frame_start`, `frame_end` (30 fps) and its flags. Each group lists `animations`, and each of those names an `action`, the Blender action holding that sequence's keys. A group's name is made of words from the dictionary in `bl_enum.py` (`Walk`, `Left`, `Right` and so on), and is the name a cutscene or an `AnimPlay` picks.
- **Defaults** of every animatable property (a particle system's speed, lifespan, size and colours, a material layer's values) are keys in one more action, `armature.m3_animations_default` (`<armature>_DEFAULTS`). The exporter takes defaults from there. Changing a value means setting both the property and its key in that action.
- **Animated values** (for example a particle system's `emit_rate` switched on in Walk) are F-curves in that group's action, by path, such as `m3_particlesystems[6].emit_rate`.
- **New items** go through `m3studio.shared.m3_item_add(collection, name)`, which gives each its handle and animation ids. Adding to a collection invalidates Python references to its items, so look items up again afterwards.
- **Blender 4.5's layered actions:** to pose the armature with an action for a render, set `armature.animation_data.action` and also `action_slot` to the action's first slot.

## Into an Asset Mod

The game loads a Workspace's mods through links in `/Applications/StarCraft II/Mods/` to `mods/<id>/<Name>.SC2Mod`, so a new or changed model goes into the Asset Mod's package, never into another copy of the mod:

1. Put the file in the mod's folder (`mods/<id>/art/<Name>.m3`). Git LFS tracks it there by the Workspace's `.gitattributes`.
2. Declare it in the Mod Blueprint's `assets` as a Workspace file: `{ "path": "Base.SC2Assets/Assets/Models/<Name>/<Name>.m3", "source": { "file": "art/<Name>.m3", "sha256": "…" } }` ([asset-sources.md](./asset-sources.md)). Declare each texture it names the same way, at the path the model names it by (`Base.SC2Assets/Assets/Textures/<Name>_Diff.dds`).
3. Run `compile-mod`. Replacing a Kept model stops the compile at the Equivalence Check (`the bytes differ`), so name the change in `acceptedDifferences`: `{ "item": "file:Base.SC2Assets/Assets/Models/<Name>/<Name>.m3", "reason": "…" }`. Update the SHA-256 whenever the file changes.

A new model that maps should place as a doodad also needs a `CModel` and a `CActorDoodad` of one id. A `CModel` alone isn't a doodad: the Editor logs `Invalid placed doodad '<id>' … A placeholder model will be used`, and its palette leaves the model out. The Campaign Mod's Blueprint declares both in `doodads` (`packages/core/src/domain/custom-doodad.ts`), and its `compile-mod` writes them after checking that the model and every texture it names are in the Workspace mods it loads, and that the id isn't a game doodad's or unit's. The `custom-doodads` skill walks through it.

## Watching a model's animations

To draft a Model Guide ([model-guides.md](./model-guides.md)), pose the model in each animation and render a few frames of each, from the front and three-quarters, into a contact sheet. The method was worked out on a Campaign's characters for the first guides (2026-11-03, #392). Five things decide whether the render shows what the game plays:

- **The model's own file, and its RequiredAnims.** A game model is exported from the game by the Host Adapter's `model.export`, the way `npm run model-anims` records one, with its RequiredAnims merged in. A mod's model is in its Asset Mod, and many keep every animation in `.m3a` files that its CModel's `RequiredAnims` names (one Campaign's hero model has none of its own). Load each one onto the imported armature with `io_m3_import.m3_import(path, ob=armature, bl_op=…)`.
- **`--factory-startup` leaves Blender's default cube, camera and light in the scene.** Remove every object before importing, or the 2 m cube hides the model.
- **An animation group can hold several animations.** A Stand can be a full-body animation plus a `LowerBody` one, each its own action. Apply every action in `group.animations`, the one with the most F-curves first, setting each with `scene.frame_set` before the next. With only the first, a hero's plain Stand rendered in her bind pose with her pistol on the ground.
- **A Talk often keys only the upper body.** The game plays it over the Stand below it, so pose the family's Stand first (`Talk B 01` over `Stand B`, a plain Talk over `Stand`), then the Talk. Start each pose from `armature.m3_animations_default`, and reset the pose bones, so nothing carries over from the last animation.
- **A portrait has backdrop planes.** They're meshes of a few vertices, metres across, and fill the frame. Hide meshes under about 30 vertices before framing.

Particles and material animation don't render, so an animation that differs only by an engine glow (a ship's Stand and Walk) looks the same as its neighbour: judge that in the Editor. Face animations (`NeutralEyes`, `Blink`) aren't worth rendering at body scale.

A family is every word of a name after the first, numbered variants aside (`animFamily`), so the guide's families follow that split, not the name's look: `Ride` and `Ride 01` are in the plain family `""`, and `Portrait Talk` is in `Talk`. List such an animation under `anims` instead.

## Authoring animations

Conventions for a new or edited clip (a new unit's, an edited model's), taken from another project's notes and checked where it could be. Each line says how far it is verified.

- **A looping clip ends on its first frame's pose. Verified for Stand and Fidget; walks only nearly.** Read from the stock Zealot, Marine and Roach (2026-11-24; `cascx` out of a game install, m3studio's import in Blender 4.5, each clip's F-curves sampled at its first and last frame, quaternions compared up to sign). Every plain Stand, `Stand 01`/`Stand 03` and Fidget (the Zealot's `Fidget 02` too) closed to within 0.01 on every bone channel, most to exactly 0; the Dance and Victory Stands did not all. The Walks did not: in each, a handful of leg bones sit 0.1 to 0.17 off in a quaternion component at the last frame (Roach `Walk` 9 of 28 channels, Zealot 2 of 46, Marine 6 of 29). Match the first frame exactly in your own loops anyway; why the stock walks don't is unexplained.
- **A one-shot starts and ends on Stand. Only partly true.** Stock Fidgets (Zealot, Roach) and the Roach's `Attack` start and end on the Stand pose. The Zealot's and Marine's `Attack` start and end on each other but in a combat stance well away from Stand (0.4 to 0.5 in a quaternion component on 16 to 19 channels). So make a one-shot start and end on the same pose, and make that pose Stand when the clip is played over or between Stands (Attack, Fidget, Taunt, Birth); a unit with a weapon stance may use that stance instead. Burrow and the like end elsewhere on purpose. A clip's flags say whether it plays once: Attack on the Zealot is once, on the Roach and Marine it is flagged to loop, so read `looping` from the model (`readM3Sequences`) and don't assume it.
- **Key every animated bone at both ends of every clip. Verified.** In every clip sampled (Stand, Walk, Attack and Fidget groups of the same three models), every translation, rotation and scale channel has a key on the clip's first frame and one on or just past its last. Without them the bone takes its value from the clip before or after, and it drifts in when the clips blend.
- **Animate a walk in place, and set its move speed to match the feet. Read, not guessed.** The model's own record of a walk's speed is in its `SEQS` entry (`moveSpeed`, from `readM3Sequences`; `npm run model-anims` records it for a game model). The Roach's `Walk` and `Walk 01` both record 225, which is its unit data's `Speed` 2.25 times 100 (the game data mirror's `UnitData.xml`), so a cutscene's `movespeed` for it is that number and it travels 2.25 cells a second ([editor-and-engine.md](./editor-and-engine.md#cutscene-walk-animations-need-their-built-in-move-speed) measures the scale). The Zealot's and Marine's Walks record 225 too. Set a new walk's `moveSpeed` to the unit's speed times 100 and the stride length to match, so the feet don't slide; a model whose anim records 0 doesn't move on a walk element at all, and a Workspace can record its own models' animations ([ADR-0026](../adr/0026-workspace-recorded-model-animations.md)).
- **No motion shorter than 2 frames.** A rule of thumb from the other project's notes: a move that short reads as a glitch in game. Unverified here.
- **At most 4 bones per vertex.** It is the m3 limit. A vertex with more is cut to four by the exporter, which sorts a vertex's influences ascending and keeps the first four, so the strongest is the one lost (the influence sort in Tools; the fork fixes it). On upstream, run Limit Total 4 and Normalize All before export so the choice is yours.

## Previewing in the Editor

A Mission Blueprint's `doodads` take a model file from the Mission's folder, so a preview map needs no hand edits:

1. Put the edited `.m3` in the Mission's folder (`art/<Name>.m3`), with each texture it names that the compile wouldn't otherwise find. The compile finds a texture in the Mission's own files, in its Map Package as Kept Content, and in the Workspace mods the Mission depends on: the Campaign Mod (and the Asset Mods it depends on) only when the Blueprint's `dependencies` name it.
2. Declare it in the Blueprint's `doodads` under a new id and a new storage path: `{ "id": "<Name>Preview", "model": "Assets/Models/<Name>Preview/<Name>.m3", "source": "art/<Name>.m3", "textures": { "<the path the model names>": "art/<file>" } }`. The original's own path would replace that model for everything in the map that draws it, and the compile warns about it. It refuses an id that is a game doodad's or unit's.
3. Place it with a doodad Anchor (`doodadType` the id), and compile the Mission.
   - **A Mission with Kept terrain** compiles only in place, into its own Map Package. Preview there, then take the declaration and the Anchor out and compile again: the compile record owns the preview's files and entries, so that compile removes them.
   - **A generated Mission** can compile a throwaway copy into its git-ignored `output/`. That copy isn't the Mission's Map Package, so ship every texture the model names in `textures`, Kept ones too.

   Open the compiled map with the Editor closed, or at least not open on that map, which can crash it.
4. To play a particular animation, give the actor its own events in `fields.actor`: `"On": [{ "index": 0, "removed": 1 }, { "index": 1, "removed": 1 }, { "Terms": "ActorCreation", "Send": "AnimPlay Preview Walk,Left PlayForever" }]`. The animation name's words go comma-separated ([editor-and-engine.md](./editor-and-engine.md#any-model-can-be-a-doodad)).

A doodad made from a game model with no file of its own (a unit or weapon model) is a Composite's `actors` entry instead.

## Drawing a cinematic set in neutral light

`npm run render-set-views` draws the cinematic sets ([the set catalog](../../packages/core/data/cinematic-sets/README.md)) in Blender, as a reference for finding the set that fits a cutscene (2026-11-17). Per set it writes a plan from directly above with the roof cut away, an overview from the south-east, a frame from each camera the set's Cutscene Editor file has, and an `index.html` with each set's size in cells and who is staged in it. The game's own captures (`capture-sets`) stay the look of a set as lit.

- **Models as glTF.** The Host Adapter's `model.exportGltf` (WhiteoutFlakes' `--export-gltf`) writes a game model with its textures embedded, and Blender's own glTF importer reads it: no m3studio and no Blender 4.5 pin, so the `blender` on the path (5.x) works. Models are kept in `<cacheDir>/set-views/models`, one file per model, and are large (10-40 MB each).
- **What the catalogue records.** Each piece's `rotation` and `scale` and each camera's `eyeHeight` (the eye's z, from `heightOffset` and pitch, or a target camera's `eyePositionZ`) are in the catalogue because a set repeats a piece around a ring (Bar's railing is six copies of one model at one origin, turned 60° apart) and a camera's lens is not at its target's height. A piece with no turn or scale leaves the field out. An actor names its model by a model entry's id (`modelLink`) or by the model's file (`modelPath`); Blizzard's later files build a room from parts named by file (2,427 actors in 71 of the 382 files: Nova's wrangler room, the Zerg story sets, the Aiur debriefs). The catalogue reads both: a piece named by file has that file as `modelPath` and the file's name as `model`, is exported for drawing from the file, and `import_set` and the Set's cutscene carry the file through. A character named by file is not a mark, since a cast member is made from a model entry.
- **Neutral light.** Eevee, with every surface lit evenly from its own textures (`evenly_lit` in `blender/render-set.py`): diffuse × 3 plus the specular map, plus the emissive, darkened to 0.55 where the normal (with its normal map) faces away from a fixed light, for form. No lamp or world light is used, because a set is a closed room: world light and a sun don't reach inside, so a brighter world left the walls dark and blew out only what faced the opening. The gains stand in for the game's lights, which run well past 1 over dark diffuse maps; they were set by eye against the in-game captures of the Bar. The importer's backface culling is turned off (a hull seen from outside lost its walls with it), and an untextured white material becomes a dark grey. The script shoots the camera frames first, with the set whole, then cuts every mesh at `cutZ` (3 over the median mark, else 1.5 over the median camera lens) for the plan and overview. Workbench is no use here: it draws one texture per material, and picks the emissive map as readily as the diffuse.
- **Composite materials.** A composite material (`CMP_`) draws other materials of the model in turn: a base, then details over it by the details' alpha and the section's weight. WhiteoutFlakes' glTF export writes one with nothing in it (its log says "an M3 CMP_ material blends 2 other materials by weight ... no common projection"), and writes the sections it names with their textures but on no triangle. Story sets lean on them: a third of the triangles in the Nova bridge, Hyperion cantina and Bar models, and nearly all of the Nova bridge's shell, which is why sets drew blank where units and doodads, on standard materials, export whole. `readM3Composites` (`catalog/m3-footprint.ts`) reads each composite's sections from the model file (`model.export`), kept as `<id>.composites.json` beside the `.glb`, and `render-set.py` rebuilds the material in Blender: the first section's material with each later section's colour mixed over it. Blender's importer makes a material only when a mesh uses it, so the script adds a marker object per material it needs to a copy of the `.glb` and removes it after the import. A section that isn't a standard material is left out (the Bar's floor is its floor material under a mirror-reflection material), and the rest are drawn. Only the colour of the later sections is layered, not their normal, metal or emissive maps.
- **Specular maps.** The game's metals are a dark diffuse under a bright specular map (the Bar's floor: diffuse about 0.2, specular near white, specular multiplier 2), and glTF's metal-roughness materials have no specular colour, so the export drops the layer ("a 'specular' layer has no place in the target kind") and a drawing from the glTF alone shows textured metal near black with its detail barely visible. That, not missing textures, is why sets looked untextured where the game shows weathered grey panels. `readM3Speculars` reads each standard material's specular map and multiplier from the model file; `model.export` with `textures` writes the texture files, and the specular maps are kept in `<cacheDir>/set-views/models/textures`. `render-set.py` adds the specular map to the diffuse, on the diffuse's UVs (see Neutral light). `<id>.materials.json` beside each `.glb` holds a model's composites and specular maps, with the version of the reading that wrote it (`MATERIALS_VERSION` in `capture/set-views.ts`): a file from an older reading is read again (kept as it is on a host without `model.export`, which can't read the model file), and a set whose pieces' materials change is drawn again. Version 2 (2026-11-21) reads the specular where each MAT_ version keeps it; before, models on MAT_ versions below 20 (the Photon Cannon, the Pylon) were drawn with their emissive or another layer as the specular.
- **Glows and fog.** A set's model carries sheets that aren't surfaces: fog volumes (`volume` materials), heat haze (`displacement`), shadow sheets (the `mod` blend modes) and glows and light shafts (the `add` blend modes). glTF has no word for any of them, so they import as opaque sheets, often a flat cyan or white that fills the frame (the Hyperion med lab's fog did). `<id>.materials.json` lists them from the model file (`readM3Footprint`'s material kinds): the script draws an additive one as light over a clear sheet, from its diffuse and emissive pictures, and the rest not at all.
- **Pieces at the origin, and hidden pieces.** An actor with no `position` in the Cutscene Editor file sits at the origin, as a set's one-piece room often does (`SMX1EggRoomSet`): the set catalogue reads it there. A piece the file turns off (`enabled="0"` or `visible="0"`) is marked `hidden` in the catalogue and isn't drawn.
- **More shots of one set.** `npm run set-shots -- <set id>` draws more pictures of a set already drawn, for whoever is describing it: `--compass <height>` (north, east, south and west from a standing point), `--orbit <bearing>,<pitch>` and `--plan` (with `--cut` to take the roof off), and `--shot <name>=<eye>:<target>[:<fov>]`. `--only` and `--without` choose pieces by model name, for a file that stacks two rooms on one origin (one Campaign's Cantina file holds the Hyperion cantina and the Nova bridge). `--list` measures the pieces chosen and draws nothing: models, bounds, floor height and cameras. The floor is a guess (the level holding the most upward-facing surface with a cell of clear air over it, under a roof where the set has one), since a set's lowest point is often a shell far below the deck; the result's `levels` lists the candidates and `--floor <z>` sets it, which is what `--compass` heights are measured from. The guess is wrong for a set with a flat cap over a lumpy floor (the Zerg egg room). A request takes a few seconds. `--cut` with no height cuts just under the ceiling over that floor: the lowest level, a cell or more over the floor, whose downward-facing surface is at least 0.3 of the floor's own area (the result's `ceiling`, with the levels holding the most such surface in `ceilings`). An open set, or one with only a gantry or a ledge overhead, has no ceiling, and the cut is then the set's own. A room's ceiling is often well under its model's top (Rouche's office has its ceiling at 9.75 inside walls that rise to 10.2), and a cut above it leaves it on.

- **Card pictures.** A set look names the pictures its card shows (`card/N.jpg` in the set's views folder), each with a `from` record: one of the set's views (`view`, `camera`), an in-game capture (`capture`, a file name) or a shot with everything it was drawn with (the compass point, orbit or camera, and its `cut`, `floor`, `only`, `without` and `fov` as resolved). `set-shots` prints the record beside each picture it draws. `npm run set-cards -- [<set id>...]` makes the pictures from the records (`capture/set-cards.ts`): copies for views and captures, one Blender run for the shots that share their options. It keeps a picture whose record and set drawing haven't changed (`card/cards.json`, which holds a hash of the set's `spec.json` and `views.json` with each record, so a set drawn again has its cards made again), and lists each one it can't make with why, taking away a picture it made earlier from another record; a `camera` record takes a `frame` (the NN of `cam-NN.jpg`) for a set with two cameras of one name; an in-game capture is made only where the machine has the captures. The records of the first 97 looks were recovered from the describers' own commands (2026-11-18); a compass shot from before heights were measured from the floor has the set's lowest point as its `floor`.

- **Open: a set the game draws differently.** The Valerian flagship corridors (`valerianflagshipcorridors`, from `SMX3_Cutscene_MP01_030`) draw as two corridors side by side running east-west, where the game shows one running north-south through the door: the file gives each corridor piece a 90° turn about z and a scale of 2, and the game draws them as if the turn were not there. The model file agrees with its glTF (the corridor runs along −y from its origin, its bones unturned, no transform keys in its Stand), and the door, which has no turn, draws where the game puts it. A render from the in-game capture's own eye (−0.46, −0.74, 0.57, looking north) shows a corridor's outer wall where the game shows the tunnel. The cause isn't found (#761).
- **Set looks.** `packages/core/data/cinematic-sets/looks.json` holds a written look for every drawn set of Blizzard's, and a Workspace's `cinematic-sets/looks.json` for its own (what the place is, size, features, facets, what it could stand in for, the model pattern for each room of a stacked file, and the problems with its pictures), each by an agent following `docs/agents/describing-sets.md`. The pictures a describer chose for the set's card are in the set's views folder under `card/`. A correction is an edit to the file that holds it.
- **Drawn again only when needed.** A set whose `spec.json` hasn't changed and whose `views.json` carries the script's `VERSION` is kept. Raise `VERSION` in `render-set.py` and `VIEWS_VERSION` in `set-views.ts` together when the drawing changes. Each drawn set keeps a `set.json`, and the index lists every one; a run over every set drops the ones no longer in the catalogue.
- **What it doesn't show.** The game's own lighting, reflections and post effects, so colours are close, not the game's. A material with no texture of its own (a plain colour, glass) is drawn as that colour. Glass, screens' pictures (a render-to-texture screen shows magenta), particles and material animation are missing. A backdrop (skybox, starfield) isn't drawn, and neither is a model with no file of its own (a unit or mod model without `--mod`).
