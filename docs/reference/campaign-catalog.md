# The Campaign Mod as a catalog layer

A Mission uses the tilesets, terrain textures, cliff sets, Lights, units, doodads and models its Workspace's Campaign Mod defines, with the same checks as the game's own ([ADR-0011](../adr/0011-mods-from-mod-blueprints.md)). Core's catalog files in `packages/core/data/` hold only the game's entries. A Campaign's own are read from its mod, so a second Campaign gets the same support without a Plugin and without copying anything into core.

## Which mod

The Campaign Mod is the Workspace mod whose package name its config names (`campaignMod` in `sc2-adjutant.workspace.json`, without `.SC2Mod`), or else the one its Campaign Pack names (`contributions.campaignMod`). A Workspace needs no Plugin for this:

```json
{
  "campaign": { "id": "lantern", "name": "Lantern" },
  "mods": ["lantern-story"],
  "campaignMod": "Lantern-Story"
}
```

When both the config and the Campaign Pack name one, they have to name the same mod, or the Workspace doesn't load.

## What's read

| Entry | Class | Used for |
|---|---|---|
| Tileset | `CTerrain` | `tilesetId`: its blend textures, cliff sets, default Light, skybox, fog and hidden lowest level |
| Terrain texture | `CTerrainTex` | `textures` and `texturePalette` names |
| Cliff set | `CCliff` | `cliffPalette` names |
| Light | `CLight` | `lighting`, transitions and a Cinematic's `light` |
| Unit | `CUnit` | `tech` lists, and whether a unit flies or is a structure |
| Doodad | `CActorDoodad` | doodad Anchors and dressing, with its model's `VariationCount`, its model file and its Editor categories; described and pictured in the mod's doodad index ([mod-doodad-index.md](./mod-doodad-index.md)) |
| Model | `CModel` | a sky model, and the Asset Catalog |

Entries still Kept come from the mod package's catalog files that the game loads: each file directly in `Base.SC2Data/GameData/` named for its catalog (`UnitData.xml`, `TerrainData.xml` …), and any other file once the includes list (`Base.SC2Data/GameData.xml`, which the Blueprint's `includes` write: [mod-includes.md](./mod-includes.md)) names it. Any other XML in GameData is ignored, since the game ignores it too. Entries the Mod Blueprint owns come from its `gameData` sources, its generic `entries` and the entries its purpose-level shapes compile to: a custom doodad in `doodads` is a `CModel` and a `CActorDoodad` of its id (`packages/core/src/mods/custom-doodads.ts`, #606). An owned entry replaces the package's copy outright, since the next `compile-mod` writes it over that copy whole, so a field the Blueprint dropped is gone. An entry the package gives twice takes the later one's fields, field by field, as the game merges catalogs. A field given only by index (`<Attributes index="Structure" …/>`, `<CliffSets index="1" …/>`) replaces just those indices, in place, or drops one with `removed="1"`. Any other field replaces the earlier ones of its name. An entry that sets only some indices of a list lays them over the list it inherits: `<CliffSets index="1" value="X"/>` on a child of a tileset with cliffs `A, B` gives `A, X`.

Each field resolves as the game resolves it: the entry's own value, else the game's entry of the same id, else its parent's. So a mod tileset with `parent="Shakuras"` and only its own `BlendTextures` keeps Shakuras's cliffs, Light and fog. A mod unit flies when its own `Mover` is `Fly`, or when the game's unit of its id or its parent does. A mod entry with a game entry's id overrides it. Template entries (`default="1"`) aren't usable on their own.

A mod Light can be named, but a Mission's `lights` copy only a stock Light (`from`), because only the game's are in `data/light-catalog.json` with their fields.

## Model animations

Cinematics need each model's animations, with their lengths and move speeds. Core records the game's models in `data/model-anims.json`. A Workspace records more, in the same shape, in a file chosen by who owns the model ([ADR-0026](../adr/0026-workspace-recorded-model-animations.md)): a game model's in `model-anims.json` at the Workspace root, a Campaign Mod's own in `mods/<id>/model-anims.json` beside its Blueprint, and a Mission's own (its Map Package's Kept `CModel`s) in `missions/<id>/model-anims.json`, which only that Mission reads. The more specific file wins, per model: core, then the root, then the Campaign Mod, then the Mission. `check` warns about an entry in the wrong owner's file, and notes a root entry that core records too. Record them from the Workspace's folder with `npm run model-anims -- [--mission <id>] <model id>...`, which puts each model in its owner's file. A game model is exported through the Host Adapter's `model.export`, and a package's own model is read from the package. In the sc2-adjutant checkout, `npm run model-anims` writes core's file instead. The MCP tool `record_model_anims` does the same as the Workspace script, and lists the stock models core doesn't record so the session can offer a Missing-Feature Report. A Workspace made before the script existed adds it to its `package.json`'s scripts as `"model-anims": "node node_modules/@team-antioch/sc2-adjutant/dist/cli/record-model-anims.js"`.

What those animations show, for casting, is in each model's Model Guide ([model-guides.md](./model-guides.md)). Core keeps the game's models' guides in `data/model-guide.json`, and a Campaign Mod keeps its own in `mods/<id>/model-guide.json`, beside `model-anims.json`. `catalogModelGuides` merges them entry by entry, and a mod's entry for a model replaces core's whole entry.

## A Mission's own game data

A Map Package can define entries of its own, as an Editor-made map with a custom `CTerrain` does. The game loads a map's data after its mods, so a Mission's catalog is its Workspace's with the Kept catalog files of its own Map Package laid over it (`src/map/mission-catalog.ts`): the same files the game loads, read as a mod package's are. A tileset, texture, unit … the map defines is then the Mission's, as the mod's are. The map's files are merged over the mod's own catalog files, field by field, as the game merges them: a map entry that sets only the `Lighting` of a mod tileset keeps the mod's textures and cliffs.

Only Kept data counts. A catalog file the Mission's compile record lists whole (`file`, `uncommitted`) is the compile's own output (a compiled `TerrainData.xml` overriding a stock tileset's textures, say), and so is an entry it lists (`catalog-entry`) in a Kept file: reading them back would check the Blueprint against what its last compile wrote. Import reads every catalog file of the package it imports, since all of it is Kept. A package with no Kept catalog files leaves the Workspace's catalog as it is.

Making it never fails. A Mission whose package can't be told (two in its folder), or whose compile record or game data doesn't read, gets its Workspace's catalog, and `check-workspace` reports the package, the record or the data where it checks them. The catalog is made once per package and made again only when one of its Kept catalog files, or what the record says the compile owns of them, changes.

## Whose layer a lookup reads

Each catalog lookup is given the catalog it reads: the Workspace's (`workspace.catalog`, read from its Campaign Mod when it loads), a Mission's (`missionCatalogFor`, the Workspace's with its package's Kept game data, or `missionWorkspace`, a view of the Workspace with it), or the game's entries alone. `validateMissionBlueprint` takes the catalog as a required argument, so each caller says which. Nothing is held process-wide. A Mission Blueprint is validated against its Mission's catalog and keeps it, as it keeps its Plugins, so its compile, checks, sync and preview read the same one. Workspaces compiled at once, as MCP tool calls may be, each read their own mod.

## Checks

A Mission's `tilesetId` must be a game tileset, the Campaign Mod's or its own Map Package's. Each `tech` unit, palette texture and cliff set must be known too, and a Light that's neither stock, a Plugin's nor the mod's gets a warning. Without the Campaign Mod (it isn't named, or isn't imported), its entries are unknown and fail those checks.

When the mod's entries can't be read (a generic entries source that isn't JSON, a missing source file), Missions get none of them, and `check-workspace` reports why against the mod.

## The Asset Catalog

The game's entries are in core's catalog files (`data/*-catalog.json`, `data/tileset-*.json`). The MCP `asset_catalog` tool lists what the Campaign Mod defines, each tileset resolved as a compile reads it (textures, cliff sets, Light, sky) and each unit with whether it flies or is a structure. The design skills check names against both.

`search_doodads` (MCP and `npm run search-doodads`) is a Doodad Search's narrowing step: a keyword and facet search over the game's doodads, its terrain objects and the Campaign Mod's doodads. The mod's doodads match on their entries in the mod's doodad index ([mod-doodad-index.md](mod-doodad-index.md)): description, Doodad Uses and sheet, as a game doodad does on core's. One whose description wasn't written for its current model is marked `pending`, and one with no description at all matches by its name and id alone. A game doodad the mod gave a model of its own is the mod's, pending until indexed.

`find_doodads` (MCP only) narrows by meaning instead: it is the Doodad Finder's narrowing and Jev ranking, for one ask at a time. The server serves it only when the `doodad-finder` package, an optional dependency of core, is installed. Its results are `search_doodads`' with Jev's level. See [the Doodad Finder's README](../../packages/doodad-finder/README.md).

`build_doodad_search_page` (MCP and `npm run doodad-search-page -- <slug> [--mission <id>] [--search <file.json>] [--build-sheets]`, or `--folder <folder>`) is a Doodad Search's showing step. It writes the search's `search.json` (its Search Parts, the queries run, the ranked candidates with the agent's notes, and the ones also considered with reasons; the schema is in `src/catalog/doodad-search-page.ts`) and builds `index.html` beside it, a page on the sheets' mid-grey with a section of cards per Search Part. A Mission's search goes in `missions/<id>/output/doodad-search/<slug>/`, which is git-ignored, and a search for no Mission goes in `doodad-search/<slug>/` under the folder `$SC2_RESEARCH_DIR` names. The page links each picture where it is: a sheet by its file URL, a gallery picture by its sc2-mapping-reference URL. It never copies them. The tool reports the candidates whose four renders are on this machine but whose sheet isn't. With `buildSheets` it builds just those, the same JPEGs `npm run catalog-sheets` makes (the sheet builder in `@team-antioch/sc2-asset-catalog`), in `data/catalog-sheets/`, where both tools find them without a catalog entry naming them. In a linked worktree, which has no renders or sheets of its own since both are git-ignored, both tools look for them in the main checkout too, and a sheet built from the main checkout's renders goes in the main checkout's `data/catalog-sheets/`. A sheet is linked by its real path, so a page built in a worktree whose `data/catalog-sheets` links to the main checkout's still finds its sheets once the worktree is gone. `build_doodad_sheets` (MCP and `npm run doodad-search-page -- --sheets-for <id,...>`) builds them by id with no `search.json`, for a shortlist of any length. A candidate may name the `variation` it recommends; its card then shows that variation from the search folder's `renders/` (its `<id>_<variation>.jpg` sheet, else its first render), and each card says which variation its picture shows.

The `doodad-search` skill runs a search from end to end. Two `npm run thumbnails` options serve it. `--out <dir> --sheets` montages each rendered variation's four angles into `<id>_<variation>.jpg` beside the renders, so the top candidates' other variations are judged from one picture each. `<name> --model <file.m3> --out <dir>` renders one model no catalog lists (or a storage path the game holds). A Campaign Mod doodad is pictured by `index-mod-doodads` instead.

### Doodad Uses

A Doodad Use is a record: `{ "use": "<short general phrase>", "variation"?: n, "scale"?: x, "from"?: "<search or source, date>" }`. The phrase never names a Mission or a story. `variation` is the Editor's variation number (0 for 00), and `scale` is the uniform scale that made it work; neither goes in the phrase. Two uses are the same when their phrases match, ignoring case and spacing (`catalog/doodad-uses.js` in `@team-antioch/sc2-asset-catalog`, which publishes the same files).

The published package keeps them outside the generated catalogs, in one file per doodad, each a list of records checked against that schema: `data/doodad-uses/doodads/<doodad id>.json` in `@team-antioch/sc2-asset-catalog`, for a doodad it describes. Core reads them, and the descriptions in `data/doodad-descriptions.json`, from the installed package as they're published, and keeps no copy. The package keeps no terrain objects' uses (`doodad-uses/terrain-objects/` stays empty), since terrain objects are core's own catalog. The catalog builders don't carry uses, and a catalog description has no `uses`. `search_doodads` merges these files when it loads, then the Workspace's notes. Each result's `uses` lists records, and its text shows each use's variation and scale.

The Workspace's Doodad Uses for game doodads and terrain objects go in `doodad-notes.json` beside `sc2-adjutant.workspace.json`, which the search merges: `{ "doodads": { "<doodad id>": { "uses": [{ "use": "…", "variation": 1 }], "look": "…" } } }`, where `look`, when set, replaces the catalog's look (`catalog/doodad-notes.js` in `@team-antioch/sc2-asset-catalog`). A use written as a plain string, as older files have them, reads as a record with only its `use`.

`add_doodad_note` (MCP and `npm run add-doodad-note -- <id> --use "…" [--variation n] [--scale x] [--from "…"] [--look "…"]`) adds a Doodad Use or a look to that file, for a game doodad or a terrain object. A use it has already (case and spacing aside) takes the new variation and scale, and the source when it has none; contributing fills the published record the same way, and a use the installed package already holds with that variation and scale is dropped from the notes. For a mod doodad it writes them into the doodad's entry in the mod's doodad index instead (its description's `uses`, the same records, and `look`), and refuses one whose entry has no description yet. `contribute_doodad_notes` (MCP and `npm run contribute-doodad-notes -- [--checkout <sc2-asset-catalog checkout>] [--dry-run]`) opens a pull request on TeamAntioch/sc2-asset-catalog with `gh` (`src/catalog/doodad-notes-contribute.ts`). It branches off `origin/main` in the checkout named, such as `../sc2-asset-catalog` beside this one, or else in a fresh clone (`gh repo clone`) in a temporary folder that it removes afterwards. Either way it pushes the branch to TeamAntioch/sc2-asset-catalog itself, so it needs push access there; a fork isn't supported. A dry run changes nothing, but without a checkout it still clones, so it needs `gh` and the network. Each doodad's uses are added to its file under `packages/sc2-asset-catalog/data/doodad-uses/doodads/`, which is created if it has none; a use the file already has with the same variation and scale is left out. A look goes into that package's `data/doodad-descriptions.json`, in place. A changeset (`.changeset/doodad-uses-<time>.md`, a patch) goes with them, so the next release publishes them. These notes stay in the Workspace, each with its reason: a Campaign Mod doodad's, and a game doodad's when the mod gave it a model of its own; a terrain object's, since sc2-asset-catalog holds no terrain objects; a doodad's that sc2-asset-catalog hasn't described, since it takes uses only for described doodads; and any note whose use, source or look names one of the Workspace's Missions (folder, id, title), its Campaign, its mods or its characters (`src/catalog/story-names.ts`), in any case or punctuation, which the repo's CONTRIBUTING forbids. Only the names the Workspace declares are caught, whole: a place, a ship or a short form that's never a Mission's, mod's or character's name isn't, so the dry run is still read before sending. A Mission folder named in general words (`terrain-objects`) holds back notes that use them. Reword such a note in `doodad-notes.json`; a last check refuses to send a pull request whose title, body, commit, branch or changeset would name one. While one of the author's earlier contribution pull requests (a `doodad-uses/` branch) is still open, it opens none and says so, so the same notes don't go twice. Contributed notes stay too, laid over the package's in every search, until a release holds them: each `add_doodad_note` or contribution drops from the file the notes the installed package already holds. Without `gh` or GitHub access the checkout is left as it is and the notes stay. It refuses a checkout with uncommitted changes, or whose `origin` isn't TeamAntioch/sc2-asset-catalog. Once the pull request is open, a checkout goes back to the branch it was on.
