# UI Components from SC2Layout

A Campaign's reusable UI (a boss bar, a toast, later a camera feed and hero frames) is generated by core as SC2Layout files, not built from trigger dialogs. The author decided on 2026-11-09 to build UI from SC2Layout wherever possible, and the in-game tests of that day showed that a package's own layouts, templates and hookups work from a mod. The decisions were made with the author on spec #582.

1. **UI Components in core.** A **UI Component** is a purpose-level piece of campaign presentation that a Mod Blueprint turns on in its `ui` field (`ui.bossBar`, `ui.toast`). Core compiles each one into the mod as the library functions that drive it and, if it shows frames of its own, a layout file. One-off screens can still be hand-written layouts in the Blueprint's `files`. Amended on spec #652 (2026-11-11): a component may have no layout. The hero moment freezes the world, moves the camera and hides the game's UI, so it has no frames. Such a component writes no layout file and adds nothing to the DescIndex, but its functions and script compile as any component's do.
2. **Look.** Each component has its structure and a default look in core, built from Blizzard's stock assets, so it works with no setup. The Blueprint's `ui.<component>` entry overrides named look fields: textures, font style, colours and anchor.
3. **Callers.** The library functions are GUI functions in the mod, so Kept and Editor triggers can call them. Blueprint triggers get matching actions (`showBossBar`, `hideBossBar`, `showToast`) that compile into calls to them. Amended on spec #652: a function may return a value, such as the option a choice picker's player picks. It is then written as a library function of kind `function` with that return type, not an action, so a trigger can use it as a value, and its Galaxy returns the value. A function's body may `Wait`, as a GUI function that isn't a condition can, so a picker can wait for the pick. A returning function gets no Blueprint trigger action until the trigger model can take a returned value into a variable. Amended later: an action may call a function that calls another component's, such as the hero moment's `grantHeroPower`, which runs the moment round a one-card choice picker; it names that component in its `needs`, and a Mission whose Campaign Mod hasn't turned it on fails its compile and `check`.
4. **Generated functions.** A component that is on adds its functions to the mod's library without anyone declaring them. Their IDs are stable, derived from the component's and function's names. Their GUI interface sits in a "UI" folder, and their bodies are Galaxy, for the frame hookups and refresh loops. A component with state (the boss bar's unit and refresh loop, the toast's queue) adds a script too: one Custom Script in that folder, holding its globals and helpers, whose Galaxy the compile writes before the library's functions. Its names are `lib<library>_ui_<component>_<name>`, a namespace the Editor's own names can't reach, so it needs no GUI globals. Amended on spec #652: a component may defer to another the mod turns on too. The toast's queue waits, and the boss bar hides, while a hero moment plays. It calls the other's functions, which the library's header declares, never its script's globals, since that script may come after its own. Without the other component, its output is as it was.
5. **Mod only.** Mission-level layouts wait until a Mission needs a one-off screen. The research note already records how a map registers its own.
6. **A generated DescIndex.** The mod compile writes `Base.SC2Data/UI/Layout/DescIndex.SC2Layout` itself. It loads the components' layouts first, then every layout in the Blueprint's `files` in Blueprint order, so a hand-written file can override a generated default. A hand-written DescIndex in `files` is refused. The DescIndex and every layout are written with CRLF line endings, which is what the Editor writes when it saves them, so opening and saving the mod in the Editor doesn't read as an edit. The ComponentList's `uiui` line is added as for any other component.
7. **The frame-path check.** `check` warns about every literal frame path passed to `DialogControlHookup*` or `DialogControlCreate*FromTemplate`, in a mod's Galaxy or Kept triggers, that is in neither the mod's layouts nor a bundled snapshot of Blizzard's GameUI frames and stock templates. It warns rather than fails, since a path can be built at run time or come from a dependency we haven't read.

## Considered Options

- **Trigger dialogs built in Galaxy.** Rejected: SC2Layout is the modern standard, keeps the look in data the UI Editor opens, and is what Blizzard's own campaign UI uses. Triggers only hook frames up, show and hide them and set their values.
- **A generic frame tree in JSON.** Rejected: it would be SC2Layout in another syntax, with none of its tooling. A component is purpose-level, and anything one-off is a hand-written layout.
- **Style Packs own the UI's look.** Rejected: a Style Pack is visual design for Missions. The look belongs to the Campaign Mod, overridable field by field.
- **Keep the hand-written DescIndex.** Rejected: the generated layouts have to be in it, ahead of the hand-written ones, and an index edited by hand drifts from `files`. Blueprint order is enough to say which layout loads first.
- **LF line endings, as our other generated text.** Rejected: the Editor rewrites a layout and the DescIndex with CRLF on save, and the compile would then see an Editor change in every one.
- **A frame-path error.** Rejected: a path built at run time, or one from a dependency's layout, would stop a good compile.

## Consequences

- Compiling a mod whose `files` still lists the DescIndex fails until it's taken out. The first Campaign Mod's switch-over names the generated DescIndex's change as an Accepted Difference.
- A Kept layout that isn't in `files` isn't loaded by the generated DescIndex, and the compile warns about it. `convert-files` takes Kept layouts into `files`, but not the DescIndex.
- The order of `files` is the layouts' load order. `convert-files` adds the layouts it takes in the package's order, not the Kept DescIndex's, so whoever converts a mod's layouts puts them in load order: templates and constants before the files that use them.
- A Kept DescIndex is written over under the Equivalence Check, as any Kept file is, so a generated one that loads other layouts, or loads them in another order, needs an Accepted Difference.
- A comment in a hand-written DescIndex, such as an include commented out, is lost: the Blueprint's `files` is the list.
- Core has a layout writer (`packages/core/src/ui/layout-writer.ts`) for the components' layouts and the DescIndex.
