# Compiling Waves and Raids

[ADR 0004](0004-reveals-waves-and-other-layout-model-additions.md) declared Waves for the checker and deferred compiling them. We now compile them, and add the **Raid**: a Wave that goes only where the player holds a unit of a given type. For example, an enemy hero raids the player's Assimilators. When losing one shuts down a defence that runs on its gas, the stake explains itself without the units having to focus the Assimilator. The design follows Blizzard's own waves, as its campaign map scripts send them.

**A Raid is a Wave, not a new kind.** It aims at fixed Zones, not at whatever the player owns anywhere:

- `targetZoneIds` (replacing `targetZoneId`, which migrates to a one-item list) lists candidates. Only a Raid may list more than one, since a plain Wave has no rule for choosing. At each send the Wave picks the first candidate the player holds, in list order.
- `onlyIfPlayerHolds: <unit type>` makes it a Raid. A candidate is held when the player owns a completed unit of that type inside the Zone at send time. With no candidate held the send is skipped and the next one waits for its interval. A skipped send never redirects elsewhere: the author's targets are what make one lane raided and the other safe, so pressure that follows the player comes from more Wave streams, not from smarter targeting. A generic raid lists both camps, and a lane's extras list one.
- The Raid aims at the first such unit found, attack-moving there, so it fights the defenders on the way. It succeeds when the player holds none of the type left in the Zone. Its survivors then go home.

**Waves are created on the spot, behind the spawn Zone's walls**, as the AI module's "Create Units Instantly" does. Counts and timings are what the author wrote, so the checker's times hold. Units appear at an optional `spawnAnchorId`, or else at the spawn Zone's walkable cell farthest from every Connection into it. A condition such as "while the enemy holds this Gateway" can be added later, if destroying production should thin the raids.

**Units per difficulty:** `units: [{ type, count }]` replaces `unitTypes`, which migrates by counting repeats. An old list therefore migrates as one unit per entry, though the calibration Blueprints wrote it as the types present; they are checker-only, so their sizes don't matter. A single `count` is Normal's. Casual copies it, and Hard and Brutal scale it ×1.3 and ×1.5, rounded. These are Blizzard's ratios, and Casual is already eased by the enemy's handicap and thinned placed groups (`src/ai/enemy-ai.ts`). Four numbers (Casual, Normal, Hard, Brutal) override the scaling, which is how a type joins only on Hard and up. Timings don't vary by difficulty yet. A unit with `sends: "first"` (the default is `"every"`) joins only the stream's first send that goes out: for a Raid, the first that finds a candidate held, so a skipped send leaves it for the next. It comes in that send's group, so it is targeted, warned, counted for the Raid's success and recalled with the rest. That is how a named leader comes once at the head of a raid (an enemy hero leading the raid, #432). A type may be listed twice, once for every send and once for the first, as an extra at its head, and a repeating Wave needs a unit that comes with every send; the compile report says when, on some difficulty, only the first send's units come, so its repeats bring nobody there. The stream turns on once a mission, since Beats only move forward, so the leader never comes again. A unit that comes once may also be a unit Anchor (#480): its entry's `anchorId` names an Anchor declared with no `position` (its `kind: "unit"`, `zoneId` the spawn Zone, `unitType` the entry's, `player` the Wave's), and the entry owns that binding. Nothing is placed for the Anchor; its unit variable is none until the send creates the one unit and sets it, so `anchorNears`, conditions, speakers and trigger scenes can name the leader. The Wave's player comes from a unit on the map, never from the Anchor it fills, and the compile reports an Anchor that names another. `check_workspace` refuses a binding that could create more than one unit or come more than once (a count above 1 on any difficulty, or `sends: "every"` in a repeating Wave), an Anchor with a position, in another Zone, of another type or with no `unitType` or computer `player`, a second entry binding it, and a binding in a Wave the compile always leaves out (one arriving by anything but ground, or starting at a Beat that never starts in the map). Two bound Anchors whose ids differ only in `-` and `_` are refused too: each one's unit is a trigger variable named for its id, `-` written as `_`. A count of 0 on a difficulty is still once only, but there the Anchor never exists (the send leaves its variable none), so a victory whose every condition waits on it (victory comes on any one of them), an objective, an encounter's start or a Beat whose every start waits on it is refused then. An encounter's attackers and Behavior, and a trigger scene's builder, which must be there from the start, refuse it always. A Wave left out of the map for its map (no computer player, or no ground route) leaves it none for good, and the compile report names the Anchor that never comes. In a trigger scene, a unit change or lasting actor message for it counts as given only once it is there, so one it arrives too late for is given in the Cleanup. A Mechanic's context lists only the Anchors on the map, and names a Wave's unit's apart (`waveUnitAnchorIds`), so a Mechanic needing its unit from the start can say why. The warning's circle reads the units of the sends it warns, on Normal: the first send's, leader and all, with `firstOnly`, else those every send brings (or, if Normal sends none of them, what Normal does send). The threat-paths check lists the first send's units apart.

**The AI's wave system commands them.** The send runs `AIAttackWaveUseGroup`, `AIAttackWaveSetTargetPoint`, one `AIAttackWaveAddWaypoint` per Connection crossing on the checker's route to the chosen candidate, then `AIAttackWaveSend(p, 0, false)`. The tactical AI gives the raiders their micro (Adepts shade, Stalkers blink), as Blizzard's hand-written waves have it. Waypoints keep the walked route the measured one. Each wave keeps its units in a global unit group, for the warning, the success check and the recall. If Test Document shows the AI misbehaving (§9 Q6 and Q9), scripted attack-move orders replace only the send and the cancel.

**Going home:** `AIAttackWaveCancel` sends a wave's units back when its Raid succeeds and when its `endsAtBeat` starts. At a fallback Beat every raid still in the field walks back to its base, so the Beat plays on the map, and the raiders the player let live defend it.

**Warnings are triggered by distance, not timed.** An optional `warning: { seconds, transmission? }` on a Wave compiles to one trigger per candidate, off until a send picks that candidate. The engine's region event takes one unit or any unit, not a group, so the trigger fires when any unit enters a circle around the aim point and the entering unit is in the wave's group. It then turns itself off and pings the minimap, and can play a Transmission cue. The circle's radius is `seconds` × the raiders' speed, so the warning survives a delayed or slowed raid, and the checker reads `seconds` as the Threat's telegraph. `firstOnly` keeps later sends from turning the warning back on, leaving them to the engine's attack alert.

**Every wave clock runs on AI time,** and each In-Game Cutscene pauses AI time on entry and restores it on exit. Raids neither advance nor strike while the player can't act.

## Consequences

- The checker routes each ground wave to every candidate, and `safe-havens` treats each candidate as threatened in the wave's Beats. That is cautious, since any of them may be hit.
- A Raid's Threat has the `combat` consequence like any Wave. A Mechanic that can destroy the same structure (a hazard that sweeps the map, say) has its own Threat, not the Raid's.
- A blueprint's waves now change the compiled map, so `golden.json` changes when the golden Mission's raids are compiled.
- Still deferred: `air`, `drop`, `nydus` and `burrow` arrivals compile only once a Mission needs one. The ground arrival is the only one built here.
