# Custom Texture Sets Beside Kept Ground

A Mission with Kept terrain can declare **texture sets** of its own: `textureSets`, each `{ "id", "name"?, "textures": [up to 8 CTerrainTex ids], "zones": [generating Zone ids] }`. The compile adds the set to the Map Package as one of the map's 8 texture sets, moves every 8×8-cell block that holds a cell of its Zones onto it, and paints those Zones from its textures. A map can then show more than its first set's 8 textures, up to the Editor's 16 across all sets.

The case is a Kept city map. Its Scene 8 factory is built of generating Zones on the map's KorhalCityEx2 textures, and in the Editor it reads as more city street. The map's one set holds 8 textures, so 8 more fit under the cap. A second set, painted only over the factory's blocks, gives the factory its own look without touching the city.

**What the Editor stores.** A texture set's slots live in `t3Terrain.xml`: a `<textureSet i="s" name="…"/>`, the set's textures in `<texture>` slots 8s to 8s+7, and each block's `tileSet`. `t3SyncTextureInfo` repeats the names, with `set_count` sets, and each cell's set. The engine reads each slot's texture name straight from the list. But the Editor holds a set to its tileset: the set's `name` is a tileset (CTerrain id), and on loading a map the Editor keeps a slot's texture only if that tileset's `BlendTextures` lists it, swapping any other for one of the tileset's unused textures, in the tileset's order. Seen on that map on 2026-11-08: a compiled set named `BraxisAlphaEx2` kept its three BraxisAlphaEx2 textures in their slots, and its five others became BraxisAlphaEx2's remaining five. Order is free within the list: the Editor's own sample holds CharDunes's `CharDunes_1`, `_5`, `_3`, `_6`, `_4`. A map adds textures to a tileset's list with a map-local `CTerrain` override in `TerrainData.xml`, as that map does for its set 0 (`<BlendTextures index="5" value="CastanarMeshEx2"/>` on KorhalCityEx2, matching slot 5). So the compile writes one for each set: its tileset, with `BlendTextures` index *l* the set's slot *l*.

**Which blocks.** A set covers every block that holds a cell its Zones own. A Zone's cells are 2×2-aligned and a block is 8×8, so an edge block often holds Kept cells as well. Their texels keep their weights and are read in the new set, layer for layer. The compile refuses unless every layer those Kept texels use holds the same texture in both sets. There are two ways to meet that. The set can reuse the Kept ground's texture at the slot it has in the old set: The factory's edge blocks hold only `KorhalCityEx2_1`, layer 0 of set 0, so a factory set can put `KorhalCityEx2_1` first. Then every Kept byte stays as it was, as everywhere else beside a generating Zone (#247), but that texture now meets itself across the set's boundary, which the Editor renders with a glitch ("Boundaries" below). Or the set's Zones can fill its blocks whole, with an apron Zone over the cells round them up to the block grid, so no Kept ground is left in the set at all. The second is the better design; the first is a stopgap. A block claimed by two sets, a block already on another set the map has (put there in the Editor), or a Zone not in a set whose cells fall in a set's block without its texture, is refused too. Taking an Editor-made set's block would leave no way to put it back.

**Painting.** A Zone in a set is painted from it by name, all 15 on the texture's layer, up to the block boundary. The Editor's texture brush leaves 2 texels unpainted on each side of a boundary between sets. A Zone owns its cells whole, so the compile paints them fully. Otherwise a stale texel would show the new set's texture on its old layer. A Zone in a set with no `texture` takes the texture most of its bordering cells show if the set has it, else the set's first; on a fully generated map, the set's first (Consequences).

**Which set, and its name.** The set takes the index the compile record gives it, else the first index the package doesn't use (no name, no textures, no block). `name` defaults to the tileset that lists most of its textures, skipping names other sets have.

**The record and undoing.** The record lists each set as a `texture-set` entry: its id, its index, its blocks, and a fingerprint of its name, its slots and those blocks' `tileSet`. A set the author changed in the Editor (Map Textures, or the Texture Set brush on its blocks) is a change to keep or discard, as `texture-set:<id>`. The change is looked for before anything is generated, so a changed set is never refused for the Kept ground it now shows differently. Kept, the compile leaves that set's lines and blocks as the Editor has them, at the index it has, and paints its Zones from whatever sets their blocks have. A block the record lists that no set covers now goes back to set 0 if its texels read the same there; otherwise the compile refuses, naming the blocks. A set no block uses any more is emptied: its name and slots go back to `""`. `set_count` is the highest set in use, plus one.

**Boundaries.** A boundary between sets is never clean on its own:
- **The same texture on both sides glitches.** The Editor renders an artifact where a texture touches itself across a boundary, whatever slot it has in each set (the author, from the Editor; an earlier guess that the same slot would blend cleanly was wrong). The compile warns wherever it happens.
- **Different textures cut hard.** The game draws a hard, straight cut along the block edge: a texel can't blend with a texture its set doesn't hold. Seen in game on the city map on 2026-11-08.

So a set's boundary runs under something that hides it: a wall, a cliff edge or a line of doodads, which is the author's practice. The block grid is axis-aligned, so a diagonal edge becomes a staircase of 8-cell steps, all of which need cover. `texture_usage` and the compile list every stretch that needs it, as cells along a block edge with the texture on each side, hard cuts and artifacts both, and leave out the stretches under a cliff (#539).

## Considered Options

- **(a) Move only blocks wholly inside the set's Zones**, and paint the Zones' cells in edge blocks from set 0. Rejected: a Zone would show two looks, cut along a block line that has nothing to do with its shape.
- **(b) Rewrite the edge blocks' Kept texels onto the new set's layers.** This keeps their look whichever layers the set uses, but it rewrites Kept bytes, and it can't work when the Kept texture isn't in the new set. Rejected in favour of asking for the shared layer, which costs one slot and keeps every Kept byte.
- **(c) The set lists its Zones, or each Zone names its set.** The set lists them, so a set and where it is painted read together, as a palette does. A Zone's `texture` still says what paints it, and must be one of its set's. An entry may be a pattern with `*` (`"factory-*"`) matching every generating Zone whose id fits, so a relayout that renames or adds Zones needs no edit to the set. A pattern that matches none is refused.
- **(d) Arrange the slots automatically**, with reused textures moved to the layers they need. Rejected: the slot order is what the author sees in the Editor's texture brush. The compile keeps the Blueprint's order and, when a layer must match, says which texture goes where.
- **(e) A new map-local tileset for the set** (`<CTerrain id="CityFactory" parent="…">` with its own `BlendTextures`), named by the set. Not chosen for now: overriding a stock tileset is what the city map already does and the Editor already reads, while a new CTerrain needs a name string and may need more of a tileset's fields to show in the Editor's lists. The override's tileset may not be one the package's own `TerrainData.xml` overrides already: that entry is Kept Content, and the set would write over it.

## Consequences

- A fully generated Mission takes `textureSets` too (#533; `terrain/generated-texture-sets.ts`). Every Zone there generates, so a set lists any of them. Its compile writes the same lines, sync names, cell sets and CTerrain overrides, through the same plan and writers, onto a fresh map of one set (the Mission's `textures` or `texturePalette`). The painter paints each Zone on its block's set's layers, and the boundary warning lists the stretches as beside Kept ground. A set's Zone with no `texture` wears the set's first, with no variety patches, unless the set has a `palette`: its Zones are then painted by the palette's bands and variety patches, counted from the set's own main level, and a set's `levels` takes every Zone at those levels that no set's list names (2026-11-10, for a cave map whose looks follow depth). No Kept ground stands in a set's edge blocks there, but Zones of two sets can share a block, and a block draws on one set. The compile **snaps** it: the block goes to the set whose Zones cover most of its cells. A Zone in no set counts for set 0, a cell is its last-listed Zone's, and a tie goes to set 0, then to the set listed first in `textureSets`. The other Zones' cells in the block are painted from the winning set, with the texture most of the block's cells wear, and the compile warns, listing each snapped block, the set it went to and whose cells it took. It doesn't refuse, as it does beside Kept ground: there is no Kept look to lose, only a Zone's edge moved to a block line (the author's call on #533, 2026-11-08). Line a set's Zones up with the 8-cell blocks to keep their own edges. A melee map keeps one set.
- The compile writes `t3Terrain.xml`'s texture-set and texture lines and its blocks' `tileSet`, and `t3SyncTextureInfo`'s names table and its cells' sets, beyond the Zones' own cells, and a CTerrain entry per set in `TerrainData.xml`, merged beside the Kept entries. Every other byte stays.
- A set's name is the tileset its override lists its textures under, so it must be a tileset the game or the Campaign Mod has, no other set's name, and not one the package's own `TerrainData.xml` overrides. With no `name`, the compile picks the tileset listing most of its textures among those still free, and refuses when none is.
- A set the author keeps after changing it in the Editor keeps its CTerrain override as the package has it. The compile writes the package's entry back unchanged, along with the sets it does write. Blocks an earlier compile put on one Blueprint set may move to another; a block on a set made in the Editor, or a kept set's, may not.
- The `texture_usage` tool reports which slots a map's ground uses, by Zone, what is free, and what a proposed set would reuse and need. It also lists, and renders on request, each stretch of boundary between sets that needs cover. The compile's warning for each set it writes lists its stretches too, in place of a warning per shared texture.
- A slot of a Blueprint set is Compiled Content: the paint brushes' slot edits, `swap-slot` and `clear-slot` (which empties a slot nothing paints to make room under the 16), refuse one, and the set's `textures` in the Blueprint is where to change or empty it (#535).
- Confirmed in the Editor: it opens and saves a compiled set, with its CTerrain override, as written (the city map, 2026-11-08).
