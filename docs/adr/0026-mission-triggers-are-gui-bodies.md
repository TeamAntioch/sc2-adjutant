# A Mission Blueprint's Triggers Are GUI Bodies Written by the One Engine

[ADR-0002](./0002-typed-gui-trigger-primitives.md) said a Mission's triggers come from typed primitives, never freeform XML or raw script, and [ADR-0025](./0025-typed-primitives-are-the-authoring-layer.md) made the primitives the authoring layer over one Galaxy engine. A trigger no Blueprint concept or Plugin Mechanic covers still had to be made by hand in the Editor (#1027, agreed with the author on 2026-11-23). **A Mission Blueprint now holds trigger elements of its own as GUI Bodies**: data stored by Editor element Id, one JSON file per element under `missions/<id>/triggers/`, listed by path in the Blueprint's `triggers`. Its global variables (`triggerVariables`) and Trigger Folders (`triggerFolders`) are declared in the Blueprint itself. A body is the tree a library function's body already uses (`library-interface.ts`): calls, parameters and values, with a trigger's flags, local variables, events, conditions and actions around it. A library's element is `<library>/<id>`, checked against the library data in reach; the map's own is its Id alone, so Kept and Blueprint elements name each other freely. The compile writes each element's XML as the Editor does and its Galaxy through the one engine, `callGalaxy` in the map's TemplateScope, by way of the Kept renderer, so an authored trigger and a Kept one come out alike.

**Custom script is relaxed, not opened up.** A converted element keeps the custom script it holds as data, as `convert_library` does for a mod. A new trigger gets custom script only when the mapper asks for it, or when no game function can do the job, and then the session says which and offers a Missing-Feature Report (ADR-0024). That relaxes ADR-0002's "never raw script" for Mission triggers. The typed primitives stay as a convenience that lowers to the same tree; Plugins keep to them (ADR-0005).

## Considered Options

- **Grow the catalog until it covers every trigger.** Rejected: the game has some 3,000 functions and the catalog about 204. Every new need would wait on a primitive, and the long tail would never close.
- **Hold authored triggers as the Editor's XML verbatim, as a Mod Blueprint's `triggers` do.** Rejected: a session can't edit XML safely, nothing checks it, and its Galaxy would still need an Editor save.
- **Hold them as Galaxy text.** Rejected: the Editor shows such a trigger as one block of custom script, which the author can't read or tune in the Trigger module, and it loses the checks against the library data.
- **Write their Galaxy from the tree directly, beside the Kept renderer.** Rejected: two writers for one map would drift. The compile writes the XML, and the Kept renderer, already checked against Editor saves, reads it back through the engine.

## Consequences

- The ids are the author's to keep, as ADR-0011's are for a mod. A Blueprint element's Id may be no Kept element's and none of the compile's own; the compile refuses a clash, naming the element and its file.
- A body can't name what a concept compiles to (a Beat's trigger, a Wave's variables): those are the compile's and may change. It names Kept elements, the Blueprint's own, and library functions in reach; anything else is refused before anything is written.
- Authored elements are Compiled Content (ADR-0010): spliced beside Kept triggers, filed in Root (before the compile's own) or in the Blueprint's folders, fingerprinted on the record, and checked for Editor changes like any other. Unlike the compile's own, each stays where the package has it from one compile to the next, so the Root's order holds.
- A Kept trigger converts into the Blueprint (`convert_triggers` given a Mission, #1030) with its element Ids, so it is the same element: a Blueprint trigger with a Kept trigger's Id is that one converted. The first compile writes it in place of the Kept one, its Root line and elements where the Editor had them and a Kept folder still filing it, under the Equivalence Check (ADR-0011): its Triggers XML and its Galaxy blocks are compared with the Editor's, and a difference refuses the compile, writing nothing. Kept References and holds (ADR-0014) go on naming it by Id and Galaxy name; a hold switches off its start in its body, as it does a Kept trigger's in the package.
- A Blueprint trigger joins the Mission's structure as a Kept one does (#1036). A trigger reference in `kept` names it by its element Id, `{ "id": "gather-fighters", "kind": "trigger", "editorId": "5A5A1001", "name": "Gather Fighters" }`, the same reference a Kept trigger has and keeps when converted, so a Beat can start on its run and a cue wait on it (`keptTriggerRuns`), and it can be held until a cue (`hold`). Such a reference is found in the Blueprint's `triggers`, not the package, so it works before the trigger has ever been compiled, and its name is compared with the trigger's file. We kept one reference form rather than adding a Blueprint-only one, since a second form would have to be rewritten whenever a trigger converts. A disabled Blueprint trigger has no script, so a reference to it is refused, as a hold on one that starts on another event, or from one that doesn't run it, is.
- A body can't name the elements a concept compiles to (its triggers, globals and functions): they are the compile's and may change. The refusal names the element and points to the cues, since a trigger reacts to a concept by being held until the concept's cue, or by a Beat starting on its run. Where a concept lacks the cue, that gap is a ticket on the concept.
- A file may hold a function instead of a trigger (`"kind": "function"`, #1032): its interface is a library function's (kind, flags, return type, parameters, block slots), its body its own variables and actions, the map's own preset types and structures named by their Ids. Its XML is the library writer's in a map's form, and its Galaxy the Kept renderer's: its declaration in Global Function Declarations and its definition in Global Functions, sections the compile makes when the script has none. A converted function is written over its Kept original under the Equivalence Check, as a trigger is; a call to a Blueprint function from a trigger or another function names it by its Id, as a call to a Kept one does. A Blueprint function the last compile wrote is the Blueprint's own, never a concept's.
- A Kept global converts into the Blueprint's `triggerVariables`, keeping its Id, and the compile writes it over the Kept one, its declaration and initialization under the Equivalence Check. A comment filed among the map's items is a file of its own (`"kind": "comment"`), with no Galaxy. A constant global, which the Editor declares in Constants, stays Kept for now.
- Other element kinds (presets, records, custom script and folders) come in a later layer of #1032, on the same layout.
