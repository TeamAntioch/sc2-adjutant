# Typed Primitives Are the Authoring Layer, Not the Limit of What Is Written

[ADR-0002](./0002-typed-gui-trigger-primitives.md) made typed primitives the way a compile writes triggers: core's catalog (`trigger-catalog.ts`) wraps each of the game's functions it needs, with its Editor ids, typed parameter names and a hand-written function that writes its Galaxy. The mod generator (ADR-0011) meanwhile wrote the same functions' Galaxy from the game's library templates, so every form was fixed twice, and a Kept trigger could only be tuned when every function it called was in the catalog (#937). We now split the two jobs (#943, agreed with the author on 2026-11-22). **Typed primitives are the authoring layer**: the names and parameters the Blueprint builders and Plugins (ADR-0005) write calls with, and the ids a compile writes into `Triggers`. **Galaxy for the game's functions comes from the library templates**, through one engine (`src/mods/library-galaxy.ts`) that takes a map's or a library's scope. The catalog no longer limits what can be rendered: anything in the game's library data, or a library in reach, can be.

## Considered Options

- **Keep the hand-written renderers beside the templates.** Rejected: two writers for one form drift, and each new form (#944–#952) would be written twice.
- **Drop the catalog and have builders call the library data by id.** Rejected: builders and Plugins would lose typed parameter names and the checks that come with them, and the ids would spread through every builder.
- **Generate the catalog from the data.** Rejected for now: its names and parameter keys are hand-chosen, and Plugins already use them (ADR-0005). The data checks them instead.

## Consequences

- A primitive's `galaxy` is optional. Core's entries have none: each is written from its template in the map's scope, and a test wrote every entry both ways and found them equal before the hand-written renderers went. The two VCMI entries keep theirs until the game's library data holds VCMI (#951).
- A Plugin's primitive with a `galaxy` of its own keeps it. A Campaign Mod's library functions as primitives have none (#974): the compile's map scope holds the libraries in reach of the map, as the Kept renderer's does, so their calls come from the mod's library interface. Two kinds still keep one: an event, whose own call leaves out the trigger it binds to, which the engine passes first as the Editor does (likely a bug in its own call, left for a follow-up since no Workspace's library has an event yet), and a UI Component's function (the Mod Blueprint's interface doesn't declare it, so the library in reach lacks it until the mod's package is compiled). One without must name a function the game's library data defines, with the data's parameter ids, or the Workspace doesn't load. A block can't have a `galaxy` of its own, since a call from its arguments would drop the calls its block holds.
- The compile's map script writer and the Kept renderer write a call the same way: its own `galaxy` where it has one, else `callGalaxy` with a map scope whose own writer writes the values. Blocks (If Then Else, Pick Each, While, Wait For Condition, Switch) come from their templates too.
- A preset's value stays a string in the catalog: it is a constant, not a renderer, and the same test checks each against the data.
- Where the hand-written renderers knew better, the engine learned it: an event's unit is a reference to the unit unless its native takes a plain unit (Unit Enters Range Of Unit's other unit, as `natives.galaxy` and Editor saves have it), and a block with an empty condition slot, or a call in a slot its template doesn't write, is refused rather than written as `if ()` or dropped. A condition, an event or a global's initial value whose template declares variables is refused, since none of the game's functions that give a value declares any and no Editor save shows where they would go.
