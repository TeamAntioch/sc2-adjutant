# sc2-adjutant

Co-design and compile StarCraft II single-player campaign missions from narrative inputs and setting descriptions into playable, unpacked map packages.

See [GLOSSARY.md](./GLOSSARY.md) for domain language, [docs/adr](./docs/adr) for architecture decisions, and [docs/plugin-api.md](./docs/plugin-api.md) for the Plugin API.

## Packages

The repo is an npm workspace:

| `packages/plugin-host-macos` | `@team-antioch/sc2-adjutant-host-macos` | The macOS Host Adapter, loaded as `bundled:host-macos`; its Editor and game facts are in its [docs](./packages/plugin-host-macos/docs/macos-host.md) |
| `packages/plugin-host-windows` | `@team-antioch/sc2-adjutant-host-windows` | The Windows Host Adapter, loaded as `bundled:host-windows`; its Editor and game facts are in its [docs](./packages/plugin-host-windows/docs/windows-host.md) |
| `packages/plugin-style-antioch` | `@team-antioch/sc2-adjutant-style-antioch` | The Antioch Style Pack: Exemplar Maps, Map Studies, Design Lessons and their rules, Doodad Composites and guides |
| `packages/plugin-anim-testbed` | `@team-antioch/sc2-adjutant-anim-testbed` | The first bundled Utility, `bundled:anim-testbed`: builds an animation and sound test map from a spec, with a dialog in the game to pick a unit, clip, slot and variation and play it, every id checked first. Its `anim-testbed` skill is copied into a Workspace that lists it |
| `packages/doodad-finder` | `@team-antioch/sc2-adjutant-doodad-finder` (private) | The Doodad Finder ([ADR-0020](./docs/adr/0020-doodad-finder-narrows-locally-and-ranks.md)): candidate cards, a local embeddings model (gte-small, run by transformers.js) and the narrowing that merges its nearest cards with core's keyword search. Core gains no dependency for it. Its model downloads to the machine's cache at first use and its vector cache is git-ignored. `npm run test-doodad-finder` runs the narrowing on past Doodad Searches and reports its hit rate and timings |
| `packages/claude-plugin` | `sc2-adjutant-claude-plugin` | The Claude Code plugin: it starts the MCP server for the Workspace Claude Code has open, and ships the co-design skills (`level-design`, `hero-mission-design`, `encounter-design`, `ally-design`, `cinematography`, `exemplar-design`, `style-pack-builder`, `texture-sets`, `doodad-search`, `custom-doodads`, `boss-design`, `boss-build`, `sound-mix`, `melee-design`), the `report-missing-feature` skill and commands. This repo's `.claude-plugin/marketplace.json` lists it, and [the site's install page](https://adjutant.antioch.games/install/) says how to install it. `.claude/skills/` links to the skills, so Claude Code in this repo still finds them |
| `site` | `sc2-adjutant-site` (private) | The site for adjutant.antioch.games: a Next.js app with Tailwind and MDX, exported as static pages to `site/out/`, then indexed there for search by Pagefind (`site/out/pagefind/`), which runs offline from the binary its npm package installs. The root build builds it last, after core. `npm run serve -w site` serves the export on http://localhost:3975, where ⌘K (Ctrl+K) searches; under `next dev` there is no index |

Plugins import core only as `@team-antioch/sc2-adjutant/plugin-sdk`, which resolves to `packages/core` through the workspace's `node_modules/@team-antioch/sc2-adjutant` link; `npm run lint` and `npm test` refuse a Plugin file that imports core any other way (`scripts/check-plugin-imports.mjs`). The doodad catalog and the Doodad Finder are the public sc2-asset-catalog's, used through its published packages at a pinned version; they also refuse a module that moved there coming back, or a pin that isn't exact (`scripts/check-catalog-moved.mjs`, which lists them; see ADR-0022 and [docs/agents/asset-catalog.md](docs/agents/asset-catalog.md)). The Host Adapters, the Style Pack and the Finder wrappers build with `tsc` to their `dist/`, from the shared `packages/core/tsconfig.plugin.json`, against core's emitted declarations (core builds first). A Plugin package's manifest `entry` names the built file, since Node won't strip types from a file under `node_modules`. Each build ends by writing `dist/.built`, and in a checkout core refuses a package whose TypeScript changed since then, saying to run `npm run build`. A package's tests may reach core's internals as `@team-antioch/sc2-adjutant/src/…`, which the shared `packages/core/vitest.plugin.ts` points at core's source. A local Plugin folder, such as a Workspace's own, can still name a TypeScript entry, which Node loads with type stripping. Each public package (listed in `scripts/public-packages.mjs`, in publish order) has a `files` list. `npm run check-packs` builds, then packs each one with `npm pack --dry-run` and fails when a tarball is over 20 MB, misses a file its `package.json` or Plugin manifest names, or holds a path that never ships (`tests/`, `frames/`, `evidence/`, `captures/`, core's `data/thumbnails/` and `data/catalog-sheets/`, and a Map Study's `minimap.png`). `npm test` runs the same check at its end (`scripts/check-packs.mjs`). The plugin's packed-install test (`packages/claude-plugin/tests/packed-install.test.ts`) installs them as a mapper would: it packs the built core, the Finder wrappers and this platform's Host Adapter, runs `init` from core's tarball with `npm exec`, installs the tarballs in that Workspace and starts the plugin's launcher with no `core_path`, so it needs the npm registry for core's own dependencies. The six public packages, the plugin's manifest and its package.json release together at one version. A `v<version>` tag on the public repo runs `.github/workflows/publish.yml`: it refuses a tag whose version isn't theirs, runs `npm ci`, the build and the tests, then `npm publish --provenance --access public` for each public package in that order, through npm's trusted publishing (OIDC, no token), skipping one already on npm (`scripts/publish-packages.mjs`). [docs/releasing.md](docs/releasing.md) has the steps for a release. On a pull request it runs `npm publish --dry-run` for each instead. The monorepo root and the plugin's package.json stay `private`: the plugin ships through the GitHub marketplace.

The macOS Host Adapter, `bundled:host-macos`, is the `@team-antioch/sc2-adjutant-host-macos` package, which core doesn't depend on. The Windows one, `bundled:host-windows`, is the `@team-antioch/sc2-adjutant-host-windows` package, likewise. Neither loads unless the machine config's `hostAdapter` names it ([the machine config](packages/core/README.md#the-machine-config)), and one it names must be installed. With none named, the CLIs and the MCP server run with no Host Adapter, so a compile or a check still works.

Run everything from the repo root. `npm install` links the packages and builds them. `npm run lint` and `npm test` run every package's, `npm run update-golden` regenerates every package's goldens (core's golden compiles a reference Mission, `docs/agents/stacked-prs.md`), and the CLI scripts (`npm run compile-map -- …` and the rest) build every package and run core's CLI from the root, so the paths you give them stay relative to where you typed them; core's own `package.json` has no CLI scripts. `npm run test:watch` watches core's tests. One package alone: `npm test -w @team-antioch/sc2-adjutant`. The catalog and analysis scripts in `packages/core/scripts/` run from the repo root too (`node packages/core/scripts/…`): they read core's `data/` wherever they run from, and those that need a Workspace use the one they're run in.

## Workspace and Plugins

A Workspace ([ADR-0005](./docs/adr/0005-code-plugins-with-typed-contributions.md)) is a folder of Missions with a `sc2-adjutant.workspace.json` at its root, which names the Campaign, the folder of Missions, its mods and the Plugins to load. Its fields are in [core's README](./packages/core/README.md#the-workspace). Plugins (Campaign Packs, Style Packs, Utilities ([ADR-0023](./docs/adr/0023-utility-plugin-role.md)), Host Adapters and single Mechanics), how a Workspace names them, their manifests and every kind of Contribution are in [the plugin API](./docs/plugin-api.md). The generic `hazard` Mechanic in `packages/core/src/plugins/hazard/` is the worked example. The CLIs find the Workspace above the blueprint they're given, and validate the blueprint against core and every loaded Plugin. A Mechanic type that neither provides fails.

This repo's own `sc2-adjutant.workspace.json` is the example Workspace (`packages/core/examples/example-campaign`) seen from the root: the same Missions, Campaign Pack and hazard, and no Style Pack, as the example's own config has, so the MCP server at the root and the CLIs run on the example's Blueprints load the same Plugins. The Style Pack's tools (`npm run study`, the capture tools and the exemplar scripts) need a Workspace that names a Style Pack: run them from your own. `packages/core/examples/test-fields` is a second example Workspace: small test maps of single features, such as `npm run lighting-preview`'s default. An author's Missions live in a Workspace of their own, often a repo cloned beside this one whose config names these packages by path (`../sc2-adjutant/packages/…`).

A Utility is a tool a Workspace chooses to add, listed in its config's `utilities` ([ADR-0023](./docs/adr/0023-utility-plugin-role.md)). `packages/plugin-anim-testbed/` is one: `"utilities": ["bundled:anim-testbed"]`, with the package installed beside core.

The Antioch Style Pack in `packages/plugin-style-antioch/` is a Workspace's `stylePack`: the Exemplar Maps, Map Studies, Design Lessons, Doodad Composites and guides the `exemplar-design` skill reads.

A Campaign Pack can be a local folder Plugin in the Workspace, as the example Campaign's `plugins/campaign-example/` is, named by the Workspace config's `campaignPack`. It may contribute Mechanics, a Screenplay naming template and its own Lights (`lights.json`). Its characters are declared in the Campaign Mod's Blueprint (`mods/<id>/blueprint.json`). A Mechanic can contribute trigger `primitives` core lacks; its triggers may use only those and core's, or the compile fails. A Plugin's entry may be TypeScript, which Node (22.18 or later) and vitest both load as it is. Its files import each other by their `.ts` names, and import core from `@team-antioch/sc2-adjutant/plugin-sdk`: the built `dist/` for Node, the source for vitest.

The Workspace config's `mods` names the Workspace's mods by id ([ADR-0011](./docs/adr/0011-mods-from-mod-blueprints.md)), each in `mods/<id>/` with its Mod Blueprint (`blueprint.json`: `id`, `kind` `campaign` or `asset`, and `dependencies` as DocumentInfo lists them), its committed mod package (`<Name>.SC2Mod`) and its compile record; `import_mod` adds them. A Campaign Pack names its Campaign Mod in `contributions.campaignMod`, by package name without `.SC2Mod` (the example Campaign's: `Example`), or the Workspace config does in `campaignMod`, so a Campaign needs no Plugin to have one; the Workspace mod of that name is the Campaign Mod, and `check-workspace` fails when the Workspace has mods but none of that name. The Campaign Mod is a catalog layer: Missions use the tilesets, textures, Lights, units, doodads and models it defines as they use the game's, and core's `data/` holds only the game's own ([docs/reference/campaign-catalog.md](docs/reference/campaign-catalog.md)).

A Campaign's characters are declared in its Campaign Mod's Blueprint (`characters`, [docs/reference/characters.md](docs/reference/characters.md)), not by a Plugin: each gives its speaker, its CCharacter id, the name its Transmissions show, the unit type or portrait model an off-map Transmission shows, its other CharacterData fields and a placeholder text-to-speech voice. Once the Campaign Pack names a Campaign Mod, a Screenplay speaker with no character fails the compile and `check_workspace`.

To start a Campaign of your own, copy the public example Workspace in [packages/core/examples/example-campaign](./packages/core/examples/example-campaign/README.md). It has its own Campaign Pack (a naming template), a small Campaign Mod declaring three stock Blizzard characters, a plain Markdown Screenplay, the `hazard` Mechanic and a small example Mission, and its README walks through making it yours.

Screenplays are Markdown in the format documented in [docs/screenplay-format.md](./docs/screenplay-format.md). The Campaign Pack may also contribute a Screenplay Source ([the plugin API](./docs/plugin-api.md#campaign-pack-kinds)). With one, a Blueprint's `screenplay.script.ref` names the Screenplay there, `npm run pull-screenplay -- <blueprint>` writes it over `screenplay.script.source`, and `npm run edit-screenplay -- <blueprint> <edits.json> [--dry-run]` edits it. `npm run refresh-screenplay -- <blueprint> [--map <output-dir>]` then pulls, moves the Cinematics' shots onto their lines' new sound IDs, writes placeholder voices, compiles the map when given a folder, and checks the Mission. Without one, the Screenplay files are the Screenplays, and the compiler reads them as they are.

## MCP server

`npm install` builds `packages/core/dist/` and each built package's `dist/`, since the root `prepare` script runs `npm run build`, core first; after pulling changes, run `npm run build` again. Then point an MCP client at `node packages/core/dist/mcp/main.js <workspace-folder>`, or the `sc2-adjutant-mcp` bin, over stdio (the current folder by default). In Claude Code, the plugin in `packages/claude-plugin` does this for you. It serves one Workspace, a Mission being its folder name under the Workspace's missions folder:

- `compile_map` compiles the Mission in place, into its committed Map Package beside its Blueprint (`<mission>/<Name>.SC2Map`: the one `.SC2Map` folder there, or one named from the Mission's folder, `ashfall-relay` giving `Ashfall-Relay.SC2Map`), and rewrites `<mission>/compile-record.json`, which lists every object, region, string key, trigger and file the compile wrote ([ADR-0010](docs/adr/0010-compiled-and-kept-content.md)). The next compile replaces exactly what the record lists and leaves everything else in the package (Kept Content) byte for byte; a Kept file it would write differently stops the compile, except a `WaterData.xml` the Editor saved holding only its own entries for stock water types (`<CWater id="Agria">`), which a compile writing the Mission's water areas replaces. Beside Kept triggers (ones the record doesn't list) the compile splices its own into `Triggers` and `MapScript.galaxy`, leaving the Editor's XML and Galaxy for each Kept trigger byte for byte (an include the compile adds stays, since a Kept trigger may come to call its library), and refuses a trigger or global whose script name (`gt_`, `gv_`) a Kept one has. A Compiled region keeps its number (its place among the Zones' regions, the Waves' warning circles, the set pieces' and the Blueprint's own `regions`) unless a Kept region holds it; then it takes the next number past every region's, and the compiled triggers that use it follow. With no record (a first compile) every file is written whole. **Editor changes:** before writing, the compile compares each record entry's fingerprint with the package. When the author has changed Compiled Content in the Editor and the compile would overwrite it, nothing is written: the compile lists each change by entry (`object:<id>`, `region:<id>`, `trigger:<id>`, `variable:<id>`, `string:<file>:<key>`, `file:<path>`). A change `sync` brings back (a moved Anchor, a redrawn region, ground raised or lowered, a water area) is listed under "Run sync first". Each other one is kept (`keep`, `--keep <entry>`): it stays as the Editor left it and leaves the record, listed under the record's `kept`, as Kept Content the Blueprint no longer writes, and each compile warns that its declaration is unused until it's removed or the entry is discarded by name. Or it is discarded (`discard`, `--discard <entry>`): overwritten with what the Blueprint says. `keepAll`/`--keep-all` and `discardAll`/`--discard-all` answer the rest. Not compared: what the Editor rewrites on every save (`MapScript.galaxy`, which follows `Triggers`; the ComponentList, `DocumentHeader`, `DocumentInfo`, `MapInfo`, `Minimap.tga` and the `.version` stamps), the terrain files it computes from others (`t3Sync*`, `t3CellFlags`, kept with the terrain file they come from), what the Editor re-encodes when it saves (`t3HeightMap` at its own quantization read as heights within 0.01, off the compile's ramps, which it works out again; `t3Terrain.xml`'s version and `<vertData>`; `t3Water`'s tiles in any order, a tile naming the stock type of the pool's own CWater; a `WaterData.xml` whose CWaters the compile also writes say the same; and a placed object's indent, its `Rotation="0"` and `Variation="0"` left out, and the `HeightAbsolute` flag it gives every doodad), and numbers within sync's tolerances (0.05 for a doodad's height, 0.01 for a position or a region's shape, 0.001 for anything else). A name in `keep` or `discard` that is neither a listed change nor a kept entry is refused. `outputDir`, a folder inside the Workspace relative to its root, is written whole and leaves the record alone. `npm run compile-map -- <blueprint.json> [<output-dir>] [--keep <entry>]… [--discard <entry>]… [--keep-all | --discard-all]` does the same. Two compiles to one folder run one after the other. A Screenplay line with no voice file gets a placeholder at `<audioDir>/<sound id>.wav`: spoken when the Host Adapter has `tts.speak`, otherwise silence as long as the line's estimated reading time, so Transmissions time correctly until real recordings replace them. Each Cinematic the Blueprint lists in `screenplay.script.cinematics` is written to `Base.SC2Data/Cutscenes/<cinematic id>.SC2Cutscene` (below).
- `import_map` makes a Mission from a Map Package built outside the Workspace (Import, [ADR-0010](docs/adr/0010-compiled-and-kept-content.md)): `source` (an unpacked `.SC2Map`, absolute or relative to the Workspace root) is copied byte for byte to `<missions>/<mission>/<Name>.SC2Map`, the source only read, with a minimal Blueprint read from the package (id, title, Campaign, setting, map size, tileset and dependencies) and an empty compile record, so everything in it starts as Kept Content. The Editor's default map name ("Just Another StarCraft II Map") becomes the title (`title`, by default the map's own name or its file name). When the Screenplay Source's `refForConversation` knows the package's conversation, the Blueprint refers to that Screenplay, under the package's own conversation id (`screenplay.script.conversationId`, in place of the naming template's, so an imported `Chapter1-01` stays `Chapter1-01`), and pulls it; one that can't be pulled, or a Source that can't look the conversation up, is left out, and the reply says why. The Blueprint has no Zones or Beats: a compile then leaves the package's terrain, map info, ComponentList and triggers as they are (even ones an earlier compile wrote, which drop off the record), writes only what the Blueprint declares beside them, adding a line to the ComponentList only for a component it writes that the list lacks, and the first compile after Import changes nothing; `check_layout` reports every check not evaluated, and `sync` refuses, since nothing in the package was compiled. `npm run import-map -- <source.SC2Map> <missionId> [--title …] [--setting …]` does the same.
- `import_mod` makes a Workspace mod from a mod built outside the Workspace (Import, [ADR-0011](docs/adr/0011-mods-from-mod-blueprints.md)): `source` (an unpacked `.SC2Mod`, absolute or relative to the Workspace root) is copied byte for byte to `mods/<mod>/<Name>.SC2Mod`, keeping its name since Missions' dependencies name it, the source only read, with a minimal Mod Blueprint (id, kind and the dependencies its DocumentInfo lists) and an empty compile record, so everything in it starts as Kept Content and the first compile changes nothing. The Workspace config's `mods` gains its id. `kind` is `campaign` when the package has `Triggers`, or catalogs, Galaxy, cutscenes, layouts or font styles in `Base.SC2Data`, else `asset` (an Asset Mod may keep its art in `Base.SC2Data/Assets`), unless given. An Asset Mod's binaries (models, anims, textures, images, audio, video, fonts, FaceFX) are tracked by Git LFS: `.gitattributes` gains each `mods/<mod>/**/*.<ext>` pattern it lacks, matching the extension in any case (`*.[dD][dD][sS]`), and every machine committing them needs `git lfs install` first. `npm run import-mod -- <source.SC2Mod> <modId> [--kind campaign|asset]` does the same.
- `compile_mod` compiles a Workspace mod's Mod Blueprint into its committed package in place, under its compile record ([ADR-0011](docs/adr/0011-mods-from-mod-blueprints.md)). The Blueprint owns `gameData` (a `<Catalog>` source per GameData file, merged entry by entry), `entries` (Generic Entries, below), `characters` (each a CCharacter in CharacterData, written as a Generic Entry: [characters.md](docs/reference/characters.md)), `library` (the Campaign Mod's **Library Interface**: each function's FunctionDef spliced into `Triggers`, its strings, and a GUI function's Galaxy written into `Lib<id>.galaxy` as the Editor generates it, a Galaxy body's script file whole; an interface change that would renumber an id the package has fails the compile: [library-interface.md](docs/reference/library-interface.md)), `strings` (keys per strings file), `triggers` (a library's triggers and globals, spliced into `Triggers`), `files` (scripts, cutscenes, UI files and plain files, written whole) and `soundSets` (a CSound per line of a conversation, in the template form or with its AssetArray in full, playing the voice file its Asset Mod declares), each source a file in `mods/<id>/`. An Asset Mod's Blueprint owns `assets` and `voices`: each file's **Asset Source** (a Workspace file checked against its SHA-256, a community asset fetched once to the machine's cache, a generated placeholder, or a file derived by a named step such as `wav-to-ogg`), and a voice file per line of a conversation, its recording first, else a placeholder in its character's voice; community assets and placeholders are kept out of git ([asset-sources.md](docs/reference/asset-sources.md)). Every Kept byte stays as the Editor wrote it, and once the Blueprint owns anything the compile generates DocumentInfo and DocumentHeader with its `dependencies`, the ComponentList and the `.version` stamps, each changed only where the Blueprint or a new component calls for it. A part written over a Kept one is converted under the **Equivalence Check**: compared with the original with ordering, whitespace, attribute order and number formatting ignored, and a difference fails the compile, writing nothing, unless `acceptedDifferences` names it (`{ item, reason }`, by entry name such as `catalog-entry:<file>:<Class>:<id>`). An **Accepted Removal** in `removals` (`{ item, reason }`: a Kept `string:<strings file>:<key>`, `line:<strings file>:<text>` for a line with no key, or `file:<path>`) is removed from the package, and the check expects it gone: a strings file converted whole is compared with its original less the removals, and a part that writes one back fails. Compiled Content changed in the Editor stops it until the author keeps or discards each change (`keep`, `discard`, `keepAll`, `discardAll`). `npm run compile-mod -- <blueprint.json> [--keep <entry>]... [--discard <entry>]... [--keep-all | --discard-all]` does the same.
- `convert_entries` writes the Kept entries of one of a mod's GameData files (or those named) into its Mod Blueprint as **Generic Entries**, `{ catalog, class, id, parent, fields }` in `mods/<id>/entries/<file name>.json`, keeping their ids, so breadth conversion is mechanical; `compile_mod` then converts them under the Equivalence Check. Generic Entries are checked against the game's **Data Schema** (`packages/core/data/catalog-schema.json`, read from the install: [catalog-schema.md](docs/reference/catalog-schema.md)), and an unknown field, a wrong kind of value or a class in the wrong catalog fails the compile, naming the entry. An entry that doesn't fit, or whose generic form wouldn't read back the same, stays Kept, with the reason, as does a CConversation whose Screenplay the Screenplay Source knows, for `convert_screenplay`. Once the Blueprint owns entries, DocumentInfo keeps its preloads but drops an `AssetFile` nothing names any more: one only converted entries named, which none of them, no Kept entry and no other file in the package (or that the compile writes) names now. It adds none, since preloading every file the entries name would grow one Campaign Mod's 13 preloads to about 1,555, untried in game. `npm run convert-entries -- <blueprint.json> <Base.SC2Data/GameData/<file>.xml> [--entry <Class>:<id>]...` does the same.
- `convert_files` writes a mod's Kept whole files into its Mod Blueprint's `files`, copied into the mod's folder (`scripts/…` for `Base.SC2Data/scripts/…`). By default it takes the Galaxy scripts, UI layouts and font styles, leaving the Editor's generated `Lib<id>.galaxy`. Each file takes the strings it names as `@<key>` (a layout's text) into its `strings` ([mod-strings.md](docs/reference/mod-strings.md#the-triggers-text-values-and-a-layouts-strings)). `npm run convert-files -- <blueprint.json> [--path <file>]...` does the same.
- `convert_assets` declares an Asset Mod's Kept art and audio files as Workspace-file Asset Sources in bulk, each copied into `mods/<id>/assets/` with its SHA-256. It lists the files whose names suggest another origin for the author's provenance check, and records the origins the author gives (a port of another game's asset, or a credited community asset) by glob ([asset-sources.md](docs/reference/asset-sources.md)). `npm run convert-assets -- <blueprint.json> [--suspect <glob>]... [--origins <origins.json>]` does the same.
- `convert_library` writes Kept functions of a Campaign Mod's GUI library (or those named, by name or id) into its Mod Blueprint's **Library Interface**, keeping their imported ids: a GUI function's body as a **GUI Body** in `mods/<id>/library/<identifier>.json`, a native one's as the script file that defines it, copied into the mod's folder. A function stays Kept, with the reason, when its XML holds a form the conversion doesn't write yet or its Galaxy wouldn't come out as the Editor's. Mission compiles call the library's functions from the interface (a Mechanic's `context.library`). `npm run convert-library -- <blueprint.json> [--function <name or id>]...` does the same. It also converts the library's categories (trigger folders), preset types, structures, comments and custom script.
- `convert_triggers` writes Kept triggers and globals of a Campaign Mod's library (or those named) into its Mod Blueprint's `triggers`, as the Editor wrote them, with their names and their text parameters' values (`triggers.strings`), keeping their ids. `npm run convert-triggers -- <blueprint.json> [--item <name or id>]...` does the same.
- `convert_screenplay` declares the Screenplay a Kept CConversation of a Campaign Mod comes from (an interlude or a set of hub chats) in its Mod Blueprint's `screenplays`, found and pulled from the Screenplay Source into `mods/<id>/screenplays/`, its lines matched to the Conversation's imported line ids and Sounds; `compile_mod` then compiles it into ConversationData and ConversationStrings, every speaker one of the Blueprint's characters ([mod-screenplays.md](docs/reference/mod-screenplays.md)). Each line whose text differs from the Kept one is listed, to name as an Accepted Difference. A wordless scene is an empty group, and a group keeps a stale imported name. Only on the author's decision, `accept` (the reason) lets the Conversation's groups or ids differ, and `renumber` pairs the lines of a Screenplay renumbered at the Source in order and makes the mod's Kept references follow the new ids. `npm run convert-screenplay -- <blueprint.json> <CConversation id> [--ref <ref>] [--source <file>] [--accept <reason> [--renumber]]` does the same, and `npm run pull-screenplay -- mods/<id>/blueprint.json` refreshes the mod's Screenplays. Given a Kept-terrain Mission instead (`mission`, with an optional `accept` reason), it converts the Map Package's own conversation to the Mission's Screenplay, so `compile_map` writes it from then on; it returns the lines keeping their imported Sounds, those changed, added and dropped, speaker changes, the Kept cutscenes the compile relinks, the Sounds and strings the first compile removes as nothing plays them, and each difference it meets, and `accept` names those as accepted. `npm run convert-screenplay -- missions/<id>/blueprint.json [--accept <reason>]` does the same ([screenplay-format.md](docs/screenplay-format.md#an-imported-maps-own-conversation)).
- `propose_removals` lists a mod's Kept leftovers that look safe to drop as Accepted Removals, each with a reason: ConversationStrings `Conversation/…` keys no GameData file names, old merge conflicts' lines in strings files, and an empty GameData `Assets.txt`. It applies none: the author confirms each before it goes in `removals`. `npm run propose-removals -- <blueprint.json>` does the same.

- A **Cinematic** (ADR 0009) is a shot list at `<mission>/cinematics/<id>.json`, listed in the Blueprint as `screenplay.script.cinematics: [{ id, scene }]` for a cued scene. Its `kind` is `"story"` (the default) or `"insert"`, for its length's norm (T4). It places `sets` (a Set's file, relative to the Mission's folder, at an `offset`), a `cast` standing on a set's `mark` or `at` a point with a `facing`, and `shots`. Each shot films a set camera (`"<set id>/<camera name>"`) or a camera of its own, and starts on a `line` (a sound ID: it cuts on that line's start, and carries it and the later lines no shot names) or `afterMs` after the shot before ends (a shot with no line, lasting its `pauseAfterMs`). `pauseAfterMs` holds a shot after its lines. Its `bookmarks` (`{ name, line | atMs }`) are named points a Mission's `cinematicBookmark` cue can play a scene from; prefer a `scenePlayed` cue, since a skip doesn't hear a bookmark (docs/reference/editor-and-engine.md, "A cutscene's events"). A shot with `intoLineMs` cuts that far into its line instead, the shot before (which has a line and no pause) carrying the line's start: a picture cut in the middle of a line. A shot's `to` moves its camera over the whole shot to another camera of its set, or to one of its own, easing out (`move: "linear"` keeps one speed); its `path` instead moves it through several, each `{ camera, atMs }` (the last may leave out `atMs` and arrive at the shot's end), smoothly by default (`move: "smooth"`, the Editor's Auto tangents: no kink at a key, at rest at the ends). A move animates the position, distance, pitch, yaw, roll (a camera's `roll`, 0 when left out), lens and focus, so two set cameras that differ in height offset or lens flag can't be joined by one, and a move to a camera of the shot's own keeps the set camera's. A shot's `shake` (`{ amplitude, hz, roll?, atMs?, ms? }`) jolts its camera's target up to `amplitude` cells, `hz` times a second, and its roll by up to `roll` degrees, over a stretch of the shot, on top of any move, with keys as Blizzard keys a shake by hand; a path key or shake past its shot's end fails the compile, and `check_workspace` warns of it. A cut inside a line past its line's end fails the compile; `check_workspace` warns of it, timed by the voice files it finds then (else the estimate). A shot through a camera of its own names the `set` it films: its camera, `to` and `lights` (a key, fill or rim of its own, `{ name, at, color, strength, range, shadows? }`, seen only in it, casting no shadows unless `shadows` is true) are in that set's frame. A shot's `light` switches the base Light on its cut with no blend, until another shot switches it; the Cinematic's `light` (else its first set's first Light) is the base Light at t=0 unless its first shot names one. It's written shot first, as Blizzard's story cutscenes are: a folder a shot (`s010 <shot name>`, in steps of 10) holding its camera and its own copy of each cast member and set piece it shows, alive only through that shot (a member on another set gets none); its lights in a top-level `LIGHTS` folder, a folder a shot; and at the top level only the Director, the lamps that light every shot and the pieces in every shot (the cinematography skill's BUILT-SETS.md, "How a compiled Cinematic is laid out"). Lines run back to back from the end of a 1 s fade in, timed by their voice files in `audioDir` (else 0.91 s + 0.39 s a word), on a ConversationDriver over the map's own conversation data; after the last shot it fades to black over 1 s and holds 2 s of black before its End Scene marker. Set pieces and lamps tied to set cameras show only in the shots through them (a camera of a shot's own on their set also sees the tied pieces, not the tied lamps, which are the cameras' rigs), and the rest of a set's only in the shots on that set (and those through a camera of their own with no `set`), so sets at their offsets don't light or show in each other's shots. A set piece loops its Stand, or its `anim` (at its `animSpeed`, written as the anim's `timeScale`, as a cast member's `animSpeed` and a shot's timed anim's `speed` are), at the length `data/model-anims.json` records for its model (a bare Stand when it isn't recorded, which leaves an animated model frozen); a piece `anim` its recorded model lacks is a problem in the set's file. A cast member's `facing` is degrees about z, the Editor's (x, y, z) (applied about the world axes, z then y then x), or `{ heading, pitch, roll }` in the ship's own frame (pitch nose up, roll about the nose, + right), which core converts, for a ship banked or nose down, and `teamColor` (`{ diffuse, emissive }`, 0-1 RGBA) paints it as a Set's pieces are painted. A shot's `moves` (`{ "<cast id>": [steps] }`) moves members through it: each step goes from where the last left the member to `to` (in its set's frame), scaling to `scale` (even, or (x, y, z) along the model's own axes) and fading to `opacity` (0-1, from the member's own `opacity`) where given, turning to its `facing` the short way round (degrees turn it about z and keep its tilt; a turn from or to an own-frame facing is keyed along the true turn, within a quarter of a degree, so a banked ship doesn't wobble), after holding `afterMs`, over `ms` (the last step may leave it out and take the rest of the shot), eased (it leaves at speed and settles, as a warp-in arrives) or `linear`; a member stays where its last step ends. They're property curves on the actor's position and rotation, as Blizzard's space cutscenes fly their ships. A step past its shot's end, or a timed anim starting there, fails the compile, and `check_workspace` warns of it. A camera keeps pace with a member moving at one speed by a `linear` move over the same distance. A cast member with a `speaker` says that speaker's lines: each plays on its actor (a conversation element with the line's sound, beside the driver's), and the model's Talk runs on a layer over its Stand while it speaks, blending in and out over 300 ms, each line taking the next Talk of the family. The Talks and Stand come from the model's animations in `data/model-anims.json`: its plain Talks ("Talk", "Talk 01") over Stand, else its B Talks over Stand B, else the family with the fewest other words over that family's Stand, unless the model's Model Guide marks a default family it has a Stand of, which it then stands and talks in (`docs/reference/model-guides.md`); a cast `anim` replaces the Stand and overrides a default. A speaker must have its model's animations recorded, and a speaker no cast member plays (a voice-over) is heard only. A shot's `anims` given a plain name (`{ "<cast id>": "<anim>" }`) runs that animation for a member through the shot, in place of its Stand and Talk; `{ "anim": "Birth", "atMs": 1500, "once": true }` starts it 1.5 s into the shot (the member's own anim until then) and plays it a single time, as a warp flash's Birth; its `priority` ranks it against the speaker's Talk playing at once (3, a Stand's, when left out; a Talk is 4, so above 4 plays over it; Blizzard writes a Birth at 7). A list of these, in time order, changes the member's anim several times in one shot, each running until the next. A timed anim replaces only the Stand: a speaker's Talk still plays over it on their lines. A shot's `enters` and `exits` (`{ "<cast id>": <ms into the shot> }`) bring a member into being and take it away (its lifetime), once each. A set piece with an `id` is timed the same way as `"<set id>/<piece id>"` in a shot's `enters`, `exits` and `moves`, whose steps may only fade and scale it. A cast member's `tint` (RGB, 1 for none) colours it as a piece's does. A shot light may be a `spot` (`{ rotation, hotspot, falloff }`) and take `steps` of its `strength`, timed as moves are, keyed on its diffuse and specular multipliers together: a warp flash. A camera's `shadowDistance` (a set camera's or a shot's own) sets how far from the eye shadows are drawn, 75 cells by default. A shot's `hide` (cast ids) leaves those members out of it (no copy): a camera of a shot's own shows every cast member on its set, so a character cast on two marks would otherwise show twice. A shot's `feed` puts live pictures on a set's display by render-to-texture: a set camera (`"<set id>/<camera name>"`), filmed through a rig whose own camera stands at its eye, with that set's pieces, cast and lamps copied into the shot, or a cast member whose model has a camera of its own (a portrait), on RTT `channel` 0 unless given (the cinematography skill's BUILT-SETS.md, "A display's live picture"). A cast member given both a `mark` and `at` is the mark's character starting at the point (with its `facing`), as one who walks onto the mark. Its `lookAts` (`[{ at, line?, atMs?, type?, point? }]`, in time order, each until the next) turn its head to another member, by cast id or as `"<set id>/<mark>"` for the one cast there, from a line's start or `atMs` into the Cinematic, as the Editor's look-at `type` (`SlowHeadOnly` when left out) aimed at the other's attach `point` (`Head`); without them a member on a mark takes its set's mark `lookAt` all through, at whoever stands on the other mark. A set lamp's `attach` (`{ mark, point, offset?, rotation? }`) rides the one cast on that mark at their attach point, so it follows them; with no one there it stands where the set puts it. The Cinematic's `sounds` (`[{ sound, line?, atMs?, untilLine?, untilMs?, fadeOutMs?, fromMs?, volume?, loop? }]`) play Sounds besides the lines, a music cue or a stinger, from a line's start or `atMs` (its start when neither) to a line's start (`untilLine`) or `untilMs` (the end when neither), fading out over `fadeOutMs` before it, once or looping, `fromMs` into their file, at `volume` (the Editor's volumeScale); an end at or before its start, or past the end, fails the compile, and `check_workspace` warns of it. Each of its sets' `sounds`, its ambience, loops through the shots on that set (and those of no `set`), from each cut to it to the cut away, fading out over 250 ms before it; a run of such shots plays one loop, and a set in every shot loops it all through. Its scene's cues play it in place of the scene's Transmissions, LotV's way: AI time paused (unless it already was), Story Mode and Cinematic Mode on, the map's environment hidden and, as hand-made campaign cutscenes do, its units paused and hidden (they would show through a set's windows), the cutscene in a full-screen HDR dialog, and a skippable wait for its end. One cleanup follows a skip or the natural end: it stops the cutscene, unpauses AI time if it paused it, shows the environment again, unpauses and shows the units it paused and hid, sets the mission Light back, destroys the dialog and turns both modes off. Then the scenes cued after it play, in order. A Cinematic at mission start also holds the goal timers, which run on game time, until it and the scenes after it have played. These are NativeLib GUI triggers, "Cinematic <Id>" and "Cinematic <Id> Watch" (`packages/core/src/triggers/cinematic-triggers.ts`). `compile_cutscene` with `play` loops one from map start only when its scene isn't cued at mission start; one that is already plays there from its cue.
- A **trigger scene** (ADR 0012, ADR 0013) is a shot list on the Mission's own map at `<mission>/trigger-scenes/<id>.json`, listed in the Blueprint as `screenplay.script.triggerScenes: [{ id, scene }]` for a cued scene that has no Cinematic. Its scene's cues play it in place of the scene's bare Transmissions. Each of its `shots` cuts to a camera Anchor (`camera`; no cut when the shot before ended on it) and may move over the whole shot to another (`to`), eased (velocity −1, decelerate 10) unless `move: "linear"`. A shot's camera may be aimed at a unit in place of its Anchor's own target, with the Anchor's values (distance, pitch, yaw, field of view): `unit` aims `camera`, and `toUnit` aims the move's end (with `to`'s values, or `camera`'s when there's no `to`), so the camera eases to the unit as between Anchors. The unit is a unit Anchor's (`{ "anchorId": "sergeant" }`, which may be a Wave's unit bound by its entry's `anchorId`, ADR 0008) or `"cue"`, the unit the scene's cue keeps, which the scene takes as it starts: the unit an `anchorNears` cue came near, or the unit an `effectStarts` cue's data effect struck (its caster for an effect on a point; docs/screenplay-format.md); it compiles to Apply Camera Object without the object's target and a Pan Camera to the unit's position over the same time, to where the unit is as it's aimed (the camera doesn't follow it). A shot starts on a `line` (a sound ID of the scene; it carries that line and the later ones no shot names) or `afterMs` after the shot before, and holds `pauseAfterMs` after its lines, as a Cinematic's shots do; a move lasts its shot, timed by the voice files in `audioDir` (else the estimate), while the lines themselves play as the scene's Transmissions, waited, with portraits. It compiles to the four triggers of the cinematography skill's RECIPES.md "Trigger scene": "Trigger Scene <Id> Setup" (under black: Cinematic Mode at full screen, AI time paused unless it was, the camera locked and saved), "... Cinematic" (the first cut, the skippable begin, a 1.5 s fade in, the shots), "... Cinematic End" (a fade out over 2.0 s, or 0.5 s after a skip) and "... Cleanup" (its own line still playing cut off, and no other transmission, the camera unlocked, AI time back, then the `handback.camera` Anchor, else the camera the player had, with the fade in and Cinematic Mode off, all over 1.5 s, or 1.0 s after a skip). It starts the moment its cue fires, never waiting for an in-play line, since it may frame a moment in play (ADR 0013): its Setup cuts off only the in-play script line playing, and no in-play line starts until the scene has handed back, or until its last line after the handback has played. The cut line then plays again from its start, followed by the rest of its cue's lines. On one cue, a trigger scene straight after a Cinematic shares its skip: a skip in the Cinematic goes straight to the trigger scene's cleanup, and the Cinematic leaves the screen black, Cinematic Mode on and the music paused for that handback. A trigger scene at mission start holds the goal timers until it hands back. Its `music` (RECIPES.md "Music") says what the mission music does, `mission: "pause"` (the default: paused with a fade in Setup, unpaused by the cleanup) or `"keep"` (it plays on, lowered under the lines in Speech mode, with Game mode back at the handback), and lists `cues`: Music Sounds (CSound ids, not Soundtracks) played once from an in-point (`fromMs`), starting on a `line` or `atMs` after the first cut, at `volume` (0-1), fading from `untilMs` after the first cut over `fadeOutMs` (stepped down every 250 ms or so; the engine's fade without it). A cue over kept music dips it (pauses it with a fade). The cleanup stops every cue with a fade and brings the mission music back, skipped or watched (M4); `check_workspace` warns of a cue that isn't a Music Sound our maps load (M1, `packages/core/data/music-sounds.json`, from the music catalogue) or still plays when the scene ends (M4). Its `cast` stages units of its own (O3): each `{ id, unitType, player, count?, at, facing? }` is created in Setup under black, `count` of them (1 when left out) for `player`, `at` a point Anchor or an `{ x, y }`, facing `facing` degrees (270 when left out), and removed in Cleanup, skipped or watched. Its `speakers` (`{ "<SPEAKER>": "<cast id>" }`) has a speaker speak from a staged unit, as a holo-projector carries a voice: each of that speaker's lines in the shots plays as a Transmission from the first unit of the cast group (Transmission Source From Unit, its flash on the unit, and the unit's own portrait on the left if its type has one, as a `speakerAnchors` unit's, so a prop with none shows none), in place of the speaker's `speakerAnchors` unit or character; a speaker is matched as `speakerAnchors` match one, ignoring case and extra spaces. A shot's `orders` (`[{ cast | units | player + inZone, moveTo, atMs?, withdraw? }]`) send a staged unit's group (`cast`), live unit Anchors (`units`), or a player's units in a Zone (`player` and `inZone`, a Zone or Kept region: every unit of theirs there that isn't a structure or the staged cast, gathered at the order, as a warp-out gathers an army) to a point Anchor or `{ x, y }` at the shot's cut, or `atMs` after it on a thread of its own, given only while its shots still play (never in the fade out after a skip); with `withdraw`, each is removed on coming within 2 cells of it (a Zone's units already that near at once), and a unit a later order takes leaves the withdrawal, so it isn't removed on its new way. Whatever a skip cuts short lands in Cleanup on both paths: each live unit walked is put at its last order's place at once (several that end at one place on a ring round it, a cell or more apart), and each that withdraws is removed wherever it is. Zone orders settle in Cleanup at their own moment in the scene's order, with its warps, actor events and unit changes (after the live units have landed): one skipped before it was given has Cleanup gather the units in the Zone then, with what came before it in place and nothing after it (so a later warp-in or owner change neither adds to nor takes from it), leaving out those a later order takes, so each unit ends as its last order leaves it; its units that don't withdraw land at its place, told to stay there, on a spiral out from any ring there that every Zone order to that place carries on. Its `marks` (`[{ unit, at, facing? }]`) move live unit Anchors, those still alive, at once to a place in Setup under black, faced `facing` degrees if given, before the skip's branch, so a scene skipped from the Cinematic before it lands them too. Its `live` (`[{ unit, hide?, pause? }]`) names unit Anchors it films that are hidden or paused in Setup and put back in Cleanup, leaving a unit the mission had hidden or paused already as it was, as a Cinematic's groups do. Its `builds` (`[{ warpIn | unit, unitType, ability, at, atMs? }]`) order the first unit of a warp-in, or a live unit Anchor, to build `unitType` at a point with the first command of its build ability (such as `ProtossBuild` for a Nexus), wait for the builder to go idle (a Probe at once; an SCV only once it has built it) and set the structure to 100%; if a skip came first or nothing was placed, Cleanup cancels the order and creates the structure finished, or finishes the one placed. Its `warpOuts` (`[{ units | player, except?, atMs? }]`) pause live unit Anchors, or every unit of a player's that isn't a structure, the scene's staged cast (which goes only by a `withdraw` or the Cleanup) or a unit Anchor in `except` (heroes who stay as the army is recalled), give them the warp effect and remove them 1.7 game seconds later; Cleanup removes them on both paths (an army only as the warp-out took it, so later units stay, and those in `except` stay too). Cleanup puts these final states in place in the order they happen in the scene. A shot's `actorEvents` (`[{ unit | cast, messages?, effects?, atMs? }]`) send actor messages as the Editor writes them ("ModelSwap <model> 0", "Signal <name>") to a live unit Anchor's actor (`unit`), or to every unit of a staged unit's group (`cast`), at the cut or `atMs` after it, `messages` before `effects`, with Send Actor Message To Unit: `messages` leave a state the unit keeps, which Cleanup sends, in the scene's order, to a unit still alive when a skip came first; `effects` (a flash) play once and are never replayed. The staged cast is removed in Cleanup, so an actor event on it sends `effects` only. - A trigger scene's **handback** has variants (cinematography H3, H4, T6). `handback.linesFrom` names the first of the scene's lines played after the handback: the shots carry the lines before it, and it and the rest play from "Trigger Scene <Id> Lines" as waited Transmissions, one after another, once Cinematic Mode is off and control is back, skipped or not. They play while the scene still holds the Mission's lines, so no in-play line cuts in. Another trigger scene that starts among them cuts off the one playing, which plays again once that scene has handed back (ADR 0013). `handback.fade: false` hands back with no fade and leaves the camera where the last shot left it, Cinematic Mode going off over the 1.5 s (an intended H3 exception); after a skip it fades as any scene does and lands on the last shot's camera. `handback.ping` pings unit Anchors on the minimap, and `handback.objective` issues one of the Blueprint's objectives, created hidden at mission start and shown straight after the handback. A run of Cinematics and trigger scenes back to back on a cue holds the Mission's clocks, the goal timers and the timers a Mechanic declares in its `clocks`, from before its first scene until its last hands back ("Clocks Hold", "Clocks Release"; only the ones not already paused). Trigger scenes chain as a Cinematic does: one straight before another on a cue hands on to it under black and shares its skip, and a scene hands back (its `handback`) only where it plays last; one that only ever hands on may not declare one, and one that hands on anywhere may not declare pings, an objective or `linesFrom`. A `fade: false` scene still fades out where it hands on. The chain's first scene saves the player's camera, and a later one keeps that save. A `scenePlayed` cue on a trigger scene's scene ([docs/screenplay-format.md](docs/screenplay-format.md)) fires once it has handed back, and on a scene that hands on, once the chain's last scene has; the lines after the handback (`linesFrom`) play on without holding it up. An entry `after` a trigger scene's entry waits on the same handback; a trigger scene's own entry with an `after` plays apart from the run on its cue, so none hands on to it and it hands back.
- A trigger scene may **open with no fade** (`open: { "fade": false, "easeMs": 1000 }`), for a short scene on a moment in play the player must keep watching, where black would hide what it shows, such as a strike's landing marker in a fight. Setup goes to no black. Cinematic Mode comes on over the ease, the camera is locked and saved as for any scene, and the first shot's camera is reached by an eased pan from the player's camera over `easeMs` (1000 when left out), in place of the cut and the fade in. The skip begins with the ease, so a skip during it goes to the cleanup as any skip does. The shot's move and its lines start once the ease ends, and what it gives at its cut (orders, actor events, unit changes, warps) happens in sight, as at any later cut. With `handback.fade: false` the scene has no black at either end. Setup's changes under black would happen in sight, so `check_workspace` refuses `open.fade: false` beside a `cast`, `marks`, a `live` unit it hides (one it only pauses is fine), `light`, `fog` or `mask`. It also refuses it on a scene a cue plays straight after a Cinematic or another trigger scene, which opens on that scene's black. The first scene of a chain may open with no fade. A scene that teaches the map, or stages anything, opens from black.
- A trigger scene with `"outro": "victory"` is a **victory outro**: played on a victory outcome's cue, last on it and with no delay, it ends the game instead of handing back. Its cleanup leaves the screen black after the fade out (2.0 s, or 0.5 s after a skip), with Cinematic Mode on, and the cue's trigger ends the game in victory straight after it, the Mechanics' victory actions having run first, with no death pause. It has no `handback`, and the compile refuses one cued anywhere else. Its T4 budget is `TRIGGER_SCENE_OUTRO_LENGTH` (about 25 s, warn over 45).
- A victory outro with no Screenplay scene, such as a closing shot with no lines, is listed by its outcome in place of a scene: `triggerScenes: [{ "id": "victory", "outcome": "victory" }]`, with no `script.cues` entry. It plays on every victory condition, last in that condition's run of scenes, as if cued there: a Cinematic or trigger scene cued last on the condition hands on to it (one skip, one fade to black, its cleanup leaving the screen black for the outro), so that scene declares no `handback` of its own, and the clocks are held once for the whole run. The first victory condition met plays it; one met while it plays starts nothing. Its T4 budget is a victory outro's, with no handback in its length. Its shots give no `line` (it has no scene, so the check refuses one, as it does `music.cues` lines and `speakers`), it must declare `"outro": "victory"`, and the Blueprint needs a victory condition. At most one trigger scene is listed by outcome, and none beside it may be a cued victory outro (`check_workspace` reports one). `outcome` takes only `"victory"`.
- **Armed from a Beat:** a victory or defeat condition, an objective's `completeWhen` or an encounter (docs/screenplay-format.md) with `fromBeat` (`{ "type": "anchorEntersZone", "anchorId": "hero_scout", "zoneId": "archives", "fromBeat": "archives" }`) does nothing until that Beat has started. Its trigger, "<event> From <Beat>" for a condition, is off from map start. "Beat - <title> Arms" turns it on, once, and runs it at once if what it waits for already holds: the Anchor's unit dead, alive in the Zone's region, or player 1's (a Wave's unit only once its send has created it), or the quota collected. An encounter armed so starts its attackers at the Anchor's unit, or the first of the player's units in its zone; one that starts on the Anchor's unit dying has "Encounter Death - <zone>", on from map start, which keeps where the unit died and runs the encounter if it's armed, since the unit may be gone by the time a Beat arms it. So an event before the Beat counts if it still holds then: a unit that entered the Zone and left again must come back. The Beat's trigger runs its Arms after its own Cinematics, trigger scenes and pings, so a condition already met isn't met over them (its Transmissions, on its Lines trigger, don't hold it up), and every later Beat's trigger runs it too if that Beat never started, so a Beat the mission skips still arms what waits for it, while one still playing its scenes as a later Beat starts arms its own after them (`beat_<id>_started`). The same event without `fromBeat`, or from another Beat, is a condition of its own with a trigger of its own: a cue on it (cues take no `fromBeat`) plays from map start, and an objective that completes with the victory needs the same `fromBeat`. So a victory outro cued by scene can't end a victory armed from a Beat: list it by its outcome. The compile refuses any other scene cued on the event of a victory or defeat armed from a Beat, which would play apart from it and race the game's end: cue it on the Beat's start or something else. `check_workspace` refuses a `fromBeat` naming no Beat, the first Beat (which starts with the mission), or a Beat with no `startsWhen`, which never starts in the map, and refuses one on a `timer`, which counts down from mission start.
- **Objectives complete:** `{ "type": "objectivesComplete", "objectiveIds": ["collect_junctions", "recover_warp_drive", "deliver_scv", "arm_silo"], "count": 3 }` holds once those Objectives, all of them or `count` of them, are marked Completed, in any order. It is a Beat's `startsWhen`, a victory or defeat condition or a cue (a scene can play at 1, 2 and 3 of 4 done). Each named Objective needs its own `completeWhen`, which is what marks it Completed (a Kept trigger that completes one isn't counted), and the condition can't itself be an Objective's `completeWhen`. The Objective's trigger counts: the first time it completes the Objective it sets `done_objective_<id>` and adds one to the count of each condition that names it (`objectives_complete_<n>_count`), then runs that condition's trigger, "All Of <ids> Complete" or "<count> Of <ids> Complete", which holds only at its own count, so it fires once. The same Objectives in another order, or a `count` of all of them, are the one condition. That trigger has no event: it runs the victory, defeat, objectives, Beat starts (each only while the Beat's trigger is on) and scenes cued on it. The Objective's own cued scenes play after the condition's, which the count runs first. `"exactly": true` (no `count`) holds when the Completed Objectives are exactly the ones named: all of them are, and no other Objective with a `completeWhen` is yet. It needs no count: each named Objective's completion runs it, and only the last of them finds it so. A cue on it plays a scene part by which Objectives are done, as a Mission plays "warp drive and SCV, no junctions" for the Objectives above (one cue entry per part, `from` its stage direction). It takes no `fromBeat`; the Objectives' own `fromBeat` already holds them back. `check_workspace` refuses an unknown or repeated Objective, one with no `completeWhen`, and a `count` past the Objectives named.
- `import_set` imports a set from the cinematic set catalog into the Mission as data, at `<mission>/sets/<set id>.json`, as `npm run import-set` does: its pieces (model, transform, variation, tint, team colour), marks, named cameras (orbit cameras, and target cameras converted to orbit values), base Lights, lamps (one attached to a character as attached to its mark), each mark's look-at at another mark, and its ambience (each Sound looping all through the file; other Sounds are left out as cues for a Cinematic's `sounds`), in the set's own frame (its pieces' centre, snapped to an 8-cell grid), with the source file, catalog name and set id. It reads the `sources` folders as the catalog does and takes the set's richest occurrence there, or the one `file` names. A camera rigged to an invisible actor is read at its own position; a moving camera (keys, or a moving rig) is read at its start and marked `moves`. The reply lists what was left out.
- `get_session_state` reports which Co-design Stage a Mission is at and which Stages the author has signed off, or every Mission's when none is named. `sign_off_stage` records the author's sign-off of the current Stage and is the only way to advance: it refuses any other Stage, so Stages can't be skipped or signed off twice. `reopen_stage` takes a Mission back to an earlier, signed-off Stage when the author asks, as when its design is redone, with a note saying why: that Stage and every later one must be signed off again. The sign-offs it takes away leave `signedOff` and are kept, superseded, in the `reopened` list (`{ stage, at, note, superseded }`) of `co-design-history.json` beside the record, a file of its own so that a core from before reopening still reads `co-design.json`. `get_session_state` reports the history too; its text gives the latest reopening and counts the rest, with dates in the author's time zone. The history is checked against what stands from the record alone, never from its times, which two machines' clocks needn't agree on: a sign-off superseded twice or still standing after it was superseded, or fewer Stages standing than a reopening left, is refused, as a record merged by hand from two branches may be. `reopen_stage` refuses the Stage the Mission is at and a Stage not reached; a sign-off of a Stage already signed off points to it. The record is `co-design.json` in the Mission's folder, so commit it, and its history once there is one, with the Blueprint. A Mission without one is at Stage 1.
- The build tools (`compile_map`, `test_mission`, `check_layout`, `preview`, the edit tools and the ones above) end their reply with a `Next (Stage n): …` line suited to the Mission's Stage.

Each Plugin's knowledge is served as MCP resources at `sc2-adjutant://plugins/<plugin>/knowledge/<id>`: its own documents, then `exemplar-maps` (its list of Exemplar Maps), `study-<id>` (each studied map's Map Study) and `composites`. Its prompts are served as MCP prompts. A prompt name is unique across the loaded Plugins.

Each call rereads the Workspace config and Plugin manifests, so config edits apply on the next call, and a Plugin that can't be loaded (such as one built for another `pluginApi`) fails the call with the reason. Plugin code is imported once, so restart the server after editing it. The machine config and Host Adapter are read once, at start. The `compile-map`, `import-map`, `import-mod`, `compile-mod`, `convert-entries`, `convert-files`, `convert-assets`, `convert-library`, `convert-screenplay`, `convert-triggers`, `kept-report`, `propose-removals`, `edit-kept`, `edit-terrain`, `tune-kept`, `survey`, `compile-melee-map`, `check-layout`, `check-workspace`, `tts`, `generate-terrain`, `sync`, `compile-cutscene`, `import-set`, `capture-composite` and `freeze-set-piece` CLIs run the same functions as these tools.

The cinematic set catalog (`npm run catalog-sets -- --source <kind>=<dir> ... --out <dir>`) reads each folder as a cutscene source kind: `blizzard` for Blizzard's game data, or a kind a Plugin contributes, such as one a Campaign Pack adds for its Campaign's actor-name conventions. A Plugin's kinds come from the Workspace `--workspace <dir>` names, or else the one the command is run in. To use a kind the root Workspace doesn't load, run it as `npm run catalog-sets -- --workspace <your Workspace> …`. `npm run import-set -- --mission <id> --source <kind>=<dir> ... "<set name>" [--file <file>]` takes the same sources and Workspace. Core's catalog (`packages/core/data/cinematic-sets`) is Blizzard's sets alone. A Workspace keeps its own in its `cinematic-sets/` folder: read its Campaign's files with Blizzard's, and write it with `--private`, which keeps only the sets with a file that isn't Blizzard's.

## Machine config and Host Adapter

Each author's machine settings live outside the Workspace, in `machine.json` in the user's sc2-adjutant config folder. Its settings and their env vars are in [core's README](./packages/core/README.md#the-machine-config), and each Host Adapter's setup, with an example `machine.json`, is in its own README: [macOS](./packages/plugin-host-macos/README.md) and [Windows](./packages/plugin-host-windows/README.md). What a Host Adapter's capabilities take and return is in [the plugin API](./docs/plugin-api.md#host-adapter-kinds), and the Editor and game behaviour each one relies on is in [macos-host.md](./packages/plugin-host-macos/docs/macos-host.md) and [windows-host.md](./packages/plugin-host-windows/docs/windows-host.md).

From a checkout, these bulk jobs with no manual form run only on a host that has their capability, and otherwise stop with the capability they need:

- `npm run thumbnails` (`model.render`) renders Asset Catalog thumbnails into `packages/core/data/thumbnails/`, then `npm run catalog-sheets` (ImageMagick `montage`) makes the reference sheets in `packages/core/data/catalog-sheets/` that the catalogs' `sheet` fields name. Both are rendered game assets, so they're generated on each author's machine and git-ignored.
- `npm run model-anims -- [--mod <SC2Mod folder>]... <model id>...` (`model.export`) records models' animations in `packages/core/data/model-anims.json`, filling in the path templates the game fills in and reading a model with variations from its first numbered file (`<name>_00.m3`). Each `--mod` adds an unpacked mod's own CModels after the game's; a model whose file the mod holds (in its `Base.SC2Assets`) is read from there with its RequiredAnims, no `model.export` needed. A Campaign's cast: `--mod <Assets>.SC2Mod --mod <Campaign>.SC2Mod`.
- `npm run model-footprints -- [--mod <SC2Mod folder>]... <model id>...` (`model.export`) records models' bounds and materials in `packages/core/data/model-footprints.json`, found as `model-anims` finds them. With `--print` it (and `model-anims`, which takes the same arguments) only reads and prints, writing no catalog, and also takes doodad ids (through `packages/core/data/doodad-models.json`) and `--variation <n>`; footprints print as w × d × h, the model's x × y × z. `check_workspace` warns, in a Set's file, on flat pieces that overlap at one height (they z-fight) and on overlapping see-through decals of one model whose tint, variation or rotation differ (they re-sort every frame); how it reads flat and see-through from the footprints is in `packages/core/src/cutscene/set-checks.ts`.
- `npm run capture-exemplars -- [--places] [id ...]` (the MCP tool `capture_exemplar` from the command line, on the active Style Pack) and `npm run capture-sets -- <manifest.json> <out dir>` (`editor.captureTour`) capture Exemplar Map tours and the cinematic-set contact sheet. Capture copies go in `<cacheDir>/capture/maps/`, the only folder whose documents a capture closes unsaved.
- `npm run capture-edit -- <blueprint.json> <edit.json>... [--name <folder>] [--lighting <id>]` (`editor.captureTour`) looks at edited Kept ground in game, when the author asks or at the end of a batch of `edit-terrain` edits. Each edit file is what `edit-terrain` took, a bare area, or a list of either. A ramp edit shows its footprint, and a slot swap, which changes the whole map, needs an area instead. A batch runs in one game. Each area gets one high view framing everything the edit may change, then two or three views at the player's angle. The summary names any view that shows only part of its ground. The tour runs on a capture copy of the Mission's Map Package, which is only read. The copy is removed once the tour is done, and kept when it stopped early. Frames go to the research archive under `missions/<id>/captures/<name>/`, as `<stop>-<view>.jpg`, with `views.json` saying what each frame shows. A host without `editor.captureTour` is refused. The camera rules are in [editor-and-engine.md](docs/reference/editor-and-engine.md#camera-tours-of-an-edited-area).
- `npm run capture-shots -- <blueprint.json | Map.SC2Map> <shots.json> [--name <folder>] [--lighting <id>]` (`editor.captureTour`), and the MCP tool `capture_shots`, capture one in-game frame per Shot, a rectangle of the map in cells, into `missions/<id>/output/shots/<name>/` for a Mission or `<cacheDir>/shots/<name>/` for any other map, with `shots.json`. `npm run capture-shots -- --status` prints the Editor Broker's status. Every capture above runs through the broker, one at a time ([macos-host.md](packages/plugin-host-macos/docs/macos-host.md#the-editor-broker-one-editor-job-at-a-time)); how to choose Shots is in [game-testing.md](docs/reference/game-testing.md#getting-in-game-screenshots-of-a-map-capture_shots).

## Research archive

Material that git ignores but is worth keeping goes in a research archive, a folder of your own outside this repo (ours is a private repo): research notes and the Blizzard data downloads behind them, full-size exemplar captures, built maps and thumbnails. Point `SC2_RESEARCH_DIR` at it: there is no default, and the tools that need the archive stop with an error when it isn't set. Its layout mirrors this repo's, with the research notes under `$SC2_RESEARCH_DIR/docs/research/`.

With `SC2_RESEARCH_DIR` set, `npm run capture-exemplars` and `capture_exemplar` write full-size captures and their 1000px frames straight into the archive, under `docs/research/exemplar-maps/` there (where the Exemplar Maps lived before they moved into the Style Pack), and `make-frames.sh`, `find_places` and `mixtures.mjs` read them from there; without it they use the Style Pack's own `exemplar-maps/`. The Style Pack holds no screenshots: the repo ignores any `captures/`, `frames/` or `evidence/` folder under its Exemplar Maps. `npm run capture-edit` writes its frames there under `missions/<id>/captures/`. The research notes cite downloads by their path there. Before removing a worktree, copy anything it holds under an ignored path into the archive and commit it there (`git -C <worktree> ls-files -o -i --exclude-standard --directory` lists those paths).
