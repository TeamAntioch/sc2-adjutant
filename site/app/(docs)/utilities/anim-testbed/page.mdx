# Anim Testbed

Picking a unit's sounds means hearing them with its animation: the grunt at the top of the wind-up, the
whoosh on the swing, the hit as it lands. The Anim Testbed builds a test map for that from one **spec**.
The map shows a dialog where you pick a unit, a moment of its life (an attack, an impact, a death) and
a variation to try, and play it. Each variation is a timeline: the animation, the sounds, the effects,
each at its time.

## Using it

A Workspace made by `/sc2-adjutant:init` has it already. Claude reaches for its `anim-testbed` skill
when you work on a custom unit, custom sounds or a custom animation, or ask for a test map ("audition
the Marine's attack and death sounds"). You can also write a spec yourself and build it. The spec's `base` is the Mission's Map
Package, so compile the Mission once first if it has never been compiled:

```sh
npm run compile-map -- missions/<id>/blueprint.json
node node_modules/@team-antioch/sc2-adjutant-anim-testbed/dist/testbed.js missions/<id>/tests/<name>.json
```

Unless the spec says otherwise in `out`, the map is written beside the base map, in the Mission's
git-ignored `output/`. Open it in the Editor and run Test Document.

### If your Workspace doesn't have it

A Workspace made before the testbed shipped needs the package beside sc2-adjutant, and the testbed
listed in its config's `utilities`:

```sh
npm install @team-antioch/sc2-adjutant-anim-testbed
```

```json
{ "utilities": ["bundled:anim-testbed"] }
```

Its skill arrives at the next Claude Code session.

## The dialog

- **Unit**, **Moment** and **Variation** pick what plays. Changing the unit keeps the moment, so you
  can compare one moment across units. Each variation is tagged with what it holds (anim, sound,
  visual), and `*` marks the one the spec recommends. A moment with one variation shows no Variation
  dropdown.
- The **timeline** has a row per element: its name, and a bar to scale. An animation's bar is its
  length, with gold ticks at its strike and land so you can line sounds up by eye. A sound's bar is
  its real length. A stop cuts the bar there and shows the rest dim.
- **Play** plays the variation's timeline: a playhead crosses the bars, and each bar lights as it
  fires. **Stop** cuts it off, and **Loop** replays it.
- **Tune** it in the game: click a row's name, then step its start and stop by 0.05 s, or untick its
  box to mute it. A changed value turns gold, and **Reset** puts it back. **Reset all**, pressed
  twice, puts every element back.
- The game's own UI is hidden to leave the dialog room: **Menu** opens the game menu.
- **Send** plays any CSound at the unit, or sends any actor message to it.

Every change is saved at once in a bank named after the spec, so quitting loses nothing and the next
game starts where you left off. When you're done, `testbed.js <spec> --apply` writes the new times
and mutes into the spec, keeping its comments and layout, and skips any the spec has changed since.
Forgot to apply? Run it later; the bank keeps the changes until then. A running game never sees a
bank changed outside it, so tuning only goes from the game to the spec: anything beyond start, stop
and mute is a spec edit and a rebuild.

A **moment** is something that happens to a unit that you want to judge: an attack, its impact, a
death, a voice line. It's only a name. What happens is in each variation: a timeline of **elements**,
each at a time in seconds from Play.

keeping it in the spec.

## The spec

A spec is JSON. This one is cut down from the package's example (`examples/stock-units.json`), which
builds on the example Campaign's Mission:

```json
{
  "name": "StockUnits",
  "base": "../Ashfall-Relay.SC2Map",
  "out": "../output/StockUnits.SC2Map",
  "stage": { "at": [36, 22], "gap": 4, "facing": 270 },
  "target": { "unit": "Zergling", "player": 1 },
  "moments": ["attack", "impact", "death"],
  "units": [
    {
      "key": "marine",
      "unit": "Marine",
      "reach": 3,
      "animations": {
        "attack": { "play": "AnimPlay Attack Attack NonLooping", "strike": 0.1, "land": 0.15 }
      },
      "moments": {
        "attack": { "variations": [
          { "elements": [
              { "anim": "attack", "at": 0 },
              { "sound": "Marine_AttackLaunch", "at": 0.1 }
            ], "note": "the Marine's own rifle burst", "pick": true },
          { "elements": [
              { "anim": "attack", "at": 0 },
              { "sound": "Marine_Stimpack", "at": 0, "stop": 0.6 },
              { "sound": "Marine_AttackLaunch", "at": 0.15 }
            ], "note": "a stim grunt, cut off at 0.6 s, then the burst" }
        ] },
        "impact": { "variations": [
          { "elements": [
              { "anim": "attack", "at": 0 },
              { "sound": "Marine_AttackImpact", "at": 0.15, "on": "target" }
            ], "note": "the Marine's own bullet hits" }
        ] },
        "death": { "variations": [
          { "elements": [
              { "kill": true, "at": 0 },
              { "sound": "Marine_Death", "at": 0 },
              { "sound": "Marine_Death_BodyFall_A", "at": 1.0 }
            ], "note": "the death and a body fall" }
        ] }
      }
    }
  ]
}
```

`moments` sets the dropdown's order; left out, it's the order the units first name them.

Actor and effect elements bring visuals into the test as well as sounds:
`{ "actor": "Create MyStumpBurst", "at": 0.1 }`, then `{ "actor": "Destroy", "on": "MyStumpBurst", "at": 2.1 }`,
or `{ "effect": "PunisherGrenadesLM", "at": 0.2 }`. An effect's damage is real, so it can kill the
target, which comes back after 2 seconds.

**A unit** is a stock CUnit (`"unit": "Marine"`) or a model of your own (`"new"`, with its `.m3`, its
`.m3a` files and its texture folders). The build copies a model of your own into the test map and adds
its unit. Its **animations** are named (`"attack"`, `"flinch"`), each with its strike, land and
length, and its **moments** list the variations to compare. Each variation picks its own animation
elements, so two animations are compared like two sounds. Private files, such as sounds extracted from the game, are named through `roots`, so no
machine path goes into the spec, and they're copied into the test map only.

The package's [README](https://github.com/TeamAntioch/sc2-adjutant/tree/main/packages/plugin-anim-testbed#the-spec)
lists every key.

## What it checks

To prevent silent failures on missing assets, the build checks to make sure that they're present.
`--check` stops there:

- **Sounds, models and units** against the game's own packages, the Workspace's mods, the base map,
  and the spec's own data.
- **Animations.** Where the build knows the model's clips, read from its `.m3` and `.m3a` files or
  from recorded model animations, each `AnimPlay` must match one of them. Where it doesn't, as for
  most stock units, it checks each word against SC2's animation words and warns about one that isn't:
  an invented word never plays. A clip named `Attack Mega` didn't, and `Spell C` did.
- **Actors and effects** that the spec's own data defines. sc2-adjutant can't list the game's actors
  or effects, so one outside the spec and the Workspace is only a warning.

## Screenshots of your own

`--capture <folder>` builds the map with the spec's `tour` and films it through the Editor, one frame
per stop. That's how the pictures on this page were made, through the macOS Host Adapter. It needs a
Host Adapter that can capture.
