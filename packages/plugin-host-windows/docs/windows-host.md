# Windows Host

How the mapper drives the StarCraft II Editor and game on Windows: the facts behind the Windows Host Adapter, `bundled:host-windows` (`packages/plugin-host-windows/`). How to install it and which capabilities it has are in the package's [README](../README.md), what each capability takes and returns is in [the plugin API](../../../docs/plugin-api.md#host-adapter-kinds), and the machine config is in [core's README](../../core/README.md#the-machine-config). This doc is what the adapter's code relies on, and what an author or assistant needs when doing the same by hand. The plan and the spikes behind it are spec #727. Everything here was seen on SC2 build 98310, in a Parallels Windows 11 ARM64 VM, between 2026-11-14 and 2026-11-18.

The adapter has `editor.open`, `editor.checkClosed`, `editor.testDocument`, `editor.save`, `editor.captureTour`, `editor.closeCaptureCopies`, `game.banksDir`, `game.launch`, `screen.capture`, `tts.speak`, `model.render`, `model.rendererKey`, `model.export` and `model.exportGltf`. The [macOS host](../../plugin-host-macos/docs/macos-host.md) has the facts the two platforms share: the Editor Broker, banks, the Custom Script the Editor keeps.

## Setup

`machine.json` lives in `%APPDATA%\sc2-adjutant\`. The adapter reads four of its paths:

- **`editorPath`**: the 32-bit Editor, `<install>\Support\SC2Editor.exe` (`C:\Program Files (x86)\StarCraft II\Support\SC2Editor.exe` by default). Not `Support64\SC2Editor_x64.exe`: under ARM emulation it hangs at startup, two threads spinning and no window. On x64 hardware the 64-bit Editor is untested.
- **`sc2Path`**: the install folder, `C:\Program Files (x86)\StarCraft II` by default. `game.launch` runs its `Support\SC2Switcher.exe`.
- **`cacheDir`**: where the adapter builds its helpers, `<cacheDir>\host-windows\bin\`, and keeps the model viewer's worker copies, `<cacheDir>\whiteoutflakes\`. Any folder outside the Workspace, such as `~/AppData/Local/sc2-adjutant`. Without it, the helpers are built in the system temp folder (`%TEMP%\sc2-adjutant`), so the open check before a compile still works; the viewer needs it.
- **`modelViewerPath`**: the WhiteoutFlakes viewer that `scripts\build-whiteoutflakes.ps1` builds, `<dir>\stage-<arch>\WhiteoutFlakes.exe` ([Rendering and exporting models](#rendering-and-exporting-models)).

```json
{
  "hostAdapter": "bundled:host-windows",
  "editorPath": "C:\\Program Files (x86)\\StarCraft II\\Support\\SC2Editor.exe",
  "sc2Path": "C:\\Program Files (x86)\\StarCraft II",
  "cacheDir": "~/AppData/Local/sc2-adjutant",
  "modelViewerPath": "~/AppData/Local/sc2-adjutant/whiteoutflakes/stage-arm64/WhiteoutFlakes.exe"
}
```

`hostAdapter` must name `bundled:host-windows`: no Host Adapter loads unless the machine config names one.

**The helpers.** The Editor is driven by a small C# program, `helpers/editor.cs`, windows are captured by another, `helpers/capture.cs`, and lines are spoken by a third, `helpers/speech.cs`. The adapter compiles each on first use with the .NET Framework 4 `csc.exe` that ships with Windows (`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe`). Nothing is installed and no binary is committed. A build is named by a hash of its source and compiler options, `editor-<hash>.exe`, so an edited source is built again on its next use. Each build compiles its own copy of the source, removed once csc is done. A helper cleaned away from `%TEMP%` while the server runs is built again on its next use. That `csc.exe` only knows C# 5: no `$"..."`, `out var` or `?.`. It can still call WinRT: the capture helper references the WinRT facades beside `csc.exe` (`System.Runtime.dll`, `System.Runtime.WindowsRuntime.dll`, `System.Runtime.InteropServices.WindowsRuntime.dll`) and the system's metadata (`%WINDIR%\System32\WinMetadata\Windows.Foundation.winmd`, `Windows.Graphics.winmd`), and is built with `-unsafe` to read frame buffers. The speech helper references `System.Speech.dll`, which `csc` doesn't find by name: it's in the framework's `WPF` folder (`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\WPF\System.Speech.dll`), so it's referenced by that path. The helpers are per-monitor DPI aware, so they work in physical pixels on a scaled display (this VM's is at 200%).

**Documents may be redirected.** Windows can move the Documents folder (OneDrive, or Parallels sharing the Mac's: here it's `C:\Mac\Home\Documents`). The game's `StarCraft II` folder (banks, `Variables.txt`, `GameLogs`, `EditorLogs`) is in whatever Documents is, so code finds it through the shell's known folder, never as `%USERPROFILE%\Documents`.

## Opening a map in the Editor

The adapter runs `SC2Editor.exe <map>.SC2Map\ComponentList.SC2Components` and waits for the map to load. Open an unpacked map through its component list, as on the Mac. **Opened by its folder, the Editor saves it as an MPQ archive:** a File > Save renames the folder to `<map>.SC2Map.old` and writes a single `<map>.SC2Map` file in its place. The title then shows the path with no trailing slash (`.../Spike.SC2Map`), where an unpacked document has one (`.../Spike.SC2Map/`).

- **One Editor.** Launching `SC2Editor.exe` with a map while the Editor runs hands the map to the running Editor, and the new process exits. Opening a map the Editor already has open makes no second copy.
- **A cold start is slow.** The first launch shows "Welcome to the StarCraft II Editor" and "Downloading Data" before it loads the map: here `editor.open` took 36 s from a closed Editor, and a minute on the day's first start. A map opened in a running Editor loads in about 5 seconds. So `editor.open` waits up to 50 s, and `editor.testDocument`, which must leave time for the game inside an MCP client's 60 s, may run out on a cold Editor: start the Editor first.
- **Loading.** While a map loads, an "Activity - StarCraft II Editor" window is open. Test Document and Save do nothing until it closes.

## The Editor's windows and menu

The Editor's windows are top-level `#32770` dialogs. One main window, with the native Win32 menu bar, holds every open document; a "Messages - StarCraft II Editor" window has a menu bar too. The adapter takes as the main window the one whose File menu has Test Document.

- **Its title names the active document**, by an elided path: `Terrain - [C:/.../examples/test-fields/missions/terrain-objects/output/Spike.SC2Map/] - StarCraft II Editor`. The first word is the open module (Terrain, Triggers, ...). `/*` after the path marks unsaved changes. With no document open, it's `Terrain - StarCraft II Editor`. The elision keeps the drive and as many trailing folders as fit about 70 characters.
- **The Window menu lists every open document**, elided harder: `&1 C:/.../output/Spike.SC2Map/`. Posting an item's command id makes that document the active one. These ids are assigned as documents open, so read them from the menu each time.
- **Commands are posted, not clicked.** `PostMessage(main window, WM_COMMAND, id, 0)` runs a menu command with the Editor in the background, and nothing comes forward. File > Test Document, Save and Close act on the active document.
- **Command ids change between Editor sessions.** In one session (and in the 2026-11-14 spike) Close was 13, Save 15 and Test Document 23, as spec #727 records. After the Editor restarted they were 18, 20 and 28, and 15 was File > New: posting the old Save id opened the New Document wizard. Exit moves with the recent-files list too (413, 416, 332 seen). So the adapter reads the main window's menu each time and finds Test Document, Save and Close by their labels; dump the menu (`editor menu <hwnd>`, the hwnd from `editor windows`) before posting any id by hand.
- **Prompts are dialogs with buttons.** Closing a changed document shows a "Warning" `#32770` with &Yes, &No and Cancel, whose text names the whole path: `Save changes to 'C:/Users/.../Spike.SC2Map/'?`. The adapter reads a prompt's buttons and text (`WM_GETTEXT` on its child controls) and clicks one by posting its `BN_CLICKED` to the dialog (`WM_COMMAND`, what a click sends), which works in the background too; `BM_CLICK` can be dropped by a dialog that isn't the active window. No OCR.

### Telling whether the Editor has a map open

`editor.checkClosed` lists the Editor's windows and its Window menu (no Editor running means no map open), and takes the map as open when any elided path the Editor shows for a document could stand for the map's whole path: each `...` stands for one or more whole folders, and the rest must match, ignoring case and slashes. The active document's title holds the longer path, so it tells more maps apart; the Window menu's shorter one can't tell `C:/.../output/Spike.SC2Map` in one worktree from another, and then the check refuses as if the map were open. That errs the safe way: rewriting a map the Editor has open can crash it. So does an Editor whose main window can't be read (its menus failed to read, or aren't in English): the check refuses, since it can't tell what is open, and so do `editor.testDocument` and `editor.save`. The Messages window doesn't count: it has a menu bar but holds no documents, and it can show before the main window while the Editor starts. An Editor in another language is refused this way every time. It reads window titles and menus without the Editor's help, so it answers while the Editor is busy. Core asks it before every tool that rewrites a package, as on the Mac.

## Test Document

`editor.testDocument` refuses a map the Editor already has open (it would test the copy it loaded), opens the map, makes it the active document, posts Test Document and waits for a new `SC2.exe`. Test Document copies the map to `<install>\Maps\Test\EditorTest.SC2Map` and starts `Support\SC2Switcher.exe`, which starts `Versions\Base<build>\SC2.exe -run "Test\EditorTest.SC2Map" -displaymode 2 ...`. Here the game was running 13 s after the call, with the Editor already open.

**Use windowed mode in a VM.** The Editor's default Test Document window mode is fullscreen (`-displaymode 2`), and in the VM the game then loses its D3D device (`D3DERR_DEVICELOST`) and shows nothing. Choose windowed in the Editor's Test Document preferences (File > Preferences > Test Document; the setting `TestDocWindowed`), which passes `-displaymode 0` ([game-testing.md](../../../docs/reference/game-testing.md#the-editors-command-line) has every Test Document setting). To quit a game you started by hand, close its window and press Yes in its Confirm Exit dialog, or stop `SC2.exe` (`Stop-Process -Name SC2`) if it hangs.

**Quit the game before testing again.** With a game still running, Test Document may load the map in it instead of starting another (the `-reloadcheck` command), so no new `SC2.exe` appears and the adapter can't tell that it worked: it says so.

The game can also start with no Editor: `game.launch`, below.

## Starting the game

`game.launch` runs `<sc2Path>\Support\SC2Switcher.exe -run "<absolute map path>" -displaymode 0 -preload 1 -NoUserCheats -reloadcheck` (the last three are what the Editor's Test Document adds, [game-testing.md](../../../docs/reference/game-testing.md#the-editors-command-line)), with `Support\` as its working folder, and waits up to 30 s for the game's window. The switcher gets past the launcher handshake that stops a bare launch of the game ([game-testing.md](../../../docs/reference/game-testing.md#the-launcher-handshake-and-exit-code-47)), with no Battle.net and no Editor. It starts `Versions\Base<build>\SC2.exe` and exits. Here the window was up after 12 s, showing the map's loading screen, and the map had loaded within about 35 s of the call. `game.launch` resolves once the window is up, while the map still loads.

- **Windowed.** `-displaymode 0` is a window. Fullscreen (2, the Editor's default) loses its D3D device in the VM.
- **The game's window** is a visible top-level window of `SC2.exe` (or `SC2_x64.exe`), class `StarCraft II`, titled `StarCraft II`. An `SC2Switcher.exe` that hasn't exited can have a window titled `StarCraft II` too, so the adapter goes by the process, not the title.
- **One game at a time.** `game.launch` refuses while a game process runs, even one whose window isn't up yet: quit it first (`Stop-Process -Name SC2`). If the switcher exits with an error status and no game started, it says so rather than wait out the 30 s. A check for game processes that fails (the helper erred) counts as unknown, not as no game: the waits in `game.launch` and Test Document ride out isolated failures and give up after three in a row. A capture is written beside its output and renamed into place, so one killed partway leaves no half image.
- A relative map path is made absolute first. Tested with an unpacked Map Package folder; a packed `.SC2Map` file is untested.

## Capturing a window

`screen.capture` captures the game's window, else the Editor's main window, to a JPEG (`.jpg`, `.jpeg`, quality 90) or PNG (`.png`), by the output path's extension; any other extension is refused. The capture helper uses **Windows.Graphics.Capture**: it creates a capture item for the window (`IGraphicsCaptureItemInterop.CreateForWindow`), a Direct3D 11 frame pool (the GPU's device, else WARP's), and waits up to 5 s for a frame. A window sends a new frame only when its picture changes, so it then waits half a second for a second, fresher one: the game, always drawing, sends it at once, and a still window (an idle Editor) is saved as its first frame showed it. The window's alpha is ignored, so the image is opaque. It hides the cursor and the yellow capture border where Windows allows it.

- **Covered is fine.** The window keeps rendering and Windows.Graphics.Capture gets its own frames while other windows cover it: with a maximized Notepad in front of the game, the capture showed the game live (its clock had moved on). PrintWindow isn't reliable for the game when it's covered.
- **Minimized isn't.** A minimized window gives no frames, so the helper checks `IsIconic` first, and `screen.capture` refuses with "the game's window is minimized ... restore it". A restored window may stay behind others.
- **What's in the image.** The whole window, title bar and frame included, as Windows draws it (the title bar greys out when the window isn't in front). The size is in physical pixels, since the helper is per-monitor DPI aware: on this VM's 200% display the game's default window made a 1028×780 image.
- About a second per capture with a built helper; the first capture also compiles it.

## Capture tours

`game.banksDir` is `<Documents>\StarCraft II\Banks`, with Documents as the shell has it (the same lookup the capture tour uses for its bank). The Editor Broker copies that folder into `<cacheDir>\banks\` before a Test Document and records what the test game changed once it quits. `game.running` answers from the same process list as `game.list`, so the broker knows when the test game has quit ([game-testing.md](../../../docs/reference/game-testing.md#what-a-test-game-does-to-the-banks-folder-issue-54)).

`editor.captureTour` runs a camera tour as the macOS adapter does, for `capture_shots`, `capture-exemplars`, `capture-sets` and `capture-edit`, which all go through core's Editor Broker (on Windows it listens on a named pipe named for the `cacheDir`; the [macOS host](../../plugin-host-macos/docs/macos-host.md#the-editor-broker-one-editor-job-at-a-time) has how the broker queues and merges jobs). It only takes a map in `<cacheDir>\capture\maps\`, since it closes it without saving.

1. It deletes the tour's bank, refuses with "A game is running that this tool didn't start. Quit it, or capture with `attach`." when any game runs (it never stops one it didn't start), and closes a copy of the map the Editor still has open from an earlier run. Then the broker writes the map (`writeMap`).
2. It opens the map in the Editor (up to 5 minutes, for a cold Editor), makes it the active document and posts File > Test Document, then waits up to 60 s for a new game. A prompt the Editor brings up instead, such as script errors, fails the tour with its text.
3. Every half second it reads the bank, `<Documents>\StarCraft II\Banks\<bank>.SC2Bank` (Documents as the shell has it: here `C:\Mac\Home\Documents`). The map counts its int key `stop` up from 1. Each new stop is captured as `<stop>.jpg`, zero-padded, and with `recordKeys` the stop and those keys' fixed values are appended to `stops.txt`. A capture that fails is tried again on the next read, while the bank still shows that stop.
4. It ends `done` at stop -1, `game exited` when the game quits first, and `never started` when no stop comes within `startSeconds`; after `pressSpaceAfterSeconds` with no stop it presses Space every 10 s, for a loading screen that waits for it. Pressing brings the game forward (attaching to the foreground window's input, as Windows requires) and takes focus from whoever is typing.
5. Whatever ends it, it quits the game it started (see **Quitting a game** below) and closes the map with File > Close, answering No to "Save changes to '<path>'?". While the Editor shows another prompt (script errors, say), it leaves the map open and says so, since a Close posted under a prompt could stack a save prompt behind it: answer it there and close the map without saving.

- **Frames.** The capture helper's `frame` command captures the game's window with Windows.Graphics.Capture (as `screen.capture` does), keeps only its client area, the window's frame and title bar cut off by the client rectangle's place in the window's extended frame bounds, scales it so neither side is over `width` (never enlarging it) and writes a JPEG at `quality`. One capture, crop and encode takes about 0.7 to 1 s, so a frame shows the game up to a second after its stop was announced, and stops less than about 1.5 s apart can be missed (the bank holds only the latest). The game's window is found once and again only after a capture fails. The game's picture isn't 16:9 here: the Editor's windowed Test Document gave a 1280×800 client area (16:10), and `game.launch` one of 1.42:1. Core's area tours frame their views for 16:9, so here a frame shows a little more above and below.
- **Covered, not minimized.** The game can sit behind other windows. A minimized one gives no frames, so a capture that finds it minimized restores it (`ShowWindowAsync(SW_SHOWNOACTIVATE)`, leaving it behind whatever covers it) and captures again. While the map loaded in front, the game undid a minimize by itself.
- **Awake.** For the tour's lifetime the editor helper's `awake` command holds `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED | ES_SYSTEM_REQUIRED)`, as `caffeinate -d` does on the Mac. It exits with the process that started it.
- **Failed checks.** A game check or bank read whose helper fails for a moment changes nothing: the game is taken as still running and the bank as last read. Ten game checks failing in a row (about 5 s) end the tour with that error, rather than watch a game that may be gone. Stopping the game and `editor.closeCaptureCopies` stop it even when the check won't answer.
- **Quitting a game.** The Editor Broker records each game a job starts by pid and start time (`game.list`: the editor helper's `games` command prints each `SC2`/`SC2_x64` process's id and UTC start time; a pid is reused, so the start time must match too). `game.quit` quits one recorded game and no other: it posts `WM_CLOSE` to the game's window (`editor close <hwnd>`), which asks the game to confirm, then presses Y for Yes in that window (`editor key <hwnd> y`), so the game writes its logs. If the process is still there after 20 s and still has the recorded start time, it ends it (`TerminateProcess`). The log says which it was. The Yes key, and that the quit leaves complete logs, are checked on a real run (#57). A Test Document's game is the author's: the broker holds its queue until it quits and never quits it.
- **`attach`.** With `attach`, the author has started the game (with `game.launch`, say): the tour only watches it, leaves the Editor alone and doesn't stop the game at the end. The bank as an earlier run left it (usually ending at -1) is ignored until the game saves it again.

`editor.closeCaptureCopies` closes, without saving, every document the Editor has open in this `cacheDir`'s `capture\maps\`, after quitting the games the broker hands it (the ones it recorded as a capture's; any other game is left running). A document counts when the path the Editor shows can stand for `<cacheDir>\capture\maps\<its name>` and either shows that path whole or the copy is on disk: the Window menu's elided `C:/.../capture/maps/X.SC2Map` could be another cache's copy. The broker runs it as it starts and after a failed tour.

Timings here: from a closed Editor, the game was running 47 s after the call and the first stop came 38 s after that; with the Editor open, Test Document ran after 14 to 17 s. Stopping the game and closing the map took 6 to 9 s.

## Input (unverified, for future input work)

Once the game has focus it takes keys sent with `SendInput`, but it ignores `SetCursorPos`, so a pointer can't be moved by setting its position. Resizing the game's window from outside desyncs the mouse: clicks land where the window used to be. Neither is covered by a test here; recorded so work that clicks in the game starts from it.

## Placeholder voices

`tts.speak` speaks a line with Windows' built-in voices through System.Speech (`SpeechSynthesizer`), straight to a 22050 Hz, 16-bit, mono PCM WAV (`SetOutputToWaveFile` with a `SpeechAudioFormatInfo`), the format SC2 plays, so no conversion follows. The text goes to the helper in a UTF-8 file, never on its command line, so a long line or one with quotes arrives whole. A line of 14 words made 6.4 s of audio in about 1.2 s, and the first call also compiles the helper. The voices leave about 0.1 s of silence before the speech and 0.75 to 0.8 s after it; core trims each spoken placeholder to its speech before it moves the file into place (`packages/core/src/host/placeholder-voices.ts`), whatever the Host Adapter, and encodes it to Ogg with ffmpeg for a Mission whose voice format is `.ogg`.

**Naming a voice.** A line's `voice` (its character's) names an installed voice in full, ignoring case (`Microsoft Zira Desktop`), or by the words of its name that tell it from the others (`Zira`). Words shared by several (`Microsoft`, `Desktop`) fail, naming the voices they could be. Any other name fails, listing the installed voices with their language and gender. A `tts.speak` with no `voice` (or an empty one) gets Windows' default voice (here `Microsoft David Desktop`), but core always names one (below). The installed voices are listed once and kept, and listed again before an unknown name fails (at most once a minute, so a voice installed while the server runs is found), and after a line in a named voice fails to speak (the voice may have been removed since). A line may take up to 2 minutes to speak.

- **The voices Windows ships.** On this Windows 11 (en-US), System.Speech has two, `Microsoft David Desktop` (male) and `Microsoft Zira Desktop` (female), both `en-US`. Other languages' Desktop voices are untested.
- **Voices from Settings don't count.** Settings > Time & language > Speech > Add voices installs OneCore voices (registered under `HKLM\SOFTWARE\Microsoft\Speech_OneCore\Voices`), which System.Speech doesn't see. Here OneCore also has `Microsoft Mark`, and `tts.speak` refuses `Mark`. A voice System.Speech can use is a SAPI 5 voice, registered under `HKLM\SOFTWARE\Microsoft\Speech\Voices\Tokens` (and `WOW6432Node` for 32-bit programs): installing a language pack's speech feature, or a third-party SAPI 5 voice, adds one. Check with `Add-Type -AssemblyName System.Speech; (New-Object System.Speech.Synthesis.SpeechSynthesizer).GetInstalledVoices().VoiceInfo.Name` in PowerShell. Piper is a later ticket.
- **The Mac's voice names aren't here.** Characters name macOS voices (`Samantha`, `Reed (English (US))`), and core gives a line with none the Mac's `Eddy (English (US))`, so on Windows those lines fail to speak: a compile gives them silence and reports why, and `npm run tts` stops at the first. Give the characters Windows voices to hear them on Windows.

## Rendering and exporting models

`model.render`, `model.rendererKey`, `model.export` and `model.exportGltf` run the WhiteoutFlakes viewer (`whiteoutflakes.ts`) on its D3D11 backend, through the same driver as the macOS adapter (the plugin SDK's, core's `src/host/whiteoutflakes.ts`): the thumbnail recipe, the retries while frames come out garbled, the background keying and the mod-model staging are shared, and [related-repos.md](../../../docs/reference/related-repos.md#fernandos27whiteoutflakes) has the viewer facts behind them. `model.export` (with `textures`, `--save-m3-textures`) and `model.exportGltf` (`--export-gltf`, a `.glb` with its textures embedded, for set views in Blender) draw nothing, so they run without the GPU-or-WARP test, in a worker's copy of the viewer. Checked here (2026-11-21) on `ShakurasRockColumn_00.m3`: `model.exportGltf` wrote a 705 KB `.glb` with its 3 textures embedded in 13 s, and `model.export` with `textures` wrote the `.m3` and its diffuse and normal `.dds` under `Assets\Textures\` beside it.

**Building the viewer.** `powershell -ExecutionPolicy Bypass -File packages\plugin-host-windows\scripts\build-whiteoutflakes.ps1` clones WhiteoutFlakes at the pinned commit (d2756ce) into `%LOCALAPPDATA%\sc2-adjutant\whiteoutflakes\src`, applies `scripts\d3d11-warp.patch`, configures with upstream CI's Windows flags for the machine's architecture (`-A ARM64` here; `-Arch x64` for the other), builds `WhiteoutFlakesStandalone` and stages the exe with its `shaders`, `lang` and `fonts` in `stage-<arch>\` (about 120 MB). Point `modelViewerPath` at `stage-<arch>\WhiteoutFlakes.exe`. It needs Git, Visual Studio 2022 or its Build Tools with the C++ workload (and its ARM64 tools for an ARM64 build), CMake and the LunarG Vulkan SDK 1.4.341.0 with VMA, for `slangc`. The SDK's Vulkan loader is x64 only, so an ARM64 build turns the Vulkan backend off, and since `platform_window.cpp` includes `vulkan/vulkan.h` whatever the backends, the script puts the SDK's `Include` on the compiler's path. It clones with `core.longpaths=true` (a submodule's test files are past `MAX_PATH`) and LF line endings (so the patch applies). Here a fresh ARM64 build took about 21 minutes: 3 to clone and configure, 18 to build. At the end it runs `--headless-test` on the GPU and on WARP and prints both results.

**GPU or WARP.** The viewer can't render on this VM's GPU: D3D11 loses its device during setup, D3D12 fails pipeline creation (`CreateGraphicsPipelineState` E_FAIL) and there's no Vulkan driver. The patch makes `WF_D3D11_WARP=1` create the D3D11 device on WARP, Windows' software rasterizer, which renders correctly (opt-in, so it's offered upstream). The adapter runs `--backend d3d11 --headless-test` once per viewer build (its path and the exe's modification time), on the GPU and, if that fails or runs over 5 minutes (as long as the build script allows), on WARP, and keeps the verdict in `<cacheDir>\whiteoutflakes\backend.json`; delete that file to test again. Here the GPU test fails after up to a minute and WARP passes in about 20 s. Each test runs in a fresh copy of the viewer of its own, `<cacheDir>\whiteoutflakes\probe-<pid>-gpu\` and `-warp\`, removed after, so whatever a GPU run that lost its device leaves beside the exe reaches neither the WARP test nor a worker. A probe interrupted partway leaves its folder behind (about 120 MB); the next probe removes those whose process has gone. A copy into a probe folder that fails fails the probe, rather than count as a GPU failure and pick WARP. Neither passing fails the render with both results, and every later render in that process fails the same way without testing again (nothing is kept on disk, so the next process tests again). `model.export` needs no verdict: `--save-m3` opens no device, and it worked on the GPU here.

**A copy of the viewer per worker.** On Windows the viewer keeps its pipeline cache and PSO trace (`pso_trace.bin`) beside its exe, not under a home folder, and processes sharing them corrupt them. So each concurrent run gets a worker folder, `<cacheDir>\whiteoutflakes\workers\<n>\`, holding a copy of the viewer's whole folder, kept between runs so the caches stay warm and copied afresh when the viewer is rebuilt (`.viewer-build` there records which build it holds). A worker claims its folder across processes with `workers\<n>.lock`, which holds its pid and a token of the claim's own, so two processes rendering at once never share a copy, and a process seeing a new build never deletes the copy another is running. A lock whose process has gone is taken over by renaming it aside first, which only one process can do, and a lock with no pid by then counts as gone once it's 10 s old. A release removes the lock only while it still holds its own token.

**Mod models.** A model from a Workspace mod is staged as on the Mac ([macos-host.md](../../plugin-host-macos/docs/macos-host.md#rendering-a-mods-models)), but its textures are copied beside the copy rather than linked, since symbolic links need Developer Mode or an elevated process on Windows.

Timings here, on WARP: a `model.render` of `Assets/Doodads/ShakurasRockColumn/ShakurasRockColumn_00.m3` at 4 angles, 512 px, takes 13 to 38 s (about 20 s usually; one run took 7 minutes and wasn't explained), of which the viewer reports about 2.5 s of rendering: most of it is the viewer opening the game's storage and reading its 3,780 GameData files. The first render of a build adds the smoke tests and the worker copy. Every frame came out on white, so each render needed one attempt. Two renders at once took 19 to 62 s, each in its own worker folder (WARP shares the CPU between them). `model.export` of the same model took 3 to 9 s and wrote a 20,128-byte MD34 file. A missing model fails with "model not found" in about 3 s.

## Saving a copy in the Editor

`editor.save` is for a copy made for the purpose, such as the MapScript drift test's under `<cacheDir>/drift/`. **A save writes only what the Editor holds as changed:** for a map it just opened, the ComponentList, `DocumentHeader`, `GameData.version`, `Preload.xml` and `PreloadAssetDB.txt`, and not `MapScript.galaxy`, even when that file is out of step with `Triggers` (a line appended to it before opening survives the save). It writes `MapScript.galaxy` when the triggers changed, or when the file is missing. So the adapter deletes the copy's `MapScript.galaxy` before opening it, and the save writes the Editor's own script from `Triggers`, which is what the drift test compares. Then it posts Save, waits up to 10 s for `MapScript.galaxy`, and posts Close, answering No if the Editor asks to save changes to that map. A prompt the save brings up, before or just after it writes the script, fails it with the prompt's text, and the map is left open for the author to answer it: a Close posted under a prompt could stack another.
