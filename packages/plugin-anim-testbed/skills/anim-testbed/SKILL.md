The anim-testbed Utility turns one **spec** into a test map. The spec lists the units with their animations, the moments to judge and the variations to compare. The map has a trigger dialog: Unit, Moment and Variation dropdowns, an Animation dropdown for moments that play one, Play, Stop, Loop, a readout of each cue as it fires, and a Send box. Build it with `node {{PLUGIN_FOLDER}}/dist/testbed.js <spec.json>`; `--check` validates without writing. The spec format and what the build checks: [README.md]({{PLUGIN_FOLDER}}/README.md). A spec to start from: [examples/stock-units.json]({{PLUGIN_FOLDER}}/examples/stock-units.json).

## Leading words

- **Moment**: something that happens to a unit that you want to judge (an attack, its impact, a hit, a death, a voice line), defined once per spec as `{ "do", "at", "from" }`. `do` is `play` (an animation) or `kill` (the cues then play where it died); left out, the cues play alone. `at` is where the sounds play, `unit` or `target`. `from` is when cue times start: `start`, or the animation's `strike` or `land` (with `do: play` only). An impact is `{ "do": "play", "at": "target", "from": "land" }`.
- **Animation**: one of a unit's animations, by name: its `play` message, `strike`, `land`, `length`, and `clear` for a hit reaction that should stop early. A unit's moment names the one it plays (`anim`, its first by default).
- **Variation**: one candidate for a unit's moment. It is a list of cues, with a `note` saying what it is, `pick` on the one recommended, and an optional `anim` to play a different animation.
- **Cue**: `<what>[@<when>][~<stop>]`. `<what>` is a CSound id, `actor <message>`, `actor:<child> <message>`, `target <message>` or `effect <CEffect id>` (from the unit at the target; its damage is real). `<when>` and `<stop>` are seconds, `strike`, `land` or `strike+0.2`.
- **Strike** and **land**: when an animation's swing goes and when it lands on the target, in seconds from its start.

## Steps

1. **Settle the test.** Find out which units, which animations, which moments, and the candidates in each. Put a unit's real model on it: a stock CUnit by `unit`, or a model of the Workspace's own by `new` (its `.m3`, `.m3a` files and texture folders). Read an animation's strike and land off it at 30 frames a second, or start from a guess the author tunes in the game with the Strike and Land steppers. Done when every candidate has CSound ids and times, and a note saying what it is.
2. **Write the spec.** Put it beside the Mission, for example `missions/<id>/tests/<name>.json`, with `base` the Mission's Map Package and `out` under the Mission's git-ignored `output/`. Use `roots` for private folders (extracted game files, a model's exports), so no machine path is written into it. Blizzard's files never go in a repo: the build copies them into the test map only. Done when `--check` reports no errors.
3. **Read the check.** An error is a real fault: an unknown CSound, unit or model plays nothing in the game and says nothing. An `AnimPlay` that matches none of a model's clips never plays, and the error lists the clips it has. Name clips with SC2's own words (`Spell C`, not `Attack Mega`). A warning about a stock actor is only that the build can't list the game's actors: make sure the id is right.
4. **Build and hand it over.** Build, then tell the author the map's path and what to try. Open it in the Editor and run Test Document. After a rebuild that changes a model, quit the Editor first: it keeps a model loaded by name.
5. **Record what the author picks.** Move `pick` to each chosen variation in the spec. Once the author has retimed animations and quit the game, run the command with `--apply` to write the new strike, land and length into the spec (it prints each change and skips one the spec has changed since the build). If it can't find the bank, ask where the game saved `AnimTune<Name>.SC2Bank` and pass it with `--bank <file>`. A death mix the author settles on can become data with the `sound-mix` skill, from its sound cues.
