# macOS Host

How the mapper drives the StarCraft II Editor and game on macOS: the facts behind the macOS Host Adapter, `bundled:host-macos` (`packages/plugin-host-macos/`). How to install and configure it (`machine.json`, `editorPath`, `cacheDir`, the permissions it needs) and which capabilities it has are in the package's [README](../README.md). This doc is what the adapter's code relies on, and what an author or assistant needs when doing the same by hand. The native Editor runs on Apple Silicon only through the community fix shim ([below](#the-native-editor-fix)).

## The native Editor fix

On Apple Silicon the native Editor crashes at launch with "StarCraft II has encountered an error while initializing your videocard." The community shim [Nish07/sc2-editor-macos-fix](https://github.com/Nish07/sc2-editor-macos-fix) fixes it without changing the game's files (source reviewed at `f3bd83e`). It builds an x86_64 `dylib` locally, launches the Editor with `DYLD_INSERT_LIBRARIES` through `open --env`, and patches seven bytes in memory: 3 that skip the graphics gate behind the misleading error, and 4 that send an `NSBitmapImageRep` call to a 32bpp conversion hook for object previews. It needs Rosetta 2 and `clang`.

Checked on an M1 Max under macOS Sequoia 15.6 with Editor 5.0.16 (97671): the Editor opens, saves, reopens and runs Test Document. On that build the preview hook was skipped (`signature not found - skipped`), and the Editor still works. The fix is unofficial and depends on the build: a new SC2 build may need its patch addresses found again. Install it apart from this repo, and don't commit its binaries.

## Opening a map in the Editor

Open an unpacked map by its component list, not its folder:

```sh
open -a "StarCraft II Editor (Fixed)" <map>.SC2Map/ComponentList.SC2Components
```

Double-clicking `ComponentList.SC2Components` in Finder opens the map in the Editor too (the author, 2026-11-21).

Use the shim's launcher app (the machine config's `editorPath`), which injects the fix; the bare `StarCraft II Editor.app` crashes at launch. The running process is still named "StarCraft II Editor". Opening a map that's already open only brings it forward, still as it was loaded.

The map the author opens is the Mission's committed package, `missions/<id>/<Name>.SC2Map` in its Workspace, which `compile_map` compiles in place by default. A throwaway copy (a test Cinematic's map, an `exp-*` bisection copy) goes under the Mission's `output/`, which survives restarts. The Workspace's `.gitignore` keeps `output/` out of commits (the example Campaign's ignores `missions/*/output/`); a Workspace without that line should add it.

**Telling whether the Editor has a map open.** The adapter's `editor.checkClosed` lists the Editor's window titles through System Events (`name of windows of process "StarCraft II Editor"`; nothing when it isn't running) and takes the map as open when a title holds the package's whole resolved path, or a shortened one (`[/.../<tail>]`, as the Editor shows a long path, seen 2026-11-21) whose tail with at least a folder beside the name ends that path, so another worktree's copy of the same Mission isn't taken for it. A title that is only the map's name counts as open too, since it can't be ruled out. Before 2026-11-21 the check needed the whole path and missed a map whose title the Editor had shortened. It needs the Accessibility permission, and sees no windows while the screen is locked. When the Editor is too busy to answer (in a Test Document session, say), System Events times out (`AppleEvent timed out (-1712)`) and the check fails, so the tool refuses as if the map were open: try again once the Editor is idle. Core asks it before every tool that rewrites a package: `compile_map` (for the package it writes, so also an `outputDir` the Editor has open), `compile_cutscene`, `test_mission`, `edit_kept_objects`, `tune_kept_triggers` and `edit_kept_terrain`, which write nothing while the map is open.

**Same-file refresh (built; checked on one throwaway map, 2026-11-21).** `compile_map` with `refresh: true` closes a map the author has open, compiles, and opens the same `ComponentList.SC2Components` again, instead of refusing (#739; the idea came from comparing another project's design, no code or text used). It was run against the real Editor through the five steps below (results after them); the two gaps are marked there.

What the author saw on a throwaway map (2026-11-21, Data module), which it rests on: (1) the window title carries `*` before the closing bracket while the document has unsaved changes (`... /Name.SC2Map/*] - StarCraft II Editor`) and none when clean, and System Events sees it; (2) a closed map whose files changed on disk shows the changes when reopened by its `ComponentList.SC2Components`, with no prompt; (3) File > Close with "Don't Save" on a dirty document closes it and writes nothing.

How it works:

- *Refuse if dirty.* The adapter's `editor.refresh` reads the window titles and reads them with `windowState` (`refresh.ts`, a pure function over title strings). A title belongs to the map when it holds the package's whole resolved path, or the shortened tail the Editor shows for a long path (seen 2026-11-21: `/.../repos/my-campaign/missions/trigger-test/output/Exp-Refresh.SC2Map/*`) that ends it with at least a folder beside the name. A `*` in the bracketed path refuses with a message and closes nothing, so the author's work is never closed over, and the save prompt is never answered "Save". A shortened title that is only the map's name (`[/.../Name.SC2Map]`) is refused too, since it can't be told from another worktree's copy. Two copies that share a whole tail can't be told apart either (needs an Editor check: how often).
- *Close.* Otherwise it clicks File > Close in the window for that map, the same System Events click the capture-copy close uses. If the Editor can't be brought forward (macOS refuses while the author is in another app) the click fails before anything is clicked, and the tool says the map is still open: it never clicks blind. It then waits up to 5 s for the title to go; if the map is still open, a save prompt may be showing, and the author answers it (it never answers one).
- *Reopen.* After the compile `compile_map` calls `editor.open` on the same path, and says so in its reply. A compile that stops (Editor changes to decide, say) writes nothing, so the map is reopened as it was. If the reopen fails, the reply gives the file to open.
- *Which maps.* It acts only when `editor.checkClosed` says the map is open, goes through the Editor Broker like the other menu clicks, and fails at once while a capture runs. A Host Adapter without `editor.refresh` makes `refresh: true` refuse and hand the close to the author, as without it.

What the author ran, on a throwaway copy under a Mission's `output/`, with the Editor open on it by `ComponentList.SC2Components`:

1. **Clean map, `refresh: true`: passed.** The window closed with no prompt, the compile ran, and the map reopened with the compile's changes, one window, no reload prompt.
2. **Dirty map: passed.** It refused, naming unsaved changes (the title ended in `*`). The window stayed open with the edit intact, nothing was written to the package, and no save prompt appeared.
3. **Another app in front: partly checked.** The adapter did bring the Editor forward. The author's click took focus away before File > Close, so the menu lookup failed and the call refused with the map still open and nothing compiled. The case where macOS refuses to bring the Editor forward at all was not tried; the code refuses on any failed click, so it should refuse the same way (needs an Editor check).
4. **Map not open: passed.** A plain compile, and the Editor did not open the map.
5. **`*` in the other modules and with a long path: not run.** The author reports `*` shows in the Triggers and Data modules too (their report, not a recorded run). A path long enough to shorten the title to just the map's name is still untried; that is refused as unclear.

Everything above is one small map, one Editor version (not recorded), one machine.

Not known: whether File > Close can leave a save prompt on a map that was clean (the title lagging an edit by a moment); the adapter would then report the map still open and leave the prompt to the author.

**Recompiling an open map can crash the Editor.** Rewriting a map's files while the Editor has that map open sometimes crashes it, and otherwise the Editor keeps testing the copy it loaded. Before recompiling a map the author has open, ask them to close it, or tell them a reopen is coming. After a crash, reopen the map: the crash isn't the map's fault.

## Starting the game: only through Test Document

On the Mac the game can't be launched directly: a bare launch exits within seconds, and the gate is Battle.net's per-launch `BDK_LAUNCH_GUID` handshake, which isn't forged. The evidence (bare, ASLR-off, lldb and Battle.net-flag launches, and the ignored `-listen`) is in [game-testing.md §1](../../../docs/reference/game-testing.md#the-launcher-handshake-and-exit-code-47). The only automatable way to start a game is the Editor's **File > Test Document** (⌘F9), which is why the adapter has `editor.testDocument` and no `game.launch`. Test Document does nothing while the map is still loading (an "Activity - " window is open).

## When the game or the Editor won't open

Two settings outside the maps have stopped both from opening. Fix them in the files with everything closed:

- **The graphics API.** `GraphicsApi=` in `~/Library/Application Support/Blizzard/StarCraft II/Variables.txt` (CRLF line endings) is shared by the game and the Editor. Choosing the beta API in the game's options writes `OpenGL3`. It was set when the game stopped opening on Apple Silicon (alongside the startup modules below, which turned out to be the Editor's problem). The working value is `Metal`; deleting the line returns to the default. The game's graphics log (`GameLogs/<time> Graphics.txt`) says `Initialized Metal GraphicsDevice` when it's working.
- **The Editor's startup modules.** `#Current User\StarCraft II Editor\Preferences\StartupModules` in `~/Library/Preferences/com.blizzard.StarCraft II Editor.prefs` is a bit mask of the editors opened at launch, the value on the line after the key. `512` opens the Cutscene Editor at startup, and with it the Editor spun at full CPU and never showed a window. Delete the key and its value line to start with the Terrain Editor; the Editor rewrites the file when it quits, so do it while it's closed.

## Driving the Editor

The adapter's AppleScript and Swift helpers are in `packages/plugin-host-macos/index.ts` and `capture-tour.ts`.

- **Focus.** `activate` and `open -a` are refused from the background. Use System Events: `AXRaise` a window and set `AXFrontmost` to true. Menus (File > Test Document) exist only while the Editor is frontmost, and macOS refuses to bring it forward while someone is using another app, but not once they pause: a capture tries again every 30 seconds and meanwhile asks the author for the click. Keys posted to the Editor's process in the background (⌘F9 through `CGEventPostToPid`) do nothing, and a background Editor's menu bar has only its Apple and application menus, so there is no way to start Test Document without bringing it forward (tried 2026-11-11).
- **Close without saving.** File > Close, then the button whose title starts "Don" (the apostrophe in "Don’t Save" is curly). Close only documents the tool opened: the author's own maps may be open with unsaved changes. The adapter closes only capture copies under `<cacheDir>/capture/maps/`, and the author's own map only through `editor.refresh`, which refuses a title showing `*` and never answers a save prompt (see "Same-file refresh").
- **Shortened titles.** A document window's title shows its path shortened, and a long file name shortens it more: `Terrain - [/.../maps/<name>.SC2Map]`, with even `capture/` gone. So the adapter finds a capture copy by its file name, which ends in the broker's job id, not by its folder. The sweep for leftover copies closes a name it reads from a title only when the title shows the full path, or when the name ends in a job id and the copy is on disk in this cache's folder.
- **Invisible dialogs.** Save prompts are sometimes invisible to Accessibility (window count 0). Find them with `CGWindowListCopyWindowInfo`, confirm the text with Vision OCR, and click with a CGEvent.
- **Screen Recording.** Without it macOS hides other apps' window titles, so the game window can't be found or captured, and a tour runs to its end with no frames. The permission belongs to the app that started the process (Terminal, or T3 Code for its terminals and agents), and an Editor Broker inherits it from the app that started it. A capture checks first and refuses with the setting to change.
- **Awake screen.** The run needs an unlocked, awake display: once it sleeps and locks, Accessibility sees no windows and screenshots fail. The adapter keeps the display awake with `caffeinate` during a capture; start `caffeinate -d` yourself before a long unattended run of anything else. Never try to unlock the screen.

## The Editor Broker: one Editor job at a time

There is one Editor, one menu bar and one frontmost window. Two captures at once click menus on each other's maps and capture each other's windows. A Test Document during a capture starts a second game, which the capture then quits. The Editor Broker (`packages/core/src/capture/editor-broker.ts`) is the one process that runs `editor.captureTour` and the other Editor actions that click menus, one job at a time, first come first served.

- **What goes through it.** Every `editor.captureTour` run: `capture_shots` and `npm run capture-shots`, `capture-exemplars`, `capture-sets` and `capture-edit`. Nothing else opens or closes capture copies. On a machine whose Host Adapter captures, `editor.open`, `editor.refresh`, `editor.testDocument` and `editor.save` go through it too (`runEditorAction` in `editor-broker-client.ts`), so `test_mission`, `compile_cutscene` with `play`, and the MapScript drift test take their turn in the same queue. `editor.checkClosed` only reads window titles and goes straight to the host. A host that can't capture has no broker, and runs those actions directly.
- **`test_mission` doesn't wait.** Its whole call has to fit under the MCP client's 60 s request timeout, so its Test Document is refused at once while a capture runs or waits. The reply names the job ("The Editor is busy … capture job <id> of <map> is running, 2 more waiting") and tells the author to wait, not to click Test Document by hand. The drift test's save does wait its turn.
- **A test game holds the queue.** A capture starts by quitting any game it finds. So after a Test Document that started a game, the broker starts nothing else until that game quits, checking `game.running` every 5 seconds. Meanwhile its status shows the Test Document job as running with `holding: true`, the log says `holding the queue until the test game quits`, and another `test_mission` is refused ("quit it first"). A game the author started from the Editor by hand isn't held for: a capture still quits it.
- **Merged tours.** Waiting tour jobs on the same map with the same capture options (lighting among them) run as one tour, and the frames are split back to each job, so the game starts once for all of them.
- **Its socket and log.** It listens on `<cacheDir>/editor-broker.sock` (the machine config's `cacheDir`). When that path is longer than a Unix socket allows (103 bytes), it uses `$TMPDIR/sc2-adjutant-broker-<hash>.sock` instead. Its output goes to `<cacheDir>/editor-broker.log`. The first capture that finds no broker answering starts one, detached, with the same machine config. It exits after 10 minutes with no job and no client connected. The Editor stays open between jobs; only the capture copies open and close.
- **Capture copies.** The broker writes each job's copy under its own name, `<map> <label>-<job id>.SC2Map` in `<cacheDir>/capture/maps/`, so a stale copy is never taken for a new one. It removes the copy once the tour is done, and keeps it when the tour stopped early, to open and debug.
- **Reading its log.** One broker runs one job at a time, so a job's `running <id>` line always follows the previous job's `done <id>: N frames, <end>` or `failed <id>: <message>`. A `running` line in the same second as its `queued` line means the queue was empty, not that two jobs ran at once. Between those lines are the job's own progress lines, `<id>: <line>` (`Test Document clicked`, `game started`, `stop 3`, `closing a stale copy`), the same lines its client sees, so a failure like "the Editor never opened" shows what the Editor was doing before it. Brokers built before 2026-11-20 log neither `done` lines nor progress lines. An editor job logs `done <id>: <action>`, a refused one `refused <action> on <map>: busy`, and a cancelled tour `cancelled <id>`.
- **Status.** `npm run capture-shots -- --status` prints the broker's pid, the script it runs from (so its checkout), the running job (or merged jobs), the queue and the last error, or says no broker is running. A `capture_shots` call that outlasts its wait reports its job's place the same way.
- **Screen and focus.** `editor.captureTour` keeps the display awake (`caffeinate -d`) while a tour runs. When macOS won't bring the Editor forward because the author is using another app, it posts a notification asking for File > Test Document and waits up to 15 minutes for the click, and every job behind it waits too.

**After a crash.** A broker that crashed leaves its socket file, which nothing answers on. The next capture starts a new broker, which takes the socket over (one at a time, with a `.lock` folder beside it). Each broker closes, unsaved, every capture copy the Editor still has open under this `cacheDir` when it starts, quitting the game first if one is running, and again after a failed job. To stop a broker that's stuck, `kill <pid>` with the pid from the status: it removes its socket as it exits.

**Cancelling a capture.** A waiting job whose client hangs up (an agent's session ending, Ctrl-C on a CLI) is dropped from the queue. A running tour is cancelled once every client of it has hung up. It stops at its next wait or stop, quits the game, closes its copy unsaved, and the broker closes any capture copy left open, as after a failure; the log says `job <id> running; its client hung up, so it is cancelled`, then `cancelled <id>`. A merged tour runs on while any of its jobs' clients is still connected. A `capture_shots` job belongs to the MCP server, which stays connected past the call's wait, so it is cancelled with `capture_shots({ job, cancel: true })`, or by stopping a call that is waiting on it (the author stopping the task). A job the call has already returned from runs on until one of those. A cancelled tour's frames so far stay in its folder, with no `shots.json`. An editor job isn't cancelled: it is short, and it runs to its end.

**A broker from another checkout.** Every checkout and worktree on the machine shares one broker, because they share one `cacheDir` socket and one Editor. The first capture to find none running starts it, from its own checkout's build, so it may come from another session's worktree. Its first log line and its status name the script it runs from. A client from another checkout gets a progress line saying so ("The Editor Broker running (pid N) was built from …"), and its job runs on that checkout's capture code. The broker doesn't refuse that client or hand over to it: a client turned away would need a second broker, and two brokers would drive the one Editor at once. When the protocol differs, the broker refuses the job ("speaks protocol N"): protocol 2 added editor jobs, so a broker built before them refuses every client built after, until it idles out. When the capture code differs in a way that matters (a fix the job needs, or a `dist` rebuilt since the broker started, which it doesn't reload), let the broker idle out, or ask whoever is using it before you `kill <pid>`.

## Placeholder voices

`tts.speak` runs `say -o <aiff>` in the line's character's voice, then `afconvert -f WAVE -d LEI16@22050 -c 1`. `say` leaves silence at the file's end, about 0.2 s, and more for some voices (0.4-0.5 s for the Protoss voices, with their effects). Core trims each spoken placeholder to its speech before it moves the file into place (`packages/core/src/host/placeholder-voices.ts`), whatever the Host Adapter, so a Cinematic that plays its lines back to back has no gap after each.

For text with nothing to say ("...", say), `say` succeeds but writes no audio, and `afconvert` makes that a WAV whose data chunk is empty. Core takes such a file for a line it couldn't speak: it writes the line's silence instead, lists the line as silent, and doesn't speak it again until its text changes. An empty WAV must never reach ffmpeg's own Vorbis encoder, which never finishes one (see [asset-sources.md](../../../docs/reference/asset-sources.md)).

## Watching the game

- **Find the window.** Find the game window with `CGWindowListCopyWindowInfo` and `kCGWindowListOptionAll`, owner "SC2", name "StarCraft II", and capture it with `screencapture -l <id>`. With the Editor's Test Document window mode set to Windowed, a covered window still captures; a minimized one doesn't.
- **Recording video of the window.** A tour that asks for `video` gets the game window recorded with ScreenCaptureKit (a small Swift helper, `record`), as HEVC at the request's `quality` (`AVVideoQualityKey`, 0.9 when it gives none; at 0.5 particles smeared away) with a list of when each stop and mark happened. It logs the window's pixels per point, and warns when it has to scale the picture up to the asked width: a 1280-point window on a display of 1 pixel a point has only 1280 pixels. Like `screencapture -l`, it records a covered window. But it gets **no frames while the game window fills the display**: macOS then sends the window straight to the display without compositing it. On 2026-11-23, a 1728×1084 game window on a 1728×1117 display gave 27 s of nothing, then steady frames from 1.5 s after it was resized to 1280×800, with no gaps. Whole-screen recording (`screencapture -v`) still works then, but it films whatever is in front. So the host resizes the window to 1280×748 (a 16:9 picture under the title bar) before it starts recording, through System Events. The game ignores that until it has loaded, so the host tries once a second, and the effect tour waits 12 s before its first effect when recording. The game writes its window size to `Variables.txt` (`windowwidth`, `windowheight`, in pixels) when it quits, but setting a smaller size there while the game was closed didn't change the next Test Document window: it opened at full size and wrote that size back.
- **Loading screens.** Some maps wait on a "press space" loading screen: send Space. Pressing it takes focus, so do it only after a long wait.
- **Getting data out.** A map can report to the outside through `BankSave`. The bank appears at once at `~/Library/Application Support/Blizzard/StarCraft II/Banks/<name>.SC2Bank`. The `Text.txt` log stays empty. The ClientAPI on port 6119 also works ([game-testing.md §5](../../../docs/reference/game-testing.md#5-the-clientapi-http-server)).

## Rendering a mod's models

`model.render` draws with WhiteoutFlakes (`whiteoutflakes.ts`, through the plugin SDK's viewer driver, core's `src/host/whiteoutflakes.ts`, which the Windows Host Adapter shares). It reads a model and its textures straight from the game's CASC storage. Given a model by its file path, it reads each texture the model names (`Assets/Textures/x.dds`) from that path under the model's folder first, and never looks in a mod package. So when a request's `packages` hold the model (ADR-0017), the adapter copies the `.m3` into its work folder and renders the copy. Beside the copy it links just the textures the model names: it reads each material layer's image path from the `.m3`, and links that path to the file in the newest package that holds it. It also links a texture kept beside the model in its package beside the copy, where the viewer looks next. Textures the packages lack still come from the game. A render costs a few links however large the packages are, since it never links a package's other files (an asset mod can hold thousands, mostly sounds). A model whose textures can't be read, one that isn't an MD34, is copied with none. Nothing is written into the packages. Without the staging, a mod model whose textures are only in the mod draws untextured: flat grey or white, and the viewer logs nothing.

## Recording a cutscene with its sound

The built-in recorder (⌘⇧5, QuickTime) records the screen and a microphone, never the game's sound. Two ways to get the sound:

**OBS Studio (recommended).** `brew install --cask obs`. On macOS 13 and later its sources use ScreenCaptureKit, so it captures the game's audio with no virtual audio device, and the volume keys keep working.

1. On first launch, skip the auto-configuration wizard (or choose "Optimize just for recording"). Grant OBS **Screen & System Audio Recording** in System Settings > Privacy & Security when asked, then quit and reopen it.
2. Start the game with Test Document, with the Editor's Test Document window mode set to Windowed (see [Watching the game](#watching-the-game)).
3. Under Sources, **+** > **macOS Screen Capture**. Method **Window Capture**, Application **SC2**, Window **StarCraft II**. Untick "Show window shadow".
4. Under Sources, **+** > **macOS Audio Capture**. Method **Application Audio Capture**, Application **SC2**. Its meter in the Audio Mixer should move while the game makes sound. If two meters move in step, the screen capture is carrying the sound too: mute one, or the sound doubles.
5. Settings > Video: set Base and Output resolution to the game window's size so nothing is scaled. Settings > Output: Recording Format **MPEG-4 (.mp4)** or **Hybrid MP4**. Recordings go to `~/Movies` by default.
6. **Start Recording**, play the cutscene, **Stop Recording**. Once the scene is set up it stays, so later recordings are steps 2 and 6 only. If the game was restarted and the picture is black, open the screen capture source's properties and pick the window again.

**The built-in recorder with BlackHole.** With the free BlackHole 2ch virtual device (`brew install --cask blackhole-2ch`): in Audio MIDI Setup, **+** > Create Multi-Output Device with the speakers or headphones listed first plus BlackHole 2ch (Drift Correction on BlackHole), and choose it in System Settings > Sound > Output. Then in ⌘⇧5 > Options pick BlackHole 2ch as the microphone. The volume keys don't work while that device is the output, so set the volume in the game, and switch the output back afterwards.

For a clean take either way, hide the FPS counter and any debug overlays, and drop the game's graphics a notch if the recording stutters.

## Custom Script the Editor keeps

When writing a `CustomScript` into the Triggers XML: the Editor strips 12 characters of indent from each line, so indent accordingly; use `<InitFunc>`; `RegionPlayableMapArea` isn't available; and the timer type is `c_timeGame`. Write the same Galaxy into `MapScript.galaxy` too, since Test Document runs that file as it stands ([editor-and-engine.md](../../../docs/reference/editor-and-engine.md#test-document-and-mapscriptgalaxy)).
